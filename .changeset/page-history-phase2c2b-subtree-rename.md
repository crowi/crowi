Moving a whole subtree is now recorded in page history (RFC-0021 Phase 2c-2b), completing the rename story that Phase 2c-2a started for single pages. Every page the move touches gets its own `page_renamed` event marked as part of a subtree, and all of them are filed under one operation so the move reads as a single action rather than N unrelated renames. **Sending an `Idempotency-Key` is now required on both subtree-rename entry points** — `POST /pages/rename` with `include_descendants: true` and `POST /pages/rename-subtree` — so any client other than the built-in UI must be updated before upgrading; the two routes previously accepted the request without one. The two routes now behave identically in every respect that matters: both validate every destination path up front and refuse the whole move with 400 `PAGE_RENAME_TREE_FAILED` and the offending paths before anything is touched, both report a partial move with the same 400 response they always have, and both record history. Retrying with the same key never moves a page twice: the set of target pages is fixed when the request is first accepted, and a retry resumes the pages that have not moved yet rather than rescanning — so a page created under the subtree after the original request is not swept up by a retry, exactly as before. A move interrupted by a crash leaves the pages it had claimed in the same recoverable state a single-page rename does, and `crowi-admin page-history repair --transitions` now settles those too. **Replace every api replica at once when upgrading to this version rather than rolling them**, for the same reason Phase 2c-2a gave: an older replica does not recognise a page mid-move and can start a second move on top of one already underway. A single-instance deployment satisfies this automatically. These events are still not shown anywhere in the UI; the merged history view comes in a later phase.
