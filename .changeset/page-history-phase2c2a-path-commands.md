Renaming a page, moving it to the trash and restoring it are now recorded in the page's history (RFC-0021 Phase 2c-2a), alongside the visibility and draft-publish events that already were. Each of the three now runs as a durable operation: the request carries an `Idempotency-Key`, a repeated delivery of the same request returns the current page and an `Idempotency-Replayed: true` header instead of moving anything twice, and the same key sent with a different destination is refused with 409 `IDEMPOTENCY_KEY_CONFLICT`. **Sending the key is required** on `POST /pages/rename` (single-page only — a subtree rename is unchanged for now), the soft-delete branch of `DELETE /pages`, and `POST /pages/revert`; the built-in UI sends one per action, and any other client must be updated before upgrading. Hard delete, subtree rename, and internal callers such as user-page activation are unchanged and record nothing. While a page is between the two writes of a move it is briefly excluded from reads, listings and search rather than being served under an ambiguous path; a move interrupted by a crash leaves the page in that state, and `crowi-admin page-history repair --transitions` settles it or reports it with the operation, page and path so an operator can act — it never rewrites a page whose state it cannot classify. **Replace every api replica at once when upgrading to this version rather than rolling them**: a replica running the older version does not recognise the in-progress state and can start a second move on top of one already underway, leaving both unfinished. A single-instance deployment satisfies this automatically. Page creation and draft cancellation deliberately record nothing — there is no correct position in the current ordering for a creation event, and a cancelled draft leaves no trace by design. These events are still not shown anywhere in the UI; the merged history view comes in a later phase.
