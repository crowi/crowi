title: Storage drivers
description: Configuring local / S3 file storage
---

Attachments uploaded to Crowi are stored through a **storage driver**. In
Crowi 2.0, you select which driver to use in the runner project's
`crowi.config.json` (`storage.driver`), and the driver implementation
itself is provided by the corresponding `@crowi/plugin-storage-*` plugin.

> **Note**: The `FILE_UPLOAD` environment variable from Crowi v1 has been
> removed. Storage selection is done with the combination of the
> `storage.driver` field in `crowi.config.json` and the matching
> `@crowi/plugin-storage-*` package.

## Available drivers

| Driver name | Provided by | Storage target |
| ----------- | ----------- | -------------- |
| `local` | `@crowi/plugin-storage-local` (always enabled by default) | The server's local filesystem |
| `s3` | `@crowi/plugin-storage-aws-s3` | Amazon S3 (including S3-compatible storage) |
| `gcs` | `@crowi/plugin-storage-gcs` | Google Cloud Storage |

`@crowi/plugin-storage-local` is always loaded as an **implicit default
plugin**. If you write nothing in `crowi.config.json`, the `local` driver
is used.

## Local storage (local)

Local storage saves uploaded files on the server's filesystem. No
configuration is needed for the minimal setup — it is enabled by either
omitting `crowi.config.json` or writing the following.

```json
{
  "storage": {
    "driver": "local"
  }
}
```

The default storage directory is `data/uploads` (a path relative to the
directory containing `crowi.config.json`).

> **Tip**: When running in containers, mount the storage directory on a
> persistent volume. Local files are lost when a container is recreated.
> Using S3 removes that concern.

## S3 storage (s3)

To store files on Amazon S3 (or S3-compatible storage), use the
`@crowi/plugin-storage-aws-s3` plugin.

### 1. Enable the plugin

Add the S3 storage plugin to `plugins` in `crowi.config.json` and set
`storage.driver` to `s3`.

```json
{
  "plugins": [
    "@crowi/plugin-storage-aws-s3"
  ],
  "storage": {
    "driver": "s3"
  }
}
```

`@crowi/plugin-storage-aws-s3` depends on `@crowi/plugin-aws`, the shared
AWS credentials base, so the dependency plugin is loaded automatically.
For details on plugin resolution, see [Managing plugins](../plugins/managing).

### 2. Configure the bucket and credentials

The S3 bucket name and AWS credentials are configured from the admin UI.

- **Bucket name** — configuration of `@crowi/plugin-storage-aws-s3`
  itself. Open the "AWS S3" settings from the plugin settings
  (`/admin/plugins`) in the admin UI and enter it.
- **Region / access key / secret key** — configuration of
  `@crowi/plugin-aws`. Enter it from the plugin settings the same way.

The access key ID and secret access key are registered as sensitive, so
they are automatically encrypted at rest when `CROWI_ENCRYPTION_KEY` is
set. See [Encrypting sensitive config](./encryption) for details.

> **Tip**: When using an EC2 / ECS instance role or IRSA, leave the
> access keys blank — the AWS SDK's default credential resolution
> (environment variables and instance metadata) is then used.

### 3. Immediate application of settings

When you save the plugin settings from the admin UI, the S3 driver
applies the new bucket / credentials **without a server restart** via
`reconfigure`.

## GCS storage (gcs)

To store files on Google Cloud Storage, use the `@crowi/plugin-storage-gcs`
plugin.

> **Tip**: For creating the bucket, service account, and IAM grants on the Google Cloud side, see [Google Cloud setup](../plugins/storage/gcp).

### 1. Enable the plugin

Add the GCS storage plugin to `plugins` in `crowi.config.json` and set
`storage.driver` to `gcs`.

```json
{
  "plugins": [
    "@crowi/plugin-storage-gcs"
  ],
  "storage": {
    "driver": "gcs"
  }
}
```

### 2. Configure the connection

From the admin UI (`/admin/plugins`) → "Google Cloud Storage", configure
these four fields.

| Field | Required | Notes |
| ----- | -------- | ----- |
| GCS bucket | Yes | Existing private bucket name. Crowi does not create buckets. |
| Object prefix | No | Prepended to every Crowi object key. Leading/trailing `/` are stripped automatically. |
| Google Cloud project ID | No | Explicit project ID. Leave blank to use ADC's own project or the inline key's `project_id`. |
| Service account key JSON | No | Encrypted at rest. Leave blank to use Application Default Credentials (ADC). |

These four fields are saved together as **one encrypted atomic
document**, not as independent rows — a partial write where some fields
saved and others didn't never happens. If a service-account key is
already saved, updating only the other fields and leaving the key field
blank does **not** clear the stored key — the admin UI never re-sends an
unchanged secret.

The service-account key is a secret field: `GET /api/admin/plugins/config`
never returns its raw value, only `{ hasValue: true }` once one is
stored, and its contents are never written to application logs.

**Leaving Service account key JSON blank** uses
[Application Default Credentials (ADC)](https://cloud.google.com/docs/authentication/application-default-credentials)
— the environment's attached service account (GCE/GKE/Cloud Run), a
Workload Identity Federation credential, or a local `gcloud auth
application-default login`. This is the recommended setup when running on
Google Cloud: let the platform vend short-lived credentials instead of
storing a long-lived key in Mongo.

An invalid key JSON (invalid JSON, wrong `type`, a missing
`project_id`/`client_email`/`private_key`, or a `private_key` that isn't
a valid PEM block) is rejected with HTTP 422 before it is saved, listing
every failing field in `issues`.

### 3. Required IAM permissions

The driver calls three GCS object operations: `storage.objects.create`
(upload), `storage.objects.get` (download), and `storage.objects.delete`
(delete). A minimal custom role built from exactly these three permissions
is sufficient — the driver never lists objects. The predefined **Storage
Object User** role (`roles/storage.objectUser`) also works and additionally
bundles `storage.objects.list`, which the driver doesn't call but which
comes along with the role at no extra grant. No `storage.buckets.*`
permission is needed — Crowi never creates, lists, or configures buckets.

**Generating V4 signed URLs (`signBlob`) is a separate permission.** A
connection using an inline service-account key signs locally with the
private key, needing no extra permission. A connection using ADC needs
the IAM Credentials `signBlob` permission
(`roles/iam.serviceAccountTokenCreator` on itself, or an explicit
`iam.serviceAccounts.signBlob` grant) to sign. Crowi's attachment
delivery routes (`/api/attachments/:id`, etc.) do not call `signedUrl()`
today and always serve through the Crowi proxy, so missing `signBlob`
does not affect normal upload/download.

### 4. The prefix is not an IAM boundary

Setting a prefix separates Crowi's objects from other data in the same
bucket by naming convention, but this is **not an access-control
boundary**. Any principal with bucket-level access can still reach
objects outside the prefix.

### 5. Applying connection changes, and the full-stop caveat

Saving a connection while GCS is **not** the active driver
(`storage.driver` is something other than `gcs`) is a normal,
hot-reloadable save, same as any other plugin setting.

Changing the bucket / prefix / credentials while GCS **is already** the
active driver in a multi-instance deployment is different. This feature
adds no cross-replica coordination mechanism (no Redis pub/sub, lease, or
CAS) — each API replica applies the change to its own in-process state
independently. An online change would create a window where some
replicas keep reading/writing against the old connection. **The only
supported procedure is full-stop: stop every API replica, change the
configuration, then restart.**

### 6. Bucket deletion / permission revocation display behavior (an accepted limitation)

If the configured bucket is later deleted, permission is revoked, or the
prefix stops existing, the 404 GCS returns is indistinguishable from a
genuinely missing object. Display falls back to a placeholder, strict
download returns `FILE_MISSING`, and derivatives fall back to the
original — the same behavior as a real missing object, even though the
underlying cause is misconfiguration. This coarseness is shared with the
`local`/`s3` drivers; GCS is not treated specially. Catching
misconfiguration early is the job of a separate feature that verifies the
connection round-trip at save time.

### 7. Migrating files (local/S3 → GCS)

Migrating to GCS uses the same `crowi-admin rebuild storage copy` as any
other driver pair, but **there is no live/online migration** — only a
full-stop procedure that pauses both writes and read delivery during the
copy.

1. Save the GCS connection in the admin UI (`storage.driver` still points
   at the old driver).
2. Stop every API replica and every storage-mutating CLI/background
   worker. Confirm zero in-flight attachment upload/delete, profile image
   upload, page hard delete, and display-derivative
   generation/regeneration. Read delivery is also stopped for the
   duration.
3. With everything stopped, run `crowi-admin rebuild storage copy --from
   <old> --to gcs` and confirm `failed: 0`. As a read-verification step,
   the cheapest exhaustive check is a reverse copy into a disposable
   scratch destination (`--from gcs --to <scratch>`), confirming every
   object reads back successfully. `<scratch>` must **not** be the old
   driver still pointed at the original source data — that would overwrite
   the very rollback copy step 5 depends on. Use a fresh, disposable
   destination instead (e.g. a new `local` driver instance pointed at an
   empty temp directory).
4. Change `storage.driver` to `gcs` in `crowi.config.json` and restart
   every replica.
5. Spot-check upload/delete/profile image/attachment delivery/strict
   download, then re-enable background workers. If a rollback is needed,
   repeat the same full-stop procedure in reverse (keep the old storage
   intact for a rollback window).
6. Run `crowi-admin rebuild attachment-display-derivatives --force` to
   regenerate display derivatives from the originals now on GCS (see the
   Note under "crowi-admin rebuild attachment-display-derivatives" below).

### Opt-in emulator for development/testing

This plugin's unit/integration tests use an opt-in
`fsouza/fake-gcs-server` service (`docker-compose.yml`'s `crowi-test-gcs`,
`gcs-test` profile) that normal CI never starts.

```bash
docker compose --profile gcs-test up -d crowi-test-gcs
STORAGE_EMULATOR_HOST=http://127.0.0.1:4443 pnpm --filter @crowi/api test -- --runInBand src/plugin/storage-gcs.emulator.test.ts
docker compose --profile gcs-test stop crowi-test-gcs
```

Against this real GCS-JSON-API-compatible server, the opt-in suite
verifies Buffer/Readable upload-download round-trips, prefix mapping to
the correct physical object name, idempotent delete (existing object
succeeds, already-absent object is a no-op), missing-object `get()`
converting to the shape the unmodified `isMissingFileError` classifies as
missing, and a local-to-GCS `runStorageCopy` round-trip.

This emulator only accepts anonymous requests — it does not exercise ADC
discovery, real IAM permission checks, or `signBlob` availability.
Verifying real ADC / IAM / signed-URL behavior requires a real GCS
bucket.

## Checking the current storage status

Opening the storage screen in the admin UI (`/admin/storage`) shows the
list of registered drivers and which driver is currently active.
Internally it calls `GET /api/admin/storage`, which returns the
following for each driver.

- `driverName` — the driver name (`local` / `s3`, etc.)
- `pluginName` — the name of the plugin that registered the driver
- `isActive` — whether it is the driver selected in `crowi.config.json`

## Switching drivers and migrating files

When you switch drivers (e.g. `local` → `s3`), **new uploads are stored
on the new driver** as soon as you rewrite `crowi.config.json`. However,
**existing files are not moved automatically**. Files left on the old
driver are copied to the new driver with the `crowi-admin` CLI.

### crowi-admin rebuild storage copy

`crowi-admin` is an operator CLI intended to be run inside the server
(ssh / kubectl exec). The `rebuild storage copy` subcommand copies every object
from one driver to another.

```bash
# Copy all files from local to s3
crowi-admin rebuild storage copy --from local --to s3

# First check the target keys only (no copying)
crowi-admin rebuild storage copy --from local --to s3 --dry-run
```

Key points:

- **Both the source and destination drivers must be loaded** by some
  plugin. This is unrelated to the "active driver" pointed to by
  `storage.driver` in `crowi.config.json`, so you can copy data from
  `local` to `s3` before making `s3` active.
- With `--dry-run`, it only enumerates the candidate keys and performs
  no actual writes. Use it to check the count in advance.
- Attachment rows are processed sequentially via a MongoDB cursor, so
  memory usage stays constant even with a very large number of files.
- A per-key error does not stop the iteration; it is added to the
  `failed` count. Re-running is safe (the local / S3 drivers overwrite
  by key).

The exit codes are as follows.

| Exit code | Meaning |
| --------- | ------- |
| `0` | Everything copied successfully (or dry-run completed) |
| `1` | Fatal error (init failed, or an exception before work started) |
| `2` | Partial failure (the copy ran but one or more keys failed — retry recommended) |

### Recommended migration steps

A safe procedure for migrating from `local` to `s3`:

1. Add `@crowi/plugin-storage-aws-s3` to `crowi.config.json:plugins` and
   configure the S3 bucket / credentials in the admin UI (keep
   `storage.driver` as `local` for now).
2. Run `crowi-admin rebuild storage copy --from local --to s3 --dry-run` to
   check the target count.
3. Run `crowi-admin rebuild storage copy --from local --to s3` to copy for real.
   If any `failed` appears, re-run it.
4. Change `storage.driver` in `crowi.config.json` to `s3` and restart
   the API.
5. Verify that new uploads and downloads work through S3.

> **Tip**: If you stage the data on S3 first in step 1, S3 is usable
> with zero downtime the moment you switch the driver.

### crowi-admin rebuild attachment-display-derivatives

Images in [Attachments](../guide/attachments) get a display-optimized
derivative generated on a best-effort basis at upload time. The `rebuild
attachment-display-derivatives` subcommand backfills, repairs, and
reclaims those derivatives for existing attachments.

```bash
# Generate for anything missing/failed, as usual
crowi-admin rebuild attachment-display-derivatives

# Check the target count first (writes nothing)
crowi-admin rebuild attachment-display-derivatives --dry-run

# Re-generate everything, including records already on the current recipe
# (required after a storage migration — see below)
crowi-admin rebuild attachment-display-derivatives --force

# Repair only records whose metadata says "resized" but the object is gone
crowi-admin rebuild attachment-display-derivatives --repair-missing

# Report orphaned derivative objects (local driver only, no deletion)
crowi-admin rebuild attachment-display-derivatives --gc

# Actually delete the reported orphans
crowi-admin rebuild attachment-display-derivatives --gc --confirm
```

Key flags:

| Flag | Description |
| ---- | ----------- |
| `--dry-run` | Writes nothing to Mongo or storage; reports only the target count and breakdown |
| `--concurrency <n>` | Worker pool size (default `2`) — see the capacity estimate below |
| `--force` | Re-evaluate and overwrite records already described under the current recipe |
| `--repair-missing` | Only targets current-recipe `resized` records; probes existence via `get()` and regenerates only the ones whose object is actually gone (a lighter mode — no decode/re-encode for objects that are still present) |
| `--only-missing` | Only targets attachments with no `derivatives.display` recorded yet |
| `--only-stale` | Only targets attachments whose recorded `recipeVersion` is not the current one |
| `--page-id <id>` | Only targets attachments on this page |
| `--since <iso>` | Only targets attachments created on/after this ISO 8601 timestamp |
| `--until <iso>` | Only targets attachments created on/before this ISO 8601 timestamp |
| `--gc` | Reports candidate derivative objects with no referencing Attachment (local driver only, v1) |
| `--gc-grace-hours <n>` | Excludes `--gc` candidates newer than this many hours (default 24) — a safety margin against mistaking an in-flight `put`→publish for an orphan |
| `--confirm` | Actually deletes `--gc` candidates (report-only otherwise) |

Key points:

- **A normal run (no `--force`/`--repair-missing`) is idempotent.**
  Current-recipe `resized`/`passthrough`/`unsupported` records are
  skipped; only `failed`, never-generated, or stale-recipe records are
  reprocessed. **If a `resized` record's metadata says the object exists
  but it has actually been lost from storage, a normal run does not
  detect that and keeps skipping it** — repairing this needs `--force`
  or `--repair-missing`.
- Attachment rows are pulled by a **single producer** through a MongoDB
  cursor; only the processing of each pulled item is fanned out to a
  bounded worker pool sized by `--concurrency` (memory usage stays
  constant, same as `storage copy`).
- Each worker stages the original into a local tmp directory before
  handing it to the generator, and deletes its own staged file
  afterward. The rough amount of data staged concurrently is
  **`--concurrency` × 100MB** (based on the actual upload ceiling for
  the footer add path). If you raise `--concurrency` above the default,
  re-multiply this disk/memory estimate accordingly. Free space is
  checked before staging; an item is safely skipped and recorded as
  failed if there isn't enough.
- **SIGINT (Ctrl-C)** stops accepting new items, cleans up any in-flight
  staged tmp file, prints the progress summary so far, and **exits
  non-zero**.
- A per-item failure does not stop the run; the Attachment ID and a
  classified reason are printed for each one.

Exit codes:

| Exit code | Meaning |
| --------- | ------- |
| `0` | Everything succeeded (or dry-run completed) |
| `1` | Fatal error (init failed, or an exception before work started) |
| `2` | Partial failure (one or more items failed — check the `failed` list and consider re-running) |
| Interrupted by SIGINT | Exits non-zero regardless of the above |

> **Note**: **Running `--force` is required right after a storage
> migration.** `storage copy` only copies originals, never derivatives
> (derivatives are disposable cache, not durable data). If you run
> `rebuild attachment-display-derivatives` normally after a migration,
> every `resized` record is still treated as "complete" even though its
> object doesn't exist on the new driver — a normal run skips all of
> them and **regenerates nothing**. Run `--force` (re-evaluate
> everything) or, to target only the lost descriptors, `--repair-missing`.
> Until `--force` runs, the canonical URL keeps safely falling back to
> the original (no data loss, just a temporary cache miss).

> **Note**: **Residual orphan risk on S3.** The local driver's atomic
> writes, plus the deletion path's atomic snapshot read and deterministic
> key sweep, close nearly every orphan source in normal operation. A
> residual risk remains only if the operational convention (run at most
> one rebuild/`--gc` process at a time) is violated — e.g. two processes
> racing on the same attachment. `--gc` only supports the local driver in
> v1; on S3 it reports "unsupported" and exits cleanly. If long-term
> accumulation is a concern, apply a conservative (e.g. ~1 year)
> expiration lifecycle rule to the `derivatives/` prefix on S3 **as a
> last-resort safety net only** — a lifecycle rule cannot tell whether an
> object is still referenced and only judges by elapsed time, so a short
> expiration would silently delete live derivatives and degrade delivery
> to the original fallback. It is not a substitute for `--gc`.
