This page explains how to think about data compatibility when migrating
from Crowi v1 to v2, and the migration paths available today.

## What is v2 (Reignite)

Crowi v2 is a version with a fully rebuilt frontend.

- **v1**: An Express + Swig (templating) + jQuery monolith
- **v2**: Hono API (`@hono/zod-openapi`) + Next.js 16 (App Router) + React 19

The UI and application layers have been rebuilt, but the **data layer
(the shape of the data in MongoDB) stays compatible with v1**. The
document structures for pages, revisions, users, comments, and so on can
be read as-is from v1. In other words, your existing wiki data is designed
to carry over to v2.

## Current state of data compatibility

| Area | Compatibility |
| ---- | ------------- |
| MongoDB document shape | Compatible with v1. v2 reads existing data as-is |
| Attachments | Accessed via the storage driver. Storage location is the same as v1 |
| Passwords | Falls back to legacy hash verification with `PASSWORD_SEED` |
| Config | v1 Config is also readable. Sensitive-value encryption is a new (optional) v2 feature |

> **Note**: v2 adds a mechanism to encrypt sensitive Config (OAuth secrets,
> SMTP passwords, etc.) with AES-256-GCM. Plaintext config rows inherited
> from v1 are still readable as-is, but if you enable encryption you can
> re-encrypt them with the crypto feature in the admin panel. See
> [Encrypting sensitive settings](./encryption) for details.

## Current state of the migration path

The data shape is compatible, but the **v1 → v2 migration path itself is
still being worked on**.

- Booting v2 directly against a v1 MongoDB is technically possible, but
  there is no officially verified and documented migration procedure yet.
- Some data needs conversion to match v2's new features (such as the
  wikilink migration described below).
- Migration procedures and tools will be developed incrementally toward
  the stable release.

For this reason, we strongly recommend that for now you **do not migrate
production data**, and limit yourself to trying it out in a verification
environment using a copy of your v1 data.

## Re-entering credentials

The storage and mail credentials that lived in v1's core config
(`crowi:upload:aws:*`, `crowi:mail:aws:*`, `crowi:mail:smtpPassword` and the
like) do not exist in v2. **Enable the matching plugin and enter the values
again**: they are stored in that plugin's namespace and encrypted
automatically when [Encrypting sensitive settings](./encryption) is configured. Nothing is
migrated automatically and the old keys are never read as a fallback.

## The migration framework (crowi-admin migrate)

v1 → v2 data migrations run through the migration commands,
exposed as the `crowi-admin migrate plan | apply | status | list`
namespace. Because `crowi-admin` connects directly to MongoDB, run it from
the runner project directory (where `@crowi/api` is installed). In the
monorepo, the `pnpm migrate` wrapper runs the same CLI.

In the **official Docker image**, `crowi-admin` is bundled into the runner
project tree (rooted at `/app`), so you run it inside the container:

```bash
# Apply pending preflight migrations inside the running container
docker compose run --rm --entrypoint node api \
  node_modules/@crowi/admin-cli/dist/bin.js migrate apply
```

This matters most for the preflight `block` policy below: when a deploy
introduces an unapplied **blocking** preflight migration the api refuses to boot, and the
command above is how you unblock it from inside the image.

Migrations are split into two layers:

- **boot** migrations apply automatically when the api starts.
- **preflight** migrations are heavier / potentially destructive, so they
  are *not* applied automatically. They are probed on every boot, and what
  happens when one is still unapplied depends on its **severity** (see below):
  a `blocking` migration **refuses boot** (the default `block` policy), while a
  `cosmetic` one only **warns and lets boot continue**. You apply preflight
  migrations explicitly with `crowi-admin migrate apply` during a maintenance
  window.

Each migration carries a `severity` that decides what an unapplied preflight
migration does to boot:

- **`blocking`** — an index-impacting / data-integrity migration (`user-unique-prepare` and `page-liker-seenusers-to-relations`). If it is unapplied, the api refuses to boot under the default `block` policy, because booting against not-yet-prepared data risks an `E11000` failure when the unique index builds. `migrate plan` / `migrate list` tag it `[blocking]`.
- **`cosmetic`** — a body-display-only migration (such as `wikilink-format`).
  If it is unapplied the api **still boots** and only logs a warning, **even
  under the `block` policy**. Cosmetic migrations re-scan the live corpus, so a
  newly written page in the old syntax can make them pending again forever;
  blocking boot on them would deadlock the cluster. `migrate plan` /
  `migrate list` tag them `[cosmetic]`.

```bash
# Preview pending migrations (preflight by default)
crowi-admin migrate plan
# or, in the monorepo:
pnpm migrate plan

# Apply pending preflight migrations
crowi-admin migrate apply

# Show how many migrations are pending
crowi-admin migrate status
```

> **Tip**: `crowi-admin`'s stdout carries only the command's own output. The
> boot-time `[crowi] Loaded N plugin(s)` line moves to stderr in development
> and is fully suppressed under `NODE_ENV=production`, so a pipe like
> `crowi-admin migrate plan --json | jq` never breaks. Node's own deprecation
> warnings (e.g. `DEP0169`) are also always suppressed under `crowi-admin`.
> Running through `pnpm migrate plan`, though, still prints pnpm's own script
> banner (`> crowi@... migrate`, etc.) to stdout — that's pnpm's own behavior
> and can't be silenced from the code — so pipe with `pnpm -s migrate plan
> --json | jq` (`-s` for silent) instead.

> **Tip**: The `block` policy only ever applies to `blocking` migrations, so
> you can safely keep the default `block` in production: `cosmetic` migrations
> (the display-only ones) never refuse boot regardless of policy, and only
> data-integrity `blocking` migrations do. If you ever need to boot with a
> `blocking` migration still pending — a controlled, single-instance
> investigation, for example — set `MIGRATION_PREFLIGHT_UNAPPLIED_POLICY=warn`
> to downgrade its boot refusal to a warning.
>
> **Multi-instance note**: `MIGRATION_PREFLIGHT_UNAPPLIED_POLICY` (env var)
> takes precedence over the `migration.preflightUnappliedPolicy` admin Config.
> If some replicas have the env var and others rely only on the Config, they
> can resolve **different** policies against the same database. Set the env var
> **consistently on every replica** (e.g. one Kubernetes ConfigMap injected
> into all pods) so the whole cluster agrees.

The registered migrations are:

| ID | Layer | Severity | What it does |
| ---- | ---- | ---- | ---- |
| `page-status-default` | boot | — | Backfill `page.status` |
| `revisions-schema-unify` | boot | — | Unify the revision schema (backfill `type:snapshot`) |
| `wikilink-format` | preflight | cosmetic | Convert wikilink syntax |
| `user-unique-prepare` | preflight | **blocking** | Deduplicate users (prepare for the unique index) |
| `relocate-reserved-api-paths` | preflight | cosmetic | Move v1 pages out of the reserved `/api` namespace |
| `files-url-to-attachments` | preflight | cosmetic | Rewrite v1 file URLs (`/files/<id>`) in page bodies to the `/api/attachments/<id>` form |
| `wikilink-html-recover` | preflight | cosmetic | Recover HTML close tags (`</font>` etc.) corrupted into wikilinks |
| `page-liker-seenusers-to-relations` | preflight | **blocking** | Migrate `pages.liker` / `pages.seenUsers` into the `likes` / `seens` relation collections |

(Severity applies only to `preflight` migrations — `boot` migrations are applied automatically and never probed, so they have no boot-block severity. `user-unique-prepare` and `page-liker-seenusers-to-relations` are the two `blocking` migrations; the rest are `cosmetic`, so an unapplied one warns but never refuses boot.)

The boot migrations (`page-status-default` / `revisions-schema-unify`) apply
automatically when the api starts, so they need no operator action. The
sections below focus on the preflight migrations, which you apply explicitly.

### wikilink migration

The `wikilink-format` preflight migration converts v1-era wikilink syntax
to match the v2 renderer.

```bash
# First check what will change (does not write new revisions)
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id wikilink-format
```

`migrate plan` only scans the target pages and reports; it does not write
anything. Always check the scope of impact before applying. The migration
needs an admin user to attribute the rewrites to — set `CROWI_MIGRATE_USER=<email>`
if no admin user is resolvable.

This migration **excludes code regions** — a `</…>` or wikilink-like string
inside a fenced code block or inline code is left untouched (no false-positive
rewrite). Applying it also **preserves each page's last-updated time and last
editor**: a migration rewrite is a maintenance operation, not a user edit, so
page list ordering and "last edited by" stay intact.

> **Tip**: v1-era wikilink syntax can also be interpreted at render time
> by the `@crowi/plugin-renderer-crowi-legacy` plugin. If you would rather
> not convert the data itself, enabling that plugin is an alternative.
> For plugins, see [Plugin architecture](../develop/plugins-overview).

### Recovering corrupted HTML close tags (wikilink-html-recover)

Where the `wikilink-format` migration was run on an older Crowi, the
**deprecated HTML close tags** used in headings and inline markup
(`</font>`, `</center>`, `</marquee>`, `</blink>`, `</applet>`) may have been
rewritten into the wikilink form (`[[/font]]`). The current migration leaves
them alone, but bodies already mangled that way do not self-heal, because
`wikilink-format` never re-runs.

The `wikilink-html-recover` preflight migration reverts the corrupted form
`[[/<x>]]` back to `</x>` **only for those five deprecated tags**
(`font` / `center` / `marquee` / `blink` / `applet`) — the only close tags the
misfire could ever have produced. Every other single-segment wikilink is left
untouched,
including ones whose name happens to be a standard HTML element
(`[[/section]]`, `[[/div]]`, `[[/br]]`): those were always known, so
`wikilink-format` never rewrote them and they are **genuine wikilinks**.
Multi-segment (`[[/foo/bar]]`), aliased (`[[/font|alias]]`) and uppercase
(`[[/Font]]`) forms are preserved too.

```bash
# Preview what would be recovered (does not rewrite bodies)
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id wikilink-html-recover
```

> **Caution**: `[[/font]]` could be a corrupted `</font>` OR a genuine
> wikilink to a real page literally at `/font` — the two are indistinguishable
> from the text alone. This migration does **not** auto-convert a `[[/<x>]]`
> whose `/<x>` matches an **existing live page**; instead it reports those in
> the `migrate plan` output so an operator can decide by hand. It **does** still
> revert a `[[/font]]` (or the other four deprecated tags) when no such page
> exists — including a dangling link to an absent / deleted page. In practice a
> real wiki page literally named `/font`, `/center`, `/marquee`, `/blink` or
> `/applet` is very rare, but if you have one, review the collisions in
> `migrate plan` and validate on dev / staging before applying in production.

The migration is idempotent — once reverted, `</x>` matches neither the
recovery scan nor the `wikilink-format` rewrite, so re-running has no double
effect.

> **Note**: A `[[/font]]` (and the like) written inside a code fence (```` ``` ````)
> or an inline code span (`` `…` ``) is **out of scope** for this migration — a
> `[[/font]]` written as a code example (e.g. in documentation about the migration)
> is left byte-identical, never reverted to `</font>`. This matches the
> code-exclusion behaviour of `wikilink-format` (`</…>`) and
> `files-url-to-attachments` (`/files/<id>`); all three body-rewrite migrations
> behave identically. Because of this, a page whose only such token lives inside
> code is never falsely reported as "pending", so it cannot block boot forever
> under the preflight + `block` policy.

### /api namespace relocation

v1 served its API under `/_api/*`, so `/api/*` (no underscore) was an
ordinary wiki page path. v2 reserves `/api` for the reverse-proxied backend
(`/api/*`), so any v1 page still living under `/api/*` would be stranded
— the web app 404s the reserved namespace, and those same paths are shadowed
by the proxy entirely.

The `relocate-reserved-api-paths` preflight migration moves every such page
to `/api-legacy/*` (preserving the rest of the path; a pre-existing target
gets a `-N` suffix). No redirect is left at the old path — it sits inside the
reserved namespace. Wikis with no `/api/*` pages see nothing to apply.

```bash
# Preview which pages would move
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id relocate-reserved-api-paths
```

### Preparing user uniqueness (user-unique-prepare)

v1 did not strictly enforce uniqueness on `username` / `email` (it allowed
case-insensitive duplicates, and deleted users could linger while keeping
their original identity). v2 declares **case-insensitive unique indexes** on
`username` / `email` (built by autoIndex on boot), so any colliding data left
behind makes the index build fail with `E11000`.

The `user-unique-prepare` preflight migration prepares the data so the index
can build (it does not build the index itself).

- **dedup-username** — merges living users that collide on a case-insensitive
  username into one, reassigning ownership references to the survivor and
  deleting the rest.
- **dedup-email** — does the same for email.
- **tombstone-deleted** — renames any deleted user that would collide with a
  living user (or another deleted user) to the per-id `deleted-<id>` tombstone,
  matching the runtime delete behaviour.

```bash
# Preview how many rows would be merged / deleted / renamed
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id user-unique-prepare
```

> **Caution**: This migration **merges and deletes** users. Always review the
> scope with `migrate plan` and take a MongoDB backup before applying.

### Migrating Like / seen-by relations (page-liker-seenusers-to-relations)

v1, and every 2.0-alpha up to and including alpha.17, stored Like and "seen by" membership directly on the `pages` document as `pages.liker` / `pages.seenUsers` ObjectId arrays. Later versions switched to the independent `likes` / `seens` collections and dropped both fields from the `Page` schema, but a schema change alone does not remove fields already persisted in MongoDB. The `page-liker-seenusers-to-relations` preflight migration is a one-time, **forward-only** copy of that legacy data into `likes` / `seens`, followed by removing the fields from `pages`.

Unlike most other preflight migrations, this one **requires a maintenance window**. Two reasons:

1. The `likes` / `seens` `{page,user}` unique index does not exist until this migration's first stage (`prepare-target-index`) explicitly builds it.
2. Before the migration runs, `likes` / `seens` hold none of the existing Like / seen-by data, so starting the new api first makes every Like / seen-by count read as zero.

Follow these steps **in order**:

1. Confirm the target is v1 or any 2.0-alpha up to and including alpha.17.
2. Enter maintenance mode: stop every old and new writer and background worker, and drain in-flight traffic at the load balancer / proxy.
3. Take a MongoDB backup and confirm it is restorable.
4. From the new image's admin CLI, run `crowi-admin migrate plan` and review `page-liker-seenusers-to-relations`'s detect counts along with every other pending `blocking` migration.
5. Run `crowi-admin migrate apply --id page-liker-seenusers-to-relations`.
6. Run `crowi-admin migrate plan` again. If any other `blocking` migration is still pending, apply it **by id**, one at a time, with `crowi-admin migrate apply --id <id>`, then re-run plan.
7. Confirm via the `plan` output that the target id and every other `blocking` migration are no longer pending. Do not deploy until this is confirmed.
8. Deploy the new binary and confirm boot completes, including the relation unique-index build.
9. Smoke test liking / unliking a page and viewing it (seen-by) and confirm the counts look right.
10. Resume traffic.

```bash
# Preview the target migration and every pending blocking migration (no writes)
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id page-liker-seenusers-to-relations

# Check for remaining pending blocking migrations, then apply each by id
crowi-admin migrate plan
crowi-admin migrate apply --id <remaining blocking migration id>
```

> **Caution**: Do NOT use a bare `crowi-admin migrate apply` (no `--id`) during this window. Without `--id`, `apply` applies every pending preflight migration, including `cosmetic` ones. In particular, `wikilink-format` rewrites page bodies and re-scans the live corpus, so it stays pending under normal operation — running it here would pull an unrelated, large batch of revision writes into a window meant only for this migration. Always target the specific id.

#### Recovering from a failed apply

When `migrate apply` fails, the error message itself carries enough detail to identify what to fix (counts plus up to 20 samples that name the affected page/user). Restoring the full backup is the last resort, not the first response.

- **A duplicate report**: `likes` / `seens` has duplicate rows. For each listed `{page,user}`, delete duplicate rows down to one. If a row has a non-null `createdAt` (a live row the new binary wrote outside the maintenance window), keep that one; otherwise any one of them may be kept. Re-run the same `apply --id` afterward.
- **A missing report**: the legacy fields on `pages` have not been unset yet, so the source data is intact. Resolve the underlying cause (e.g. a dropped connection) and re-run the same `apply --id` — copy and verify will re-run from scratch and converge.
- **Any other error**: resolve the cause named in the message and re-run the same `apply --id`.

In every case, re-running is safe as long as the legacy fields are still present — `isPending` stays `true` until they are gone.

> **Note**: If you boot with this migration still pending via `MIGRATION_PREFLIGHT_UNAPPLIED_POLICY=warn`, Like / seen-by counts from before the migration are not counted during that window, and any unlike a user performs during it is not reflected back onto the legacy arrays — a later `apply` can bring a Like back that the user had removed. Once `$unset` completes, do not roll back to the old binary; fix forward, or restore the full pre-migration backup if something is wrong.

> **Note**: This migration excludes invalid elements and duplicates within one page when computing the real relation row count, so `likerCount` / `seenUsersCount` can be lower than a raw array-length count would have shown. For a non-array (scalar) stored value, only an invalid one is dropped by this correction — a **valid** ObjectId (already counted as a single Like today) is not excluded; it migrates as exactly one relation and is not part of this count correction.

### Rebuilding the search index

If you want to use full-text search on data migrated from v1, you need to
rebuild the search index on the v2 side.

```bash
crowi-admin rebuild search
```

See [Search backend setup](./search-setup) for details.

### Storage migration

To change where attachment files are stored (for example from local to
S3), use the storage copy command.

```bash
crowi-admin rebuild storage copy --from local --to s3 --dry-run
crowi-admin rebuild storage copy --from local --to s3
```

> **Note**: v1 AWS / S3 credentials (the old `upload:aws:*` core config) are
> **not carried over**. Enable `@crowi/plugin-aws` (and
> `@crowi/plugin-storage-aws-s3`) and re-enter the credentials in the admin
> **Plugins** screen — they are stored in the plugin's namespace and encrypted.

### Bulk URL replacement after a domain change (replace url)

If you **changed the public domain (host)** during the v1 → v2 migration,
page bodies keep their **absolute URLs** pinned to the old host (image embeds
and links, e.g. `![shot.png](https://old.example/files/<id>)`). Page / file
ids carry over unchanged, so the fix is a **literal host (URL prefix) swap**,
not an id remap.

`crowi-admin replace url` replaces a **literal string** in every page body,
from `--from` to `--to` (a verbatim match, not a regex — safe for URLs full of
`/` `.` `?`).

```bash
# Preview what would change first (writes nothing)
crowi-admin replace url --from https://old.example --to https://new.example --dry-run

# Run it (prompts to confirm the number of pages)
crowi-admin replace url --from https://old.example --to https://new.example
```

The replacement is a **quiet rewrite that is invisible to end users**. It
pushes a new revision per page, but leaves the last-updated time, the last
editor and the visibility untouched, and notifies no watchers (and auto-watches
no one). Listings and notifications do not move, which is what you want for a
domain cleanup.

The options are listed in [crowi-admin](../reference/admin-cli). Without `--yes` and without a TTY, the command refuses to write.

> **Caution**: Passing a **bare host without a scheme** like `old.example` to
> `--from` risks corrupting longer hosts that share the prefix, such as
> `old.example.com`. The CLI refuses this by default and requires `--force`.
> Prefer a full origin like `https://old.example` whenever possible.

After a run, each page's rendered HTML is regenerated as the new revision, so
it is fresh. The **search index, however, must be rebuilt separately**
(`crowi-admin rebuild search`). Backlinks are unaffected (external URLs are not
internal links).

> **Note**: `replace url` is neither a versioned migration (it takes arbitrary
> from/to and is re-runnable) nor a derived-data rebuild (it mutates page
> bodies), so it lives in its own namespace — not under `migrate` or `rebuild`.

### Modernising file URLs (files-url-to-attachments)

v1 referenced attachments / images in page bodies with **v1 file URLs** (the
relative form `![shot.png](/files/<id>)`, or the absolute form
`![shot.png](https://wiki.example/files/<id>)` when the editor pasted a full
URL). Crowi 2.0 serves attachments from a dedicated stream endpoint at
`/api/attachments/<id>` and the legacy `/files/<id>` compat route was
removed, so **v1-form URLs now 404 — those images are broken**. The id is the
same 24-hex attachment id in both v1 and v2, so the fix is **just a URL
rewrite** (no id remap).

The `files-url-to-attachments` preflight migration walks the current-revision
body of every published page (plus legacy `null` status) and rewrites the URL of
Markdown images `![alt](url)` / links `[text](url)` by these rules (raw HTML
`<img>` / `<a>` is out of scope):

- **relative `/files/<id>`** → `/api/attachments/<id>` (unconditional — a
  root-relative path is always this site).
- **self-host absolute `https://<CLIENT_URL host>/files/<id>`** →
  `/api/attachments/<id>` (relativised by dropping the host, so the URL
  becomes host-independent). Self-host is decided by matching the `CLIENT_URL` /
  `BASE_URL` origins only.
- **external-host absolute URLs** → **left untouched** (so an unrelated
  third-party `/files/<id>` image is never rewritten by mistake).

```bash
# Preview what would be rewritten first (writes nothing)
crowi-admin migrate plan

# Apply just this migration
crowi-admin migrate apply --id files-url-to-attachments
```

The migration is idempotent: the rewritten `/api/attachments/<id>` is never
double-converted on a re-apply. It needs an admin user to attribute the rewrites
to — set `CROWI_MIGRATE_USER=<email>` if none is resolvable.

> **Tip**: If you **changed the domain**, first align the old host → new host
> with [replace url](#bulk-url-replacement-after-a-domain-change-replace-url),
> then apply this migration. Once `replace url` lines up the self-host absolute
> URLs with the `CLIENT_URL` host, this migration can relativise them; in the
> opposite order the old-host absolute URLs are classified as "external" and
> left alone.

> **Note**: As a safety net for migration misses and un-rewritten bodies, the
> api restores a `/files/<id>` → `302` `/api/attachments/<id>` redirect. A
> runtime request to a relative `/files/<id>` is forwarded to the canonical form, so an
> image is not left broken even if the body rewrite has not run yet (absolute
> URLs pointing at an external host cannot be saved by the redirect, which is why
> the body rewrite is the primary fix).

> **Note**: A `/files/<id>` URL written inside a code fence (```` ``` ````) or an
> inline code span (`` `…` ``) is **out of scope** for this migration — a
> `![pic](/files/<id>)` written as a code example is left byte-identical, never
> rewritten. This matches the code-exclusion behaviour of `wikilink-format`
> (`</…>`) and `wikilink-html-recover` (`[[/font]]`); all three body-rewrite
> migrations behave identically. Because of this, a page whose only such URL lives
> inside code is never falsely reported as "pending", so it cannot block boot
> forever under the preflight + `block` policy.

## What to do before migrating

Before actually trying a migration, complete the following.

1. **Take a complete backup of the v1 data** — back up MongoDB with
   `mongodump` and the attachments via the storage driver's location.
   See [Backup](./backup) for the procedure.
2. **Prepare a verification environment** — use a copy of the v1 data and
   bring up v2 in an environment isolated from production.
3. **Prepare a `CROWI_ENCRYPTION_KEY`** — if you will use sensitive-config
   encryption in v2, generate a key and store it securely.
4. **Preview the migrations first** — run `crowi-admin migrate plan` to
   see the pending preflight migrations, and `rebuild storage copy ... --dry-run`,
   before applying anything for real.

## Summary

- v2's data shape is compatible with v1, and existing wiki data carries
  over.
- The `crowi-admin migrate` framework (with `plan` / `apply` and the
  preflight-block boot guard), plus `rebuild search` / `rebuild storage copy`
  and `replace url` for bulk URL replacement after a domain change, are
  provided. Preview each one (`migrate plan` / `--dry-run`) before applying.
- Migration procedures will be documented toward the stable release. See
  the [release notes](https://github.com/crowi/crowi/releases) and Crowi's release announcements for the
  latest status.
