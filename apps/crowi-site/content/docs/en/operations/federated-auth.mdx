---
title: Signing in with an external account
description: Setting up sign-in through an OAuth2 / OIDC provider such as Google
---

Crowi takes authentication providers as plugins. Enabling `@crowi/plugin-google` puts a "Sign in with Google" button on the sign-in screen and lets people sign in to Crowi with their Google account. See [RFC-0014](https://github.com/crowi/crowi/blob/main/docs/rfcs/0014-auth-provider-plugins.md) for the design.

Google is not special-cased. Everything protocol-shaped — OIDC discovery, state / PKCE / nonce, the token exchange, ID token verification — lives in Crowi itself, and the plugin supplies only three Google-specific things: where to discover, which scopes to ask for, and what to call the button. A plugin for any other OIDC provider works the same way.

## Required environment variables

The redirect URI for external sign-in is built from a **configured public URL, never from the request's `Host` header**. So one of these is required:

| Variable | Default | Purpose |
| -------- | ------- | ------- |
| `AUTH_PUBLIC_WEB_URL` | `CLIENT_URL` | The public origin of Crowi as the browser sees it |
| `AUTH_PUBLIC_API_URL` | the resolved web URL | The public origin of the API. Leave unset when it shares an origin with the web app |

Both must be origin-only (no path, query, or fragment) — including one fails boot. **When both are unset, external sign-in is silently disabled**: boot succeeds, the provider list comes back empty, and `/api/auth/providers/<name>/start` returns 404. This is the first thing to check when no button appears.

Setting up [config encryption](./encryption) (`CROWI_ENCRYPTION_KEY`) is also strongly recommended so the client secret is stored encrypted. It works without one, but the secret is then stored in the database as plaintext.

## Setup

### 1. Enable the plugin

Add `@crowi/plugin-google` to your runner project's `package.json` dependencies and list it in the `plugins` array of `crowi.config.json`.

```json
{
  "plugins": ["@crowi/plugin-google"]
}
```

### 2. Create an OAuth client in Google Cloud

In the [Google Cloud Console](https://console.cloud.google.com/apis/credentials), create an "OAuth 2.0 Client ID" of type **Web application** and register this as an **Authorized redirect URI**:

```
<AUTH_PUBLIC_API_URL>/api/auth/providers/google/callback
```

With `AUTH_PUBLIC_API_URL="https://wiki.example.com"`, for instance, that is `https://wiki.example.com/api/auth/providers/google/callback`. A single character of difference produces a `redirect_uri_mismatch` on Google's side.

### 3. Enter the credentials in the admin screen

Open the Google plugin under **Plugins** in the admin screen, enter the Client ID and Client secret, and save. No restart is needed — the button appears on the sign-in screen as soon as the save succeeds.

The Client ID and secret are stored as **one setting in a single document**. A state where only one of them was saved cannot arise, and entering just one leaves the provider "not configured", so **a button that could only fail is never shown on the sign-in screen**.

## What happens at sign-in

How a first-time Google sign-in is handled follows the **registration mode (registrationMode)** setting in the [admin screen](./admin).

| Registration mode | An unregistered user signing in with Google |
| ----------------- | ------------------------------------------- |
| Open | Picks a username, the account is created and becomes active immediately |
| Restricted | Picks a username, the account is created and **waits for administrator approval** |
| Closed | Sign-in is refused and the sign-in screen explains that registration is closed |

A few constraints matter:

- The email address is used **only when Google asserts it is verified**. An unverified address is not accepted.
- **An address matching an existing local account is not linked automatically.** That sign-in fails instead. Sign in with the password first, then link the account explicitly from the settings screen. This is deliberate: matching email addresses alone must never hand over control of an existing account.

## Linking and unlinking accounts

A signed-in user can attach or detach external providers from **Settings → Password / API tokens / Linked accounts**. Linking runs as three authenticated steps rather than a single top-level redirect:

1. Pressing **Link** sends an authenticated `POST /auth/providers/<name>/link-start`, which returns an authorization URL and sets a short-lived, flow-specific cookie. The browser then navigates to the provider.
2. The provider redirects back to Crowi's callback, which verifies the flow and — without reading or writing any Crowi user data — issues a one-time confirmation code, then redirects to `/me?provider=<name>&link_completion=<code>`.
3. The settings screen shows a confirmation dialog (the provider's display label, plus the account's email when the provider returns one) and only inserts the identity once the user presses **Link** again, which sends an authenticated `POST` to consume the code.

Each step has its own lifetime: the link-start state is valid for 300 seconds, the confirmation code for 300 seconds from the moment the callback issues it, and a consumed code is retained for 5 minutes so a browser that loses the response to the final `POST` can safely resend it and get the same answer back.

Linking is **same-site only**: the `link-start` request is sent with `credentials: 'include'`, so a split-origin deployment (`AUTH_PUBLIC_WEB_URL` different from `AUTH_PUBLIC_API_URL`) works as long as both are on the same registrable domain — Crowi's production CORS allow-list includes the resolved `AUTH_PUBLIC_WEB_URL` origin exactly, alongside `CLIENT_URL`. A deployment that needs third-party cookies (unrelated domains) is not supported.

**Multi-instance deployments must set `REDIS_URL`.** A shared Redis is required so the confirmation code issued by whichever API replica handled the callback is visible to whichever replica later handles the confirmation. This fails **closed**: with `CROWI_MULTI_INSTANCE` declared and no Redis client available, the very first `link-start` request returns a `500` before issuing any cookie, authorization URL, or confirmation code — linking is unavailable rather than silently falling back to a store one replica cannot share with the others. A single-instance deployment (no `CROWI_MULTI_INSTANCE` declared) falls back to an in-process store, so a link attempt does not survive an API process restart in between. In Redis mode, every deadline above (link-start state, confirmation code, consumed retention) is measured against Redis's own clock (`TIME`), never the API process's local clock — so a replica with a skewed system clock can neither shorten nor extend any of these windows.

The confirmation code briefly appears in the URL (`?provider=...&link_completion=...`) on the way back from the provider, so it can be visible in browser history, a `Referer` header, or a reverse proxy's access log for that one request. On its own it cannot attach anything: consuming it still requires an authenticated session belonging to the same user who started the flow, and the settings screen strips it from the URL immediately after reading it.

**Immediately before inserting the identity**, Crowi re-reads the account fresh and confirms it is still active and that nothing changed its session generation (a password reset or a forced sign-out) since the link was started; either failure ends the flow without linking anything, and the confirmation code cannot be reused afterward. There is no compensating rollback past that point — a fresh-read-then-insert is a single database round trip, and the brief window it spans is treated the same as any other legitimate ordering of two operations that could have completed in either sequence.

Unlinking requires that the account **can sign in with a password**. It is refused when either of these holds:

- The user has no password set
- Password sign-in is disabled instance-wide

The password is the only thing the guard looks at — **another linked provider does not satisfy it**. A user with both Google and GitHub linked but no password cannot unlink either one. Counting identities instead would be racy: two concurrent unlinks would each see the other's identity still present, both proceed, and leave an account with no way to sign in at all.

### What an administrator sees

The admin user list marks a linked account with an icon on its row, and the row menu lets an **administrator unlink** a provider. The condition **differs from a user unlinking their own**: a self-service unlink is refused without a password, whereas an admin unlink **issues one first** when the target has none, showing the generated password once. Recovering a compromised provider account is the point of an admin unlink. An existing password is left untouched — unlinking is not itself a reason to invalidate a password the user already knows.

Only two cases are refused, both with `409`: **unlinking your own identity**, and **an instance with password sign-in disabled**.

**The email address on a linked account cannot be changed by an administrator either.** A different address is refused with `409 EMAIL_LOCKED_BY_FEDERATED_IDENTITY`. A linked account can sign in from outside crowi, so swapping the address would redirect the confirmation link — the account's recovery channel — away from its owner. The same lock applies in the user's own settings, for the same reason (see [User pages and profile](../guide/profile)).

## Troubleshooting

**No button on the sign-in screen**
Check that `AUTH_PUBLIC_WEB_URL` (or `CLIENT_URL`) is set, and that **both** the Client ID and the secret have been saved. The provider is omitted from the list if either is missing.

**Google reports `redirect_uri_mismatch`**
Check that the redirect URI registered in the Google Cloud Console matches the one built from `AUTH_PUBLIC_API_URL` exactly. Behind a reverse proxy, `AUTH_PUBLIC_API_URL` must be set to the **origin outside the proxy**.

**"That email address is already registered"**
A local account with that address already exists. Sign in with the password and link the Google account from the settings screen.
