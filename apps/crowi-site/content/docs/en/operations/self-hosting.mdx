This page is for operators who need to **self-host with their own runner project**
because the official full / slim images don't cover their requirements. Typical
cases:

- You want to load **custom plugins** that aren't bundled in the official images
  (e.g. packages from a private npm registry).
- You want to pin a **specific combination** of storage / search / mail / renderer
  drivers.
- You want to keep the image's dependencies minimal and own the build pipeline
  in-house.

If the official images (built from the monorepo's bundled `apps/crowi-runner` /
`apps/crowi-runner-slim`) are enough, the "Building the official Docker images"
section of [Installation](./installation) covers that. This page goes one step
further: **building a runner project from scratch**.

<Callout type="info">
  A Crowi production deployment is "**api (Hono) + web (Next.js) + MongoDB
  (optionally Redis / Elasticsearch / S3)**". `@crowi/api` **bundles no plugins**,
  so the runner project owns which drivers are used. This premise is detailed in
  "How plugins are resolved" in [Configuration](./configuration).
</Callout>

## The big picture

With the recommended single-domain + reverse-proxy setup, requests are routed
like this:

```
                         ┌──────────────────────────────┐
  browser ──HTTPS──▶ reverse proxy (nginx / Caddy / ...)
                         │  /            → web  :3000     │
                         │  /api/*       → api  :3000     │
                         │  /collab/*    → api  :3000 (WS) │
                         └──────────────────────────────┘
                                   │            │
                              ┌────▼───┐   ┌────▼───┐
                              │  web   │   │  api   │──▶ MongoDB / Redis / ...
                              └────────┘   └────────┘
```

`web` and `api` are separate containers, both listening on container port `3000`.
`/collab/*` is a WebSocket endpoint, so enable **Upgrade-header passthrough** on
the proxy.

## Build the runner project

<Steps>

<Step>

### Project directory and `package.json`

Create a directory anywhere and declare `@crowi/api` plus the **plugins you want**
as dependencies. The example below uses S3 storage + Elasticsearch search +
PlantUML/KaTeX renderers.

```json title="package.json"
{
  "name": "my-crowi-runner",
  "private": true,
  "type": "module",
  "scripts": {
    "start": "crowi-api"
  },
  "dependencies": {
    "@crowi/api": "2.0.0-alpha.0",
    "@crowi/plugin-storage-aws-s3": "2.0.0-alpha.0",
    "@crowi/plugin-search-elasticsearch": "2.0.0-alpha.0",
    "@crowi/plugin-renderer-plantuml": "2.0.0-alpha.0",
    "@crowi/plugin-renderer-katex": "2.0.0-alpha.0"
  }
}
```

<Callout type="warn">
  Pin the versions to **the Crowi release you actually run**. Keeping `@crowi/api`
  and every `@crowi/plugin-*` on the same version is the safe choice (releases bump
  together as a linked group).
</Callout>

The implicit default plugins (`@crowi/plugin-storage-local` /
`@crowi/plugin-search-mongo` / `@crowi/plugin-mail-smtp`) load without being
declared. If local storage + MongoDB search + SMTP is fine, depending on just
`@crowi/api` works (i.e. you assemble a slim-equivalent yourself).

</Step>

<Step>

### `crowi.config.json`

Declare which plugins to load and which drivers are active. Per-plugin settings
(bucket names, credentials, etc.) are **not** written here — configure them from
the admin UI (`/admin/plugins`) after boot.

```json title="crowi.config.json"
{
  "plugins": [
    "@crowi/plugin-storage-aws-s3",
    "@crowi/plugin-search-elasticsearch",
    "@crowi/plugin-renderer-plantuml",
    "@crowi/plugin-renderer-katex"
  ],
  "storage": { "driver": "s3" },
  "search": { "driver": "elasticsearch" }
}
```

See [Configuration](./configuration) for the field meanings and driver-name
mapping.

</Step>

<Step>

### `.env`

Provide the environment variables the api reads at boot. At minimum set
`MONGO_URI`; in production always set `CROWI_ENCRYPTION_KEY` and
`WS_TOKEN_SECRET`.

```bash title=".env"
MONGO_URI=mongodb://mongodb:27017/crowi
REDIS_URL=redis://redis:6379          # required for multi-replica deployments
CROWI_ENCRYPTION_KEY=...               # openssl rand -base64 32
WS_TOKEN_SECRET=...                    # identical across all api replicas
```

See "Environment variables" in [Configuration](./configuration) for what each
one does.

<Callout type="warn">
  Leaving `WS_TOKEN_SECRET` unset generates a random secret per process. That is
  acceptable for single-instance testing, but with **multiple replicas it must be
  the same value on every replica** — otherwise realtime-collab WebSocket auth
  fails on one side.
</Callout>

</Step>

<Step>

### Verify locally

Install dependencies and start with the **project directory as cwd** (`process.cwd()`
must be the `projectDir`).

```bash
pnpm install   # or npm install
pnpm start     # = crowi-api; the api listens on container port 3000
```

At boot the api resolves plugins from this project's `node_modules/`. Adding or
removing plugins **does not require rebuilding the api**.

</Step>

</Steps>

## Build the api Docker image

Containerize the runner project as-is. Like the official image, set `WORKDIR` to
the runner project root (= `projectDir`) and run `node_modules/@crowi/api/dist/app.js`.

```dockerfile title="Dockerfile"
FROM node:24-bookworm-slim
WORKDIR /app

# Copy manifests first so dependency resolution caches well
COPY package.json pnpm-lock.yaml* package-lock.json* ./
RUN corepack enable && pnpm install --prod || npm install --omit=dev

# Place config and sources
COPY crowi.config.json ./
# Do NOT bake .env into the image — pass it via container env / env_file

ENV NODE_ENV=production
ENV PORT=3000
EXPOSE 3000
CMD ["node", "node_modules/@crowi/api/dist/app.js"]
```

<Callout type="info">
  For plugins from a private registry, COPY an `.npmrc` to configure the registry
  / auth before `pnpm install`. Mounting `crowi.config.json` from outside the
  container lets you swap driver choices without rebuilding (the official compose
  setup does this too).
</Callout>

Keep secrets (`CROWI_ENCRYPTION_KEY` / `WS_TOKEN_SECRET`, etc.) **out of the
image** — pass them via container env or `env_file` at deploy time.

## Wire up the web frontend

The web app builds from `packages/web/Dockerfile`. The built `crowi/crowi-web`
image is a **render-only** Next.js server that bakes **no** absolute API URL:
the browser hits relative `/api` / `/files` paths on its own origin and
derives WebSocket URLs from `window.location`. So one image works against any
api host — but it needs a **front reverse proxy** to route those paths to the
api.

<Callout type="warn">
  Do **not** expose the web server directly and rely on it to proxy `/api`. With
  `output: 'standalone'` the Next `rewrites()` proxy target is **baked at build**
  (not read from `CROWI_API_URL` at runtime), so a directly-exposed web server
  proxies to its build-time default and cannot reach your api. Put a reverse
  proxy in front instead.
</Callout>

The recommended topology is **single-origin + a reverse proxy** in front of both
web and api. The full wiring (a minimal Caddy / nginx config routing `/api`,
`/files`, and the realtime `/collab`, `/presence`, `/notifications` WebSocket
upgrades), plus the cross-origin and Vercel / PaaS variants, are in
[Deployment topologies](./deployment). Read that page before going to
production.

## Boot order and health checks

<Steps>

<Step>
### Start middleware first
Bring up MongoDB (and Redis / Elasticsearch if used) and make them reachable.
</Step>

<Step>
### Apply migrations
If you have a v1 upgrade or preflight migrations, apply them before starting the
api. See [Upgrading from v1](./upgrading-from-v1).
</Step>

<Step>
### Start api, then web
Start the api and confirm `/api/app/info` returns 200, then start the web app.
</Step>

</Steps>

<Callout type="info">
  For multi-replica deployments, `REDIS_URL` (collab/presence/notifications
  pub/sub, editor-cap counter, Config sync, rate limiting, LRU) is
  **required**, and `WS_TOKEN_SECRET` must be identical across all api replicas.
  See [Realtime collaboration](./realtime-collab).
</Callout>

## `/api` prefix cutover

Starting from the release that removes the `v2` path segment, the api's
public HTTP prefix is `/api` instead of `/api/v2`. This is a listener-
boundary rename, not a versioned rollout: the api does **not** serve a
runtime alias or redirect for the old prefix. Once a given api replica is
running the new version, every request to `/api/v2/*` against that replica
is a plain 404 — and symmetrically, a replica still running the previous
version does not understand unprefixed `/api/*` requests from an
already-upgraded web / CLI / MCP client. The two listener generations
cannot interpret each other's prefix, so this upgrade cannot be rolled out
gradually.

### Coordinated drain/restart — no one-at-a-time rolling restart

<Callout type="warn">
  **Do not roll this release out one replica at a time.** A normal rolling
  restart — replacing api replicas one by one behind a load balancer with no
  sticky sessions (see [Realtime collaboration](./realtime-collab)) — puts
  old-prefix and new-prefix replicas in the same pool at the same time.
  Whichever prefix a given request happens to use, roughly half the fleet
  will 404 it. Instead, stop **every** api replica together, deploy the new
  version to all of them, and restart them together — or stand up a fresh
  fleet on the new version and cut traffic over to it all at once
  (blue/green). Single-instance deployments, including local dev, are not
  affected: with only one replica, old-prefix / new-prefix mixing cannot
  happen.
</Callout>

### Preflight check

Before opening the gate to real traffic, confirm every replica has actually
switched — don't rely on the deploy tool's "finished" signal alone. Hit each
replica **individually** (not through the load balancer, which would only
ever sample one replica per request):

- `GET /api/openapi.json` must return **200** on every replica.
- `GET /api/v2/openapi.json` must return **404** on every replica.

If any replica fails either check, it is still on the old prefix (or was
never restarted) — do not route production traffic to the fleet yet.

### Rollback

Rolling back runs the same check in reverse. Before sending traffic back to
a rolled-back replica, confirm it returns **404** for `/api/openapi.json`
and **200** for `/api/v2/openapi.json`. As with the upgrade direction, roll
back every replica together — a fleet with a mix of rolled-back and
not-yet-rolled-back replicas has the same split-prefix problem as a partial
upgrade.
