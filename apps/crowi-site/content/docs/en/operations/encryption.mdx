title: Encrypting sensitive settings
description: Encrypting sensitive config with CROWI_ENCRYPTION_KEY
---

Crowi can **encrypt sensitive configuration values at rest** — OAuth
secrets, AWS credentials, SMTP passwords, Slack tokens, and the like. To
enable encryption, set the master key `CROWI_ENCRYPTION_KEY`.

> **Important**: `CROWI_ENCRYPTION_KEY` is optional, but **strongly
> recommended for production**. The app works without it, but sensitive
> values are stored in plaintext in MongoDB (the legacy mode described
> below).

## What gets encrypted

Only the keys in the MongoDB `Config` collection that are registered as
sensitive are encrypted.

**1. Plugin sensitive fields (the primary target)**

Third-party credentials for storage, mail, search, etc. live in their
**plugin's config namespace** (`crowi:plugin:<plugin name>:<field>`). Fields a
plugin marks with `@sensitive` are automatically registered into the sensitive
list at boot and follow the encryption path. For example:

| Namespace:key | Description |
| ------------- | ----------- |
| `crowi:plugin:@crowi/plugin-aws:secretAccessKey` | AWS credentials (S3 storage / SES mail) |
| `crowi:plugin:@crowi/plugin-mail-smtp:password` | SMTP password |
| `crowi:plugin:@crowi/plugin-mail-resend:apiKey` | Resend API key |

**2. Sensitive keys that remain in core config**

| Namespace:key | Description |
| ------------- | ----------- |
| `notification:slack:clientSecret` / `token` | Legacy Slack integration secret / token |

Credentials for external sign-in (Google and friends), storage and mail live
in **their own plugin's namespace** (`crowi:plugin:<plugin>:<field>`) rather
than in core config, and are encrypted the same way. For what changes when
migrating from v1, see [Migrating from v1](./upgrading-from-v1).

> **Note**: User passwords are separately hashed with
> bcrypt and are not part of this encryption. Personal access tokens use a
> different mechanism, since they need equality lookups.

## Generating the master key

`CROWI_ENCRYPTION_KEY` must be a **base64-encoded 32-byte value** (which
decodes to exactly 32 bytes = the AES-256 key length). Generate it with
it.

```bash
openssl rand -base64 32
```

Set the generated value in `.env`.

```bash
CROWI_ENCRYPTION_KEY="the generated base64 string"
```

Restart the API after setting it to enable encryption of sensitive
values.

## How encryption works

Encryption uses AES-256-GCM, and an encrypted value carries an `enc:v1:`
prefix. Looking at the database, that prefix is how you tell an encrypted
value from a plaintext one.

Sensitive keys are encrypted when saved and decrypted when loaded. There is
nothing for an operator to run.

## Legacy mode (when the key is unset)

When `CROWI_ENCRYPTION_KEY` is unset, or does not decode to 32 bytes,
Crowi runs in **legacy mode**.

- Sensitive values are stored in MongoDB **as plaintext**.
- A warning is logged at boot.
- Encryption is treated as best-effort, so the app never crashes just
  because the key is missing.

Also, even after you enable encryption, plaintext rows that are not yet
encrypted (= without the `enc:v1:` prefix) can still be read. `decrypt`
passes prefix-less values through untouched, so a mix of legacy and
encrypted data still works.

## Re-encrypting existing plaintext data

If you enable encryption later on, sensitive values saved before that
remain in plaintext. To encrypt them all at once, use the encryption
settings screen in the admin UI (`/admin/crypto`).

### Checking the status

Opening `/admin/crypto` shows whether a master key is configured, how many
sensitive values are encrypted, how many are still plaintext, and which key
is in which state.

### Running re-encryption

Running re-encryption from that screen encrypts the values still stored in
plaintext.

- With no master key configured it fails; set `CROWI_ENCRYPTION_KEY` first.
- Already-encrypted values are skipped, so running it repeatedly is safe.
- Afterwards it reports how many values were rewritten, how many were already
  encrypted, and how many did not exist.

> **Tip**: Re-encryption is safe to run any number of times
> (idempotent). Run it whenever you need to — for example after
> entering new OAuth settings in plaintext.

## About key rotation

The current implementation assumes a single fixed
`CROWI_ENCRYPTION_KEY`. If you change the key to a different value,
values encrypted before that can no longer be decrypted (GCM
authentication-tag verification fails). If you need to change the key,
prepare to re-enter the affected sensitive settings from the admin UI
before the change.
