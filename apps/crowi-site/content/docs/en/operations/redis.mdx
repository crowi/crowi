Crowi uses Redis to coordinate between replicas. It is optional on a single replica and **required with several**. Which features use it, and how each degrades without it, is in [Operating realtime collaboration](./realtime-collab).

Crowi does not bundle a Redis server; it connects over the network to one you provide. If you choose a managed service (ElastiCache, MemoryDB, Upstash and so on), selecting it and complying with its terms is your organisation's responsibility.

## Supported versions

- The tested range is **`>=8.0 <9`**. That is a policy, not a runtime check — Crowi does not refuse to connect to a Redis 7 server.
- **Pin the version.** A moving tag such as `redis:8` or `redis:latest` crosses versions whenever upstream decides. Crowi's own compose file and CI pin a single patch tag by digest.
- **Valkey is not officially supported.** It is protocol-compatible and very likely works, but Crowi's compatibility tests do not run against Valkey in CI, so it is best-effort. It becomes supported once that same test suite passes against it continuously.
- **Snapshots are not portable across engines.** Do not assume a Redis-written RDB can be read by Valkey, or the reverse.

## Estimating connections

The connection count per api instance depends on what that instance has done.

- **Just after boot**, with no collaborative session started yet: **5** — one shared client (editor cap, recently viewed, rate limiting, presence writes and notification publishes all ride it), one presence subscriber, one notification subscriber, and two for config sync.
- **After the first collaborative session on that instance**: **7** — the five above plus a dedicated pub and sub connection for collaboration, which are not opened until the first document loads.

Ten api replicas therefore mean 50 connections after boot and 70 once collaboration has started everywhere. The web app opens no Redis connections of its own (everything goes through the api). That fits comfortably inside the default `maxclients=10000`, but check the headroom on small managed instances (`cache.t3.micro` and similar).

## Replacing the endpoint

<Callout type="warn">
  **Never run replicas pointed at different Redis servers at the same time (split-brain).** Redis pub/sub offers no distributed locking, so this does not fail loudly: the fan-out between replicas — collaboration, presence, notifications, config sync — quietly splits into two disconnected groups.
</Callout>

The standard procedure is to stop every replica together, switch `REDIS_URL` to the new endpoint, and start them together again (the full procedure is in [Upgrading](./upgrade)). Only use a vendor's online promotion (managed replica promotion, blue-green switching) when you have confirmed your Redis distribution really supports a topology change that way — Crowi's own tooling does not verify it.

**Clear the stale coordination state on the old instance before switching.** If editor-cap keys and presence hashes survive and every replica reconnects, stale socket ids mix with new connections: the editor cap counts higher than reality and pushes editors into read-only, and presence shows ghost viewers.

1. Confirm every replica has drained from the old endpoint (existing WebSockets closed, no new connections pointing at it).
2. Make the target either a freshly created empty instance, or one whose `crowi:<instance-slug>:` keys you cleared.
3. After switching, check that the editor count and the presence list match the real connections before returning production traffic.

Page content never lives in Redis, so a cold start loses no pages. What is lost is the recently-viewed list and any account-link confirmation still in flight — both of which a user can simply redo.

## Security

- **Transport and credentials**: keep TLS (`rediss://`) and certificate verification at their defaults. Disable verification only in a controlled development environment or a private-CA scenario. Keep credentials in environment variables or a secret manager, never in settings screens or logs.
- **Network**: make Redis reachable only from Crowi and your internal infrastructure; never expose it unauthenticated to a public network.
- **Key separation**: every key and channel is created under a per-instance namespace `crowi:<slug>:…` (defaulting to the hostname in `CLIENT_URL`, overridable with `REDIS_KEY_PREFIX` — see [Configuration](./configuration)). Every replica of one instance must resolve to the same value, and a different instance sharing that Redis must use a different one. **The database number in the URL (`/1`) is not a substitute**: pub/sub is not scoped to a database, so two instances differing only by database number still cross-talk on every channel.
- **Failure semantics**: the editor cap and rate limiting are not authorization boundaries and fail open when Redis is unreachable. JWT and WebSocket-token authentication do not depend on Redis, so a Redis outage never bypasses authentication.

### Permissions a restricted ACL needs

When you create a restricted ACL user, all of the following must be allowed. Without them, saves in collaborative editing start failing with permission errors rather than degrading cleanly. Every key and channel sits under `crowi:<slug>:`, so grant against the slug that actually resolves.

| Purpose | Commands | Keys / channels |
| --- | --- | --- |
| Collaboration fan-out | `SUBSCRIBE`, `UNSUBSCRIBE`, `PUBLISH` | `crowi:<slug>:collab:<documentName>` — one channel per document |
| Editor cap counter | `SADD`, `SCARD`, `SREM`, `EXPIRE` | `crowi:<slug>:collab:editors:<pageId>` |
| Presence | `HSET`, `HGET`, `HGETALL`, `HDEL`, `EXPIRE`, `PUBLISH`, `SUBSCRIBE` | `crowi:<slug>:presence:viewers:<pageId>`, `crowi:<slug>:presence:editing:<pageId>`, `crowi:<slug>:presence:feed` |
| Notifications | `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE` | `crowi:<slug>:notifications:user:<userId>` |
| Config sync | `PUBLISH`, `SUBSCRIBE` | `crowi:<slug>:config` |
| Rate limiting | `INCR`, `PEXPIRE` | `crowi:<slug>:ratelimit:<name>:<userId>:<window>` |
| Recently viewed pages | `ZREMRANGEBYRANK`, `ZADD`, `ZRANGE`, `MULTI`, `EXEC` | `crowi:<slug>:lru:<namespace>` |
| Account linking | `GET`, `SET`, `EVAL`, `TIME` | `crowi:<slug>:link-completion-*:<hash>` — `<hash>` is a hash; no plaintext appears |
| Boot connection | Connection establishment only | None |

Two sources of commands are easy to miss.

- **What the client libraries send on connect**: a `CLIENT SETINFO` per connection and an `INFO` ready check. Denying them does not necessarily break the connection outright, but allow them explicitly.
- **The lock behind collaborative saves**: every save takes a cross-instance lock through a Lua script. Redis applies ACL checks to commands called *inside* a script too, so besides `EVAL` / `EVALSHA` the user needs `SELECT`, `EXISTS`, `SET`, `GET` and `DEL` on `crowi:<slug>:collab:<documentName>:lock`. **An ACL missing those makes every collaborative save fail in production wherever Redis is enabled** — edits stay in memory, never persist, and the error log fills up until the ACL is fixed.

<Callout type="info">
  ACLs are scoped to a **user**, not to a listener, so "restrict only the TLS port" is not a workable design: disable or password-protect the `default` user on every listener and make Crowi use scoped credentials. The table above was derived by reading the source, not verified by an automated permission-denial test, so re-check it after upgrading the client libraries.
</Callout>
