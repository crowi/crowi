The Crowi admin panel is where you manage site-wide settings, users, and
plugin configuration from the web UI. Open `/admin` to see the dashboard,
and use the left sidebar to move between sections.

## Accessing the admin panel

- The admin panel is accessible **only to users with `user.admin === true`**.
  A user without permission who opens anything under `/admin` sees an
  "Access denied" card.
- Authorization is also enforced on the API side. Admin endpoints are
  mounted under the `jwtAdminRequired` middleware (= JWT auth +
  `user.admin === true`), so requests that bypass the UI are still
  rejected with 401 / 403.
- The first administrator is granted automatically to the first user
  created during installation. Subsequent admin grants are done from the
  [Users](#users) section.

> **Tip**: Admin privileges are powerful. Log in as a regular user for
> everyday editing, and use an admin account only when you need to change
> settings.

## Dashboard

The `/admin` landing page shows cards for each section. The sidebar
headings are grouped as follows.

| Group | Sections | Status |
| ----- | -------- | ------ |
| Settings | App / Security / Authentication / Plugins | Available |
| User management | Users (+ "User approval" when sign-ups are pending) | Available |
| Shared services | (config-only base plugins, e.g. AWS) | Plugin-dependent |
| Storage | Storage (+ storage plugins) | Available |
| Mail | Mail | Available |
| Notification | Notification | In progress |
| Search | Search (search index + search-backend plugins) | Available |
| Renderers | (renderer plugins, e.g. PlantUML) | Plugin-dependent |

Loaded plugins are injected into the sidebar as links to their settings
pages. The target group comes from the plugin's **`adminPlacement.section`**
declaration, or is derived from the **extension hook** it registers:

| Hook / declaration | Group |
| ------------------ | ----- |
| `registerStorage` | Storage |
| `registerSearch` | Search |
| `registerRenderer` | Renderers |
| `registerMailSender` | Mail |
| `registerNotifier` / `registerAuth` | Settings (the fallback below) |
| config-only (no hook) | Settings, or Shared services when it declares `section: 'shared'` |

`adminPlacement.section` also accepts `notification` and `auth`, but the
sidebar **has no heading for either**. An entry that names a section with no
heading — or derives one from `registerNotifier` / `registerAuth` — **falls
back to the Settings group** rather than being dropped. Auth-provider plugins
take this path by default, since their section is derived from
`registerAuth`. The fallback is what keeps a plugin's config page from
becoming reachable only by typing its URL when it names a section the
sidebar does not render.

For example, the Elasticsearch search plugin appears under "Search" and the
PlantUML renderer plugin under "Renderers" (only plugins that declare a config
schema are shown).

> **Note**: As of a point in the v2 alpha, **Authentication moved into the
> Settings group** (directly under Security). The former standalone "Auth" and
> "Maintenance" groups were removed; Search now has its own "Search" group and
> renderers a "Renderers" group. Backlink rebuilding moved from the admin panel
> to the `crowi-admin` CLI, so the Backlink sidebar entry was removed.

## App

Basic site settings. Maps to `GET/PUT /admin/app`.

- Configure app-wide items such as the **site title**.
- Keys that contain sensitive values are masked on input; saving while
  left blank keeps the existing value (this prevents accidentally
  overwriting it with an empty string).

> **Note**: In older versions, App settings included AWS S3 upload
> credentials. In v2 those have moved to the [Storage](#storage) section
> and the storage plugin settings.

## Security

New-user registration settings. Maps to `GET/PUT /admin/security`.

- **Registration mode (registrationMode)**: Controls how new users register.
  - `Open` — anyone can register; usable right after email confirmation.
  - `Restricted` — anyone can apply, but an **administrator must approve** the
    account before it can be used (applicants are created in a pending state
    and appear in the "User approval" queue under [Users](#users)).
  - `Closed` — public sign-up is disabled; accounts are created **only by
    admin invitation**. In this mode the `/register` page shows an
    invite-only notice instead of the form, and the "Sign up" link on the
    login page is hidden as well (the entry points are closed before
    submission).
- **Registration whitelist (registrationWhiteList)**: The list of email
  addresses / domains allowed to register. It is **evaluated in every mode
  except `Closed`**; an empty list means no restriction. One entry per line,
  matched case-insensitively as:
  - `admin@example.com` — that exact full address only
  - `@example.com` — any local-part at that domain
  - `example.com` — that domain or any subdomain of it

> **Note**: The legacy **site-wide HTTP Basic auth**
> (`security:basicName` / `security:basicSecret`) was **removed** in v2
> (breaking change). It could not reliably gate a single-page app in the
> Next.js + Hono architecture and was never actually enforced. If you need a
> site-wide Basic-auth gate, configure it at your **reverse proxy** (e.g.
> nginx). Any leftover config rows in the DB are simply ignored.

## Authentication

Settings related to the authentication method. Maps to
`GET/PUT /admin/auth`.

**As of 2.0.0-alpha this screen is an explanatory, read-only notice.**
Third-party (Google / GitHub) sign-in was removed from core, and the two
settings that depend on it cannot be edited.

- **requireThirdPartyAuth** (make third-party auth mandatory) and
  **disablePasswordAuth** (disable password login) would leave every
  account with no way to sign in, so **the toggles are not rendered** and
  the API rejects any request that tries to enable them with
  `400 THIRD_PARTY_AUTH_UNAVAILABLE`.
- The config keys and schema are kept, inert, for a future auth-provider
  plugin. If a previously-enabled value is still in the database, the
  screen shows a warning.

> **Note**: The fields for entering Google / GitHub clientId and client
> secret are gone from this screen too. **Google sign-in has already
> returned as the auth-provider plugin `@crowi/plugin-google`** — it is
> configured under plugin settings (`/admin/plugins`) rather than here.
> See [Signing in with an external account](./federated-auth) for the
> setup. The `requireThirdPartyAuth` / `disablePasswordAuth` settings on
> this screen stay uneditable: they have not yet been reworked around
> plugin-provided auth.

## Mail

Mail delivery settings. Maps to `GET/PUT /admin/mail` and
`POST /admin/mail/test`.

- The only field editable on this screen is the **sender address
  (`from`)**.
- The name of the currently active mail driver is shown read-only,
  together with a link to the plugin settings screen where its connection
  details are edited. The SMTP host / auth, the Resend API key and the AWS
  credentials for SES live under `/admin/plugins`.
- The **test send** button sends a test mail to the logged-in admin's
  registered email address so you can verify the configuration (it uses
  the saved settings).

See [Mail settings](./mail) for details.

## Users

List, search, and manage users. Maps to the `GET /admin/users` family of
endpoints.

| Operation | Description |
| --------- | ----------- |
| List / search | Filter by email or username, browse with pagination |
| Invite | Enter multiple email addresses and invite users in bulk |
| Edit profile | Change a user's display name and email address |
| Admin permission | Grant or revoke admin permission |
| Status change | Activate (ACTIVE) or suspend (SUSPENDED) a user |
| Reset password | Reissue a random password (the plaintext is returned once) |
| Resend invite | Resend the invitation email to an **INVITED** user (a fresh invite token is issued) |
| Delete | Physically remove an **INVITED** user (users who have ever activated cannot be deleted) |
| View / unlink a federated identity | A row shows an icon when the account is linked to an external provider, and the row menu can unlink it. If the target has no password, unlinking issues one and shows it once. Only two cases are refused: **unlinking your own identity**, and **an instance with password sign-in disabled** |

### Username format

A username chosen during invite acceptance may contain only ASCII letters,
digits, `_`, and `-`, and must be 1–64 characters long. The same rule
applies to self-registration and to installer admin creation; values that
do not match are rejected with `400` before the account is created.

This matches the character set `@mentions` recognises and keeps the
`/user/<username>` page namespace intact. Usernames already stored are
left unchanged — the rule applies to new and changed usernames only.

For an invited user's row, a **"Resend invite"** button is shown directly in
the row, with a row menu next to it limited to "Change email" and "Delete"
(since the account has not activated yet, edit / permission / status actions
are hidden).

Clicking "Resend invite" issues a new invite token and resends the invitation
email. The invite token is valid for **7 days**. There is no need to explicitly
invalidate the old token — the status check on acceptance prevents a double
acceptance. Note that sending email requires mail (e.g. SMTP) to be configured,
so **a resend is not possible when mail delivery is unconfigured** (a send
failure surfaces an inline error).

> **Tip**: The plaintext password returned by a password reset is shown
> only at that moment. After a reset, deliver it to the user promptly over
> a secure channel and have them change it themselves after their first
> login.

> **Note**: An admin-initiated password reset **signs that account out of
> every existing login session**, so when you suspect an account has been
> taken over the reset is itself what evicts the intruder. It also kills
> everything still in flight for the account: password-reset links already
> mailed to the user, and an email-address change they requested but have
> not confirmed yet (they can simply request it again after signing in with
> the new password). **Personal access tokens and OAuth-connected apps are
> not affected** — they are separate credentials, revoked by their owner
> from their own settings screen (see
> [User pages and profile](../guide/profile)). If you need those cut off
> too, set the account's status to **SUSPENDED**: a suspended user's
> requests are refused whatever credential they present.

### User approval

When one or more **pending (REGISTERED) users** created by `Restricted` mode
exist, a **"User approval"** entry appears directly under "User management" in
the sidebar, with a **count badge** so admins notice pending sign-ups. Opening
`/admin/users/pending` lists the pending users; the "Approve" button on each
row activates (sets ACTIVE) that user. The badge refreshes on an interval.

## Storage

A read-only page that shows the status of the attachment storage
(storage driver). Maps to `GET /admin/storage`.

- Shows the currently active driver and the list of all loaded drivers.
- **Driver switching is not done from the admin panel.** Edit
  `storage.driver` in `crowi.config.json` and restart the api.
- File migration between drivers is done with the
  `crowi-admin rebuild storage copy --from <a> --to <b>` CLI.

For storage configuration and plugins in general, see
[Storage settings](./storage).

## Plugins

Lists loaded plugins and lets you edit each plugin's configuration.

- `/admin/plugins` lists the loaded plugins.
- `/admin/plugins/edit?name=<plugin-name>` edits an individual plugin's
  configuration. The form is auto-generated from the plugin's Zod schema;
  for sensitive fields only "whether a value is set" round-trips — the
  plaintext is never shown.
- Field labels and descriptions are **localized** to the admin UI language
  when the plugin ships a `configI18n` catalog (missing locales or fields fall
  back to the Zod `.describe()` default text).
- Clearing the render cache per-plugin or globally is also done here.

### Connection check after saving

Saving a plugin's configuration **also tries the saved values against the real
backend, for plugins that support it**, and shows the outcome. Today that is
`@crowi/plugin-storage-local` and `@crowi/plugin-storage-aws-s3` (a write, read and
delete round trip) and `@crowi/plugin-search-elasticsearch` (a cluster-info call
only).

**The check runs after the save and never rolls it back.** A failure still leaves
the value saved and reports "saved, but verification failed". The reason is reduced
to one of five — unreachable, authentication failed, resource missing, write denied,
unknown — and the backend's own message is never shown.

Two operational caveats:

- **The result is the result on whichever instance answered the request.** Nothing
  is aggregated across instances, so a configuration that one instance can reach and
  another cannot is indistinguishable here.
- The storage round trip fires its cleanup delete on an independent budget, but
  **a failed delete does not overturn the verdict**. Credentials that allow writes
  but deny `DeleteObject` still report success, leaving one probe object behind per
  save.

The form stays uneditable while a check is in flight, so a value you never submitted
cannot end up treated as saved.

### Confirming a credential change on an auth plugin

Changing the OAuth client credentials of an **auth plugin** such as
`@crowi/plugin-google` raises a confirmation dialog **when users are already linked
through that provider**. The dialog names how many people are linked and warns that
the change may stop them signing in. Confirming saves; cancelling saves nothing and
leaves your input in the form.

Confirmation is triggered when the credentials are declared as an **atomic group** —
a set of fields that only mean anything together, such as a client ID and its
secret — and you change any member of it. Changing only `clientId` without sending
`clientSecret` therefore still asks, because the stored secret would be paired with
a client it was never issued for. Saves that touch only fields outside an atomic
group, and saves to plugins that register no auth driver (storage, search, and so
on), are unaffected.

Against the API directly, `PUT /admin/plugins/config` answers with
`409 LINKED_IDENTITIES_EXIST` and the linked count. Resending the same request with
`confirmLinkedIdentities: true` saves it. That flag is never persisted into the
plugin's stored configuration.

For installing and managing plugins see [Managing plugins](../plugins/managing),
and for how plugins work see [Plugin overview](../plugins/overview).

## Search

A page to check the status of the search driver. Maps to `GET /admin/search`.

- Shows the currently active search driver and the index status.
- Index rebuilds are not done from the admin panel — use the
  `crowi-admin rebuild search` CLI.
- Search-backend plugins such as Elasticsearch are auto-injected into **this
  "Search" group** (derived from `registerSearch`) as a settings-page link.

See [Setting up the search backend](./search-setup) for details.

> **Note**: The **Backlink** rebuild page that used to live under the
> "Maintenance" group was removed. Backlink rebuilding is now a
> `crowi-admin backlink rebuild`-style CLI operation.

## Rebuilding rendered ASTs (rebuild rendered-ast)

`crowi-admin rebuild rendered-ast` regenerates the pre-rendered AST stored on each page's **current revision** (`Revision.renderedAst`) with the running renderer pipeline ([RFC-0023](https://github.com/crowi/crowi/blob/main/docs/rfcs/0023-client-agnostic-rendered-ast.md)). It belongs to the same rebuild family as `rebuild search` / `rebuild storage copy` and is safe to run any number of times (idempotent).

```bash
# Pre-deployment verification (no writes) — only counts eligible revisions
crowi-admin rebuild rendered-ast --dry-run

# Real writes (run right after deploying a version bump)
crowi-admin rebuild rendered-ast

# Tune the worker pool (default 4)
crowi-admin rebuild rendered-ast --concurrency 8
```

**When to run it (rollout procedure)**: after deploying a release that bumps the renderer pipeline's version, **run it with real writes immediately**. The read path serves a stored AST verbatim only when its version is an **exact match** for the running pipeline, so this is not a major-bump-only procedure — minor and patch bumps invalidate stored ASTs just as thoroughly. From the bump onward, every read of a page whose stored AST predates the new version triggers a full re-render on the fly (and the result is never persisted) — this read amplification is an **intended interim cost** that only goes away once the backfill completes. Conversely, **avoid real-write runs before that deployment** — pre-deploy verification must stay `--dry-run` only (even before the bump, a real-write run would rewrite legacy revisions that carry no `rendererVersion`).

**Declaring completion**: the save path stamps each api replica's own binary version, so as long as even one old-version replica is still routable, new old-version revisions keep being minted after your backfill finished. Only declare the backfill complete once both of the following hold:

1. You have confirmed every api replica runs the new version (no old writers remain).
2. One final `rebuild rendered-ast` run reports 0 eligible revisions remaining.

The command is idempotent, so the final re-run only costs time proportional to the residual count.

## Repairing page history (page-history repair)

`crowi-admin page-history repair` repairs the internal state behind page metadata history ([RFC-0021](https://github.com/crowi/crowi/blob/main/docs/rfcs/0021-page-metadata-change-history.md)).

- `--outbox` (default) — drains any unprocessed entry a crashed writer left behind in `Page.pendingHistoryEntry`.
- `--scan` — assigns `historySequence` to unsequenced revisions on pages that are ready to record history. Not run by default.
- `--batch-size <n>` (default 200) bounds how many pages are loaded per round trip; `--resume-after <pageId>` resumes a scan that was killed partway.

```bash
# Drain leftover outbox entries (the default)
crowi-admin page-history repair

# Only assign sequences to unsequenced revisions (skips the outbox pass)
crowi-admin page-history repair --scan

# Run both passes
crowi-admin page-history repair --outbox --scan
```

Passing `--scan` on its own **turns the default outbox pass off**. Say `--outbox --scan` when you want both.

**The first writer has landed (RFC-0021 Phase 2a).** Every content save — creating a page, creating a draft, an HTTP update or revert, a collaborative editor save, and `crowi-admin replace url` — now assigns its Revision a page-local `historySequence`, promoting that page's `historyTracking` to `ready` on its first tracked save.

Assignment runs as a **separate, resumable step after the pointer write has committed**, never as part of it, so a crash between the two cannot fail the save. This repair command is what recovers an assignment interrupted that way.

`--scan` **skips Revisions younger than ten minutes** (`RepairScanOptions.minAgeMs`'s default), so it cannot mistake an assignment still in flight for one that failed and run it twice. It also skips Revisions older than the page's tracking start, which would otherwise be given sequences out of order. Run it after that window if you want it to pick up recent writes.

The metadata commands — rename, grant, trash, restore, publish — still have no writer; those come in a later phase.
