---
title: Operating realtime collaborative editing
description: Operator guide for deploying Crowi 2.0's realtime collaborative editing (RFC-0003)
---

Crowi 2.0's realtime collaborative editing ships with Hocuspocus attached
as a library inside the `@crowi/api` process. There is no separate
collab process or extra port to manage; running the existing api
container is enough to enable realtime editing.

See [RFC-0003](https://github.com/crowi/crowi/blob/main/docs/rfcs/0003-realtime-collaborative-editing.md)
for the design rationale, and [Realtime collaborative editing](../guide/realtime-editing)
for the end-user guide.

## Overview

- Hocuspocus is attached to the api process's `http.Server` in
  `ws noServer` mode via `packages/api/src/collab/attach.ts`.
- The WebSocket endpoint is `wss://<crowi-host>/collab/:pageId?token=…`,
  served by the same host and port as the api. No reverse-proxy split
  to a separate process is required.
- For multi-instance deployments, `@hocuspocus/extension-redis` is
  attached automatically when `REDIS_URL` is set. Yjs updates are
  fanned out across replicas via Redis pub/sub, and sticky sessions
  are **not** required.
- The 20-editor per-page cap (default) is enforced via a Redis counter
  shared across instances.

## Single-instance deployment

The minimal stack is api + web + MongoDB.

```yaml
# docker-compose.yml (excerpt)
services:
  api:
    image: ghcr.io/crowi/api:2.0
    environment:
      MONGO_URI: mongodb://mongo:27017/crowi
      WS_TOKEN_SECRET: ${WS_TOKEN_SECRET}
      CROWI_ENCRYPTION_KEY: ${CROWI_ENCRYPTION_KEY}
      # REDIS_URL is optional in single-instance mode. See "Redis
      # connection budget" below for the 7 consumers it backs.
      REDIS_URL: redis://redis:6379
    ports:
      - "3000:3000"
  web:
    image: ghcr.io/crowi/web:2.0
    environment:
      NEXT_PUBLIC_API_URL: https://crowi.example.com
    ports:
      - "3001:3000"
  mongo:
    image: mongo:7
```

Notes:

- `REDIS_URL` may be omitted in single-instance mode, but the 7
  consumers don't all degrade the same way:
  - Collab pub/sub (`extension-redis` simply isn't attached), presence
    fan-out, notification invalidation, and Config sync exist purely
    to coordinate **across replicas** — a lone instance has no other
    replica to talk to, so these are effectively no-ops and nothing is
    lost.
  - The editor-cap counter **fails open**: without Redis it stops
    enforcing `COLLAB_MAX_EDITORS_PER_PAGE` instead of blocking the
    21st editor (see [Failure modes](#failure-modes)) — a deliberate
    degrade-safe choice, not a no-op.
  - Rate limiting falls back to an in-memory per-process window, so it
    keeps working single-instance, just without cross-replica sharing.
  - LRU (recently-viewed pages) has no fallback: without `REDIS_URL`
    this feature is unavailable outright, single-instance or not.
- The browser derives the `/collab/` WebSocket URL from
  `NEXT_PUBLIC_API_URL`, so `NEXT_PUBLIC_COLLAB_URL` is not required.
- `WS_TOKEN_SECRET` is optional in single-instance mode — leave it unset
  and the api generates a random per-process secret (a startup warning is
  logged). Set it (and `CROWI_MULTI_INSTANCE`) only when you scale past one
  api node.

## Multi-instance deployment

Additional requirements when running multiple api replicas:

1. **Point every replica at the same Redis via `REDIS_URL`** —
   extension-redis attaches automatically and fans Yjs updates out
   across replicas.
2. **Declare multi-instance with `CROWI_MULTI_INSTANCE` and set the same
   `WS_TOKEN_SECRET` on every replica** — a wsToken minted on one replica
   may be verified on another, so a mismatch leaves clients unable to
   connect (see [Environment variables](#environment-variables)). Set
   `CROWI_MULTI_INSTANCE=1` (or a replica count) on every replica; when it
   is set, booting **without** a stable `WS_TOKEN_SECRET` **aborts api
   boot** (a per-process random secret can't be cross-verified by other
   replicas). A single-instance deployment leaves `CROWI_MULTI_INSTANCE`
   unset and may run without `WS_TOKEN_SECRET` (a random per-process secret
   is generated, with a startup warning) — note that `REDIS_URL` presence
   alone does **not** require a secret, since Redis is also used by
   single-replica deployments.
3. **No sticky sessions** — clients can connect to any api replica.
   Yjs updates are routed via Redis pub/sub.
4. **`Page.yjsState` is the source of truth** — even a full cluster
   restart recovers from persisted state. Redis is for live routing
   only.

> **Important (data-loss risk — single-instance is recommended):**
> multi-instance deployments carry a known, rare risk of **lost edits**.
> `extension-redis` only handles live pub/sub; it does not rebuild a
> disconnected replica's Y.Doc. If a replica materialises a Y.Doc from a
> stale `Page.yjsState` and then writes a checkpoint (compaction), it can
> overwrite newer state written by another replica — compaction has **no
> cross-instance lock** (a cross-instance lock + last-writer arbitration
> is currently out of scope). `@crowi/collab` mitigates this with a
> **server-doc save lock**: the page's revision pointer is advanced in a
> single atomic compare-and-set anchored to the revision the live server
> document was materialised from, so a save against a pointer that an
> out-of-band edit (or another replica) has moved is rejected with
> `CONFLICT` and the client reloads — `revision` and `currentRevision`
> never diverge. Automatic checkpoints add a **desync guard**: a checkpoint
> that would write an empty document over a still-non-empty page (the
> tell-tale of a doc materialised from a failed load) is skipped, and a
> skipped checkpoint keeps the surviving state **and** its pending deltas
> so no edit is lost. A deliberate deletion — even clearing a page — from
> the editor is treated as explicit user intent and saved normally
> (deletions persist durably in `Page.yjsState`, not in short-lived rows).
> Together these mitigate the worst case on single and multi-instance
> alike, but **do not fully prevent it**. For this reason Crowi currently
> **recommends a single instance** (e.g. one Lightsail box). Adopt
> multi-instance only when you need to load-balance concurrent editing,
> with this risk understood.

```yaml
# 2-replica example
services:
  api:
    image: ghcr.io/crowi/api:2.0
    deploy:
      replicas: 2
    environment:
      MONGO_URI: mongodb://mongo:27017/crowi
      REDIS_URL: redis://redis:6379           # required in multi-instance
      WS_TOKEN_SECRET: ${WS_TOKEN_SECRET}     # identical across replicas
      CROWI_ENCRYPTION_KEY: ${CROWI_ENCRYPTION_KEY}
```

## Reverse proxy configuration

The `Upgrade` header must be forwarded all the way to the api.

### nginx

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

upstream crowi_api {
    server api1:3000;
    server api2:3000;
    # No sticky directive needed even in multi-instance setups.
}

server {
    listen 443 ssl http2;
    server_name crowi.example.com;

    # Send both /api/v2/* and /collab to the same upstream.
    location /api/v2/ {
        proxy_pass http://crowi_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # Prefix match WITHOUT a trailing slash so it also covers the bare
    # `/collab` upgrade. HocuspocusProvider dials `ws[s]://<host>/collab`
    # and sends the page id through the protocol after the handshake, so a
    # `location /collab/` (with trailing slash) block would never match the
    # bare upgrade. `location /collab` (no slash) covers both `/collab` and
    # `/collab/...`.
    location /collab {
        proxy_pass http://crowi_api;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;   # Keep long-lived sockets alive.
        proxy_send_timeout 3600s;
    }

    location / {
        proxy_pass http://crowi_web:3000;
    }
}
```

### Traefik

```yaml
# Labels on the api service in docker-compose.yml
labels:
  - "traefik.enable=true"
  - "traefik.http.routers.crowi-api.rule=Host(`crowi.example.com`) && (PathPrefix(`/api/v2`) || PathPrefix(`/collab`))"
  - "traefik.http.services.crowi-api.loadbalancer.server.port=3000"
  # Sticky sessions are disabled by default — leave them off.
```

Key points:

- `/api/v2/pages/:id/yjs-token` (HTTP) and `/collab` (WebSocket;
  HocuspocusProvider dials the bare `/collab` and sends the page id over
  the protocol) must both reach the api upstream.
- Set a generous idle timeout on the WebSocket location (around an
  hour). Editor sessions are long-lived, and premature disconnects
  hurt UX.
- Sticky sessions are **not** required.

> **Note (Crowi 2.0 / RFC-0005)**: The page-presence feature attaches its
> WebSocket at `/presence/:pageId`, with **exactly the same setup** as
> `/collab`. In your reverse proxy, route a `/presence` location to the
> api upstream the same way as `/collab` and forward the `Upgrade` header
> (for nginx, duplicate the `location /collab` block above and change only
> the path; for Traefik, add `/presence` to the `PathPrefix` rule).
> Presence viewer state and cross-instance propagation share the `REDIS_URL`
> Redis — there is no extra dedicated infrastructure. If the presence
> WebSocket does not reach the api, the live presence row simply hides
> itself; page viewing is unaffected.

## Environment variables

| Variable | Required | Purpose |
| -------- | -------- | ------- |
| `WS_TOKEN_SECRET` | Yes in multi-instance (cluster-wide identical) | HMAC signing key for the short-lived wsToken (JWT). **Must be identical** across all api replicas in multi-instance mode. If `CROWI_MULTI_INSTANCE` is set but `WS_TOKEN_SECRET` is unset (or a known placeholder), api **aborts boot** (a per-process random secret can't be cross-verified). In single-instance mode (`CROWI_MULTI_INSTANCE` unset) it may be left unset — a random secret is generated per process and a warning is logged. The shipped `.env.example` leaves it empty on purpose (no world-known secret is templated). **Must be at least 32 characters when set** — a shorter value aborts boot under `NODE_ENV=production` (also the default when `NODE_ENV` is unset) and only warns otherwise (known placeholder values are exempt). Generate one with `openssl rand -base64 32`. |
| `CROWI_MULTI_INSTANCE` | No (default single-instance) | Declares a multi-instance api deployment (`1` / `true`, or a replica count `>= 2`). This — **not** `REDIS_URL` presence — is the signal the `WS_TOKEN_SECRET` boot guard keys off, so a single replica that happens to use Redis (e.g. for rate limiting or the editor-cap counter) boots without a shared secret. Set it on every replica when you scale past one api node. |
| `COLLAB_MAX_EDITORS_PER_PAGE` | No (default `20`) | Per-page simultaneous-editor cap. The 21st editor and beyond receive read-only realtime updates but cannot type. |
| `NEXT_PUBLIC_COLLAB_URL` | No | The WebSocket URL the browser dials. When unset, it is derived from `window.location.host` and `NEXT_PUBLIC_API_URL`. Leave this unset if `/collab/*` is reverse-proxied to the same host as the api. |
| `REDIS_URL` | Yes in multi-instance | Coordination for collab pub/sub, the editor-cap counter, presence, notification invalidation, Config sync, rate limiting, and LRU (recently-viewed pages). See the next section for behaviour when unset. |
| `CROWI_ENCRYPTION_KEY` | Recommended | AES-256-GCM key for sensitive Config (OAuth secrets etc.). Not directly used by collab, but should be generated with `pnpm --filter @crowi/api crypto:gen-key` and shared across replicas. |

## Redis connection budget

The number of connections per api instance depends on the instance's
lifecycle stage, not a fixed count:

- **Right after boot** (before any collab session has started): **6**
  connections — 1 shared client (the editor-cap counter, LRU, rate
  limiting, presence hash writes, and notification publish all share
  it), 2 presence subscriber connections, 1 notification subscriber
  connection, and 2 Config publisher/subscriber connections.
- **After the first realtime-collab session starts on that instance**:
  **8** connections — the 6 above plus the 2 dedicated `ioredis`
  pub + sub connections `@hocuspocus/extension-redis` opens
  (`lazyConnect: true`, so they don't open until the first document
  load).

Example: 10 api replicas + 1 web replica

- Right after boot: 10 × 6 = 60 connections.
- Once every replica has hosted at least one collab session: 10 × 8 = 80 connections.
- Direct connections from web: none (proxied via the api).

Comfortably fits within the default `maxclients=10000`, but plan
accordingly for very small Redis tiers (ElastiCache `cache.t4g.micro` /
`cache.t3.micro`, Redis Cluster shards, etc.).

## Two-instance smoke test

Stand up a multi-instance environment via `docker compose --scale`:

```bash
# 1. Start the existing compose stack with api scaled to 2 replicas
docker compose --profile app up -d --build --scale api=2

# 2. Verify both api containers are up
docker compose ps api
# crowi-api-1   Up   3000/tcp
# crowi-api-2   Up   3000/tcp

# 3. Tail logs to see extension-redis attach on both replicas
docker compose logs -f api
# Expect 2 lines like:
#   crowi:collab:extension-redis attaching extension-redis (identifier=…)
```

Verification:

1. Open two browser windows (regular Chrome + Incognito, or two
   different browsers) and sign in as different users.
2. Navigate both windows to `/_edit?page_id=<pageId>` for the same page.
3. Type in one window — the change should appear in the other in
   real time.
4. If a load balancer is in front, confirm that each browser is
   routed to a different replica (compare the `instance=` identifier
   in the api's `onConnect` log).
5. **Presence**: with both windows still on the same page, confirm each
   window's live-viewer indicator shows the other user — this exercises
   the presence subscribers propagating viewer state across replicas
   via Redis. Run this check **before** the next step — once a replica
   is stopped there is only one replica left, so cross-replica fan-out
   can no longer be observed.
6. **Notifications**: from one window, trigger a notification for the
   other user (e.g. mention them in a comment) and confirm it arrives
   in real time in the other window even when the two browsers are
   pinned to different replicas — this exercises the notification
   subscriber's cross-instance invalidation via Redis. Also run this
   **before** the next step, for the same reason.
7. Stop one container (`docker compose stop api-1`); the surviving
   replica should accept the reconnecting clients and editing should
   resume.

## Failure modes

- **Redis outage (`REDIS_URL` set but unreachable):** ioredis keeps
  retrying. New Yjs updates still propagate within each api instance
  via the embedded Hocuspocus engine, but cross-instance pub/sub is
  paused. The editor-cap counter falls **open** (admits the editor).
  Pub/sub resumes automatically when Redis comes back.
- **`WS_TOKEN_SECRET` mismatch / unset:** wsTokens minted on one replica
  cannot be verified on another and `onAuthenticate` rejects the
  connection. The client sees an immediate disconnect and the editor
  stays in "could not connect" state. Fix by re-setting the same
  secret on every replica and performing a rolling restart. Note that
  declaring multi-instance via `CROWI_MULTI_INSTANCE` while
  `WS_TOKEN_SECRET` is unset (or a known placeholder) **aborts api boot**
  to prevent this class of failure up front; a single-instance deployment
  (no `CROWI_MULTI_INSTANCE`) boots fine without a secret. These
  diagnostics (wsToken verify failure / editor-cap reached) are emitted
  to production logs as
  **sampled warnings**, so you can distinguish the true cause of a
  "could not connect" report (expired token / secret mismatch / clock
  skew / cap reached).
- **`WS_TOKEN_SECRET` is too short (under 32 characters):** when it is set
  but shorter than 32 characters (known placeholders are exempt), api
  aborts boot under `NODE_ENV=production` (also the default when
  `NODE_ENV` is unset). The error message names the variable, its current
  length, the 32-character minimum, and how to generate a strong one
  (`openssl rand -base64 32`). Under any other `NODE_ENV` (`development`,
  `test`, ...) boot is not blocked — it is folded into the same
  consolidated boot-time warning report as every other env-validation
  finding. This is a plain length check only, with no entropy or
  dictionary heuristics.
- **Lost edits on multi-instance (known risk):** see the Important note
  under "Multi-instance deployment" above. A stale replica that
  materialises a Y.Doc from an old `Page.yjsState` and writes a
  checkpoint can overwrite newer state — a known risk mitigated (not
  fully prevented) by the optimistic lock + anti-shrink guard. A single
  instance is recommended.
- **WebSocket upgrade failure:** if the reverse proxy strips the
  `Upgrade` header, `/collab/` returns 400 or 426. Verify
  `proxy_set_header Upgrade $http_upgrade` in nginx (or the
  equivalent in your proxy of choice).
- **External edit during a live editing session:** when a page with an
  open collab session is updated through an **external path** — the REST
  API, the MCP `crowi_update_page` tool, or an in-process `Page.updatePage`
  — Crowi re-points `currentRevision` to the new revision and nulls
  `Page.yjsState`. If a live Y.Doc exists **in the same api process**, Crowi
  invalidates it after the write commits: it broadcasts `crowi:force-reload`
  to every connected client, tombstones the document's base revision so any
  in-flight stale save is rejected with `CONFLICT`, and force-closes the live
  connections after a short grace. This stops a client that reloaded first
  from re-attaching to the stale live Y.Doc and entering a `CONFLICT` loop.
  Each client shows a warning dialog and reloads; any unsaved local text can
  be restored from the recovery buffer, and the next connection re-materialises
  from the new `currentRevision` body.
  - **Known limitation (multi-instance / out-of-process):** the
    invalidation handle only reaches live Y.Docs **in that api process**. A
    live Y.Doc on a **different replica**, or an **out-of-process writer** (an
    admin CLI doing a DB-direct `Page.updatePage`), is not reachable, so under
    a multi-instance deployment an external edit may leave connected clients
    **editing stale content** until they **manually reconnect**. A
    cross-instance invalidation channel (Redis pub/sub fanned to every
    replica) is future work and out of scope for now (RFC-0003 §5b) — another
    reason a **single instance is recommended**.
- **Rename / delete during a live editing session** ([RFC-0017](https://github.com/crowi/crowi/blob/main/docs/rfcs/0017-collab-invalidate-on-rename-delete.md) Phase 1): when a page with an open collab
  session is renamed, soft-deleted, or reverted, Crowi advances a monotonic
  epoch on the Page model (`collabLifecycleVersion`) in the SAME write as
  the mutation. This epoch is signed into the wsToken at issue time and
  checked at three boundaries — connection `onAuthenticate`, the save's
  atomic compare-and-set, and checkpoint writes — so **a live editing
  session that started before a rename/delete has its save rejected, even
  in a multi-instance deployment, regardless of which replica performed
  the rename/delete**. This holds even for a plain rename, where the path
  and revision pointer alone wouldn't change — the epoch mismatch is what
  rejects the stale save. In other words, **write-safety for rename/delete
  is already cross-replica safe as of Phase 1**.
  - **Limitation until Phase 2**: the reload *prompt* (the
    `crowi:force-reload` broadcast + forced disconnect), however, has the
    same reach as the G1 external-edit invalidation above — it only reaches
    live Y.Docs **in the api process that performed the rename/delete**. An
    editor connected to a different replica may not see the reload prompt
    until its rejected save surfaces as a `CONFLICT` error (i.e. writes are
    safe, but prompt latency stays replica-local). Cross-replica prompt
    fan-out (via Redis pub/sub to every replica) is Phase 2 work and not
    yet implemented as of this writing.
- **`Page.yjsState` corruption:** in `onLoadDocument`, if `Y.applyUpdate`
  throws on the persisted yjsState, Crowi rebuilds the Y.Doc from the latest
  revision's Markdown body and broadcasts a force-reload notice to connected
  clients. Each client displays a warning dialog and reloads the page.
- **`renderedAst` drift (RFC-0002 coupling):** collab saves go through
  `Revision.prepareRevision`, which regenerates `renderedAst`. If
  `Page.body` and the latest `Revision.body` ever drift, a normal re-save of
  the affected page regenerates both. (A bulk `crowi-admin rebuild renderer`
  command is planned in RFC-0008 but not implemented yet.)
- **api process down:** all connected clients enter a reconnect loop.
  If your health check fails over to other replicas, clients dial
  the next available api and the Y.Doc is restored from
  `Page.yjsState` in MongoDB.

## Redis licensing and engine support policy

> This section is not specific to realtime collaborative editing — it
> is the Redis-wide license, engine-support, and security policy for
> **all 8 code paths** that talk to Redis in this codebase: collab
> pub/sub, the editor-cap counter, presence, notification invalidation,
> Config sync, rate limiting, LRU (recently-viewed pages), and the boot
> connection itself. It lives in this document because this is where
> operators already read about Redis requirements, connection budget,
> and failure-mode behaviour — not because it is collab-only.

### License facts and project policy

- **Established fact:** starting with Redis Open Source 8.0, the Redis
  project offers licensees a choice of three licenses — RSALv2,
  SSPLv1, or AGPLv3. Of the three, only AGPLv3 is OSI-approved open
  source.
- **Established fact:** Crowi never bundles the Redis server.
  `@crowi/api` and `@crowi/web` talk to Redis exclusively over TCP;
  neither the npm packages nor the api/web Docker images
  (`packages/api/Dockerfile`, `packages/web/Dockerfile`) contain a
  Redis binary.
- **Project policy:** the reference configuration Crowi tests against
  is an unmodified upstream Redis image, and the project evaluates
  that configuration under AGPLv3 — the one option of the three that
  is OSI open source. (AGPLv3 §13's network-interaction
  source-disclosure trigger requires the licensee to have modified the
  covered program; Crowi's reference deployment does not modify Redis,
  so that trigger does not apply to this usage pattern.)
- **Project policy:** the `image:` references in `docker-compose.yml`
  and the quickstart docs point at the upstream image only. Crowi does
  not modify, sublicense, or redistribute the Redis server — pointing
  a compose file at an upstream image is not the same thing as
  bundling or distributing it (that word is reserved for cases that
  actually copy image layers, archives, or binaries).
- **Project policy:** the project records the exact tested patch
  version and digest and does not use moving tags (like `redis:7`) in
  reproducible operator-facing instructions — see "Image pin policy"
  below. As of this writing, the `redis:7` tag on Docker Hub already
  resolves to Redis 7.4.x under the RSALv2/SSPLv1 choice, not the
  BSD-3-Clause-licensed Redis 7.2 line — a concrete example of how a
  moving tag can silently carry an operator across a license boundary
  they never opted into, independent of ordinary version drift.
- **Project policy:** Valkey is treated as a best-effort BSD-3-Clause
  alternative until it clears the same bar Redis 8 itself had to clear
  — see "Valkey" below.
- **Operator notice:** Redis itself, and any Redis-compatible managed
  service (ElastiCache, MemoryDB, Upstash, etc.), is a separate
  product with its own license or terms of service. Selecting it and
  complying with its terms is the operating organization's
  responsibility, not Crowi's.
- **Not legal advice:** this section records Crowi's technical
  architecture and maintainer policy — it is not legal advice. It
  reflects Crowi's understanding as of this writing and is not a
  substitute for qualified legal counsel. If you plan to redistribute,
  modify, bundle, or offer Redis as a managed service, consult a
  lawyer; Crowi's own usage pattern (talking to an unmodified upstream
  server over the network) does not need to answer that question, but
  yours might.

> **A scoping note, not a legal conclusion:** Crowi's own deployment
> pattern — running an unmodified Redis server behind Crowi over the
> network — looks like the straightforward self-hosted use that
> RSALv2's "provide … to third parties as a service" restriction is
> understood to target commercial database-as-a-service offerings, not
> this pattern. That reading is not a settled legal determination,
> though, so it is stated here as Crowi's working assumption rather
> than as fact.

### Valkey

Valkey is a BSD-3-Clause fork of Redis and is **not** formally
supported today — it is treated as best-effort. Crowi does not run its
real-Redis-8 compatibility smoke suite covering all 8 consumers
(collab pub/sub, editor-cap counter, presence, notification
invalidation, Config sync, rate limiting, LRU, and boot connection)
against Valkey in CI. Valkey graduates to formally supported once that
same 8-path smoke suite passes continuously against it in CI — the
same bar Redis 8 itself had to clear.

### Image pin policy

- The documented compatibility range is **`>=8.0 <9`**. This is an
  operator-facing statement of the versions Crowi tests and supports
  — it is not enforced at runtime. Crowi does not refuse a Redis 7
  connection in code.
- `docker-compose.yml` and CI pin to a single reviewed patch tag with
  its digest:
  `redis:8.8.0@sha256:234c902a2db49461a129e2d4aeff85b28cf20187ed274a67f6e50995fa713c7b`.
  Moving tags (`redis:7`, `redis:8`, `redis:latest`) are not used.
- In practice, only that one pinned patch tag is continuously
  exercised by CI and compose — the `>=8.0 <9` range is a stated
  compatibility target, not a claim that every patch or minor version
  in it has been individually verified.

### Multi-replica upgrade and rollback

- **Standard procedure: coordinated drain/restart.** Stop all
  replicas together, point every replica's `REDIS_URL` at the new
  endpoint, and restart together. Redis pub/sub provides no
  distributed mutual exclusion, so **running replicas against
  different Redis servers at the same time (a "split brain") is
  explicitly disallowed** — instead of failing loudly, cross-replica
  fan-out (collab, presence, notifications, Config sync) silently
  splits into two disconnected groups.
- **Vendor-supported online promotion** (a managed replica promotion,
  blue-green cutover, etc.) is fine to use **only when you have
  confirmed your specific Redis distribution actually supports a 7→8
  topology change that way** — Crowi's own tooling does not verify
  this.
- **RDB cross-engine portability is not guaranteed.** Don't assume an
  RDB snapshot written by Redis can be loaded by Valkey, or vice
  versa.
- **Rollback: clear stale coordination state before reconnecting.**
  Coordination keys such as the editor-cap counter
  (`crowi:collab:editors:<pageId>`, 24h TTL) and the presence hashes
  (`crowi:presence:viewers:<pageId>` / `crowi:presence:editing:<pageId>`)
  can linger on the pre-switch instance. Reconnecting every replica
  without clearing them first can mix stale socket ids in with live
  ones — the editor cap can over-report and push an editor into
  read-only unintentionally, and presence can show short-lived ghost
  viewers. Standard procedure:
  1. Confirm every replica has drained from the old endpoint (existing
     WebSocket connections closed, no new connections dialing it).
  2. Point the rollback target at a **fresh, or
     `crowi:`-prefix-cleared,** Redis instance.
  3. After cutover, verify the editor-cap counter's `peek()` and the
     presence viewer list match the actual connection count before
     resuming traffic.

  None of the 8 consumers store page content in Redis — `Page.yjsState`
  and all page content live only in MongoDB — so a cold start of any of
  these Redis instances never causes page-content data loss; see
  [Failure modes](#failure-modes). That doesn't mean every consumer's
  own Redis-resident state survives a cold start equally well, though:
  collab pub/sub, presence, notification invalidation, and Config sync
  are pure cross-replica coordination with nothing to lose; the
  editor-cap counter and rate limiting deliberately reset (fail open /
  fall back to an in-memory window) rather than block; and LRU's
  recently-viewed-pages list has no fallback at all, so a cold start
  loses it outright — see the per-consumer breakdown in
  [Single-instance deployment](#single-instance-deployment).

### Re-review triggers

Re-review this policy if any of the following happen (summarized into
six categories from a more detailed internal design review):

1. Crowi starts forking, modifying, mirroring, or bundling the Redis
   image itself.
2. Crowi starts exposing RESP directly to end users, or starts selling
   or otherwise offering Redis's own functionality as a service.
3. Redis moves from a separate process/service to something that
   crosses a process boundary with Crowi — single-process integration,
   shared memory, etc.
4. Redis's own license, its official image contents, or its version
   policy changes.
5. A client library's license changes (`node-redis`, `ioredis`,
   `@hocuspocus/extension-redis`).
6. Valkey is promoted to formally supported, or Crowi starts using a
   Redis module it doesn't use today.

### Security operations guide

> This guide is derived from reading the actual code paths and the
> upstream libraries' source as of this writing. It is **not** a
> CI-verified contract — see "What CI does and doesn't verify" below
> — and should be re-checked whenever `redis`, `ioredis`, or
> `@hocuspocus/extension-redis` are updated, since the exact commands
> they issue can change between versions.

**Transport and credentials.** Use `rediss://` and keep
`REDIS_REJECT_UNAUTHORIZED` at its default (certificate verification
on); reserve verification-disabled connections for an explicitly
controlled dev / private-CA scenario. Keep credentials in environment
variables or a secret manager — don't put them in a Config row's
plaintext field or log them.

**Network exposure.** Redis should be reachable only from Crowi and
its internal infrastructure. Never expose it, unauthenticated, to a
public network.

**ACL command / key / channel matrix.** Building a restricted ACL
user? Every one of these needs to be granted, or collab saves and
other operations will start failing with permission errors instead of
a clean "unsupported feature" failure:

| Consumer | Commands | Keys / channels |
| --- | --- | --- |
| Collab pub/sub | `SUBSCRIBE`, `UNSUBSCRIBE`, `PUBLISH` | `crowi:collab:<documentName>` — a single channel per document; Y.Doc sync and awareness updates are both multiplexed over it (there is no separate `:awareness:` / `:y-update:` sub-key) |
| Editor-cap counter | `SADD`, `SCARD`, `SREM`, `EXPIRE` | `crowi:collab:editors:<pageId>` |
| Presence | `HSET`, `HGET`, `HGETALL`, `HDEL`, `EXPIRE`, `PUBLISH`, `SUBSCRIBE` | `crowi:presence:viewers:<pageId>`, `crowi:presence:editing:<pageId>`, `crowi:presence:updates`, `crowi:presence:page-updated`, `crowi:presence:comment-changed` |
| Notification invalidation | `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE` | `crowi:notifications:user:<userId>` |
| Config sync | `PUBLISH`, `SUBSCRIBE` | fixed channel `config` |
| Rate limiting | `INCR`, `PEXPIRE` | `crowi:ratelimit:<name>:<userId>:<window>` |
| LRU (recently-viewed pages) | `ZREMRANGEBYRANK`, `ZADD`, `ZRANGE` (`ZREMRANGEBYRANK` + `ZADD` pipelined via `MULTI`/`EXEC`) | an operator-chosen namespace key (no fixed `crowi:` prefix) |
| Boot connection | connection handshake only | n/a |

Two more command sources are easy to miss because Crowi's own code
never issues them directly:

- **Client-library connect-time commands.** `node-redis` (the shared
  `crowi.redis` client) sends `CLIENT SETINFO` (`LIB-NAME`/`LIB-VER`)
  on every connect; `ioredis` (the two dedicated collab pub/sub
  clients) runs `INFO` as its ready check. Denying these via ACL does
  not necessarily break the connection outright — ioredis logs a
  warning and skips the ready check when `INFO` comes back `NOPERM`,
  and node-redis swallows a permission-denied `CLIENT SETINFO` reply
  (it only rejects the connect promise for an unrelated, non-`ErrorReply`
  failure) — but grant them explicitly rather than relying on that
  survival behaviour in production.
- **The upstream Redlock the collab extension runs internally.**
  `@hocuspocus/extension-redis` acquires, extends, and releases a
  cross-instance store lock via `@sesamecare-oss/redlock` on **every
  collaborative save**, using `EVAL`/`EVALSHA` to run a Lua script.
  Redis ACLs authorize commands called from *inside* a Lua script too,
  so the ACL must also allow the script's own `SELECT`
  (pcall-protected), `EXISTS`, `SET`, `GET`, and `DEL`
  (pcall-protected) against `crowi:collab:<documentName>:lock`. **An
  ACL that omits this matrix makes every collaborative save fail with
  a permission error in a Redis-enabled production deployment** — the
  save never reaches Crowi's Mongo compare-and-set checkpoint, so the
  edit stays stuck in memory (retried on the next debounce cycle)
  instead of persisting, and it produces constant error-log noise
  until the ACL is fixed. **This Redlock does not add a persistence
  guarantee of its own** — it only serializes concurrent store
  attempts across instances. If the Crowi process dies *after* the
  Redis store hook (including this Redlock) succeeds but *before*
  Crowi's own Mongo compare-and-set checkpoint completes, the unsaved
  document may be lost until the client reconnects and Yjs re-syncs
  from the last durable Mongo state.

**ACL scope: users, not listeners.** Redis ACLs are scoped to
**users**, not to a listening port — "restrict the TLS port" is not a
coherent ACL design. A restricted deployment needs every listener to
disable or password-protect the `default` user, and every Crowi
client (the shared node-redis client and the collab `ioredis`
clients) to explicitly authenticate as a scoped user. Prefer
key/channel-pattern grants over a broad `@all` category.

**Failure-time semantics.** The editor-cap counter is a soft
availability control, not an authorization boundary — its fail-open
behaviour (it stops enforcing the cap rather than blocking new
editors) is a deliberate design choice; see
[Failure modes](#failure-modes). Redis being unreachable never
bypasses JWT or WS-token authentication — neither check depends on
Redis. Rate limiting also fails open: if a Redis round trip throws,
the request is allowed rather than blocked, so a missing ACL grant the
rate limiter needs produces the same silent, undetected disabling of
the limit that a Redis outage would — watch for it when narrowing an
ACL.

**Key / channel separation.** The 8 consumers use disjoint prefixes:
`crowi:collab` (collab pub/sub, sub-keyed per document),
`crowi:collab:editors:<pageId>` (editor cap), `crowi:presence:*`
(presence hashes and channels), `crowi:notifications:user:<userId>`
(notifications), the fixed channel `config` (Config sync — not
`crowi:`-prefixed), and `crowi:ratelimit:*` (rate limiting); LRU uses
an operator-chosen namespace key with no fixed prefix. **Don't rely on
the Redis URL's database-number segment for worktree or cluster
isolation** — nothing here uses it, and it is not a substitute for the
prefixes above.

**Alternative engines.** See "Valkey" above: tested support,
best-effort protocol compatibility, and unsupported configurations are
three different tiers. Valkey's BSD-3-Clause license and independent
governance matter to operators who prefer it, but binary/RDB
persistence compatibility is not guaranteed — see "Multi-replica
upgrade and rollback" above.

**Supply chain.** Pin an explicit image family and version (see
"Image pin policy" above), record the tested digest in your own
release tooling where possible, and don't use a generic distro alias
as a stand-in for a compatibility claim.

**What CI does and doesn't verify.** CI runs real Redis 8 smoke tests
for all 8 consumers, but it does **not** run them against a restricted
ACL user — the matrix above is written from source inspection, not
exercised by an automated permission-denial test. Treat it as an
operator reference, not a guarantee, and re-verify it after upgrading
`redis`, `ioredis`, or `@hocuspocus/extension-redis`.

## Capacity tuning

- `COLLAB_MAX_EDITORS_PER_PAGE` controls the per-page editor cap. The
  default 20 reflects rendering cost for awareness cursors. Raising
  it significantly should be paired with browser-side testing under
  many concurrent awareness payloads.
- Y.Doc changes are flushed to `onChange` with `debounce: 2000` ms
  (inherited from Hocuspocus defaults). Small bursts of edits do not
  generate one `PageYjsUpdate` write per keystroke.
- `PageYjsUpdate` rows expire after 1 hour (TTL index), and a
  periodic compaction merges them into `Page.yjsState`. Long editing
  sessions therefore do not blow up MongoDB storage linearly.

## Save SLO

- A typical collab save completes in 100-500ms.
- The server enforces a 5-second timeout. Past that, the client
  receives an error response (HTTP 408 equivalent).
- A timeout **does not necessarily mean the save failed**: the DB
  write may have succeeded with only the response delayed. Clients
  do **not** retry automatically. The correct recovery is to reload
  the page and inspect the latest revision.
- The 5-second cap is a safety net against extreme slowness; under
  normal network conditions it has plenty of headroom. If you see
  recurring timeouts, investigate MongoDB latency, renderer pipeline
  cost, and connection pool sizing.
