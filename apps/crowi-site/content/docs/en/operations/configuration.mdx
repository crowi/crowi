Crowi 2.0 configuration is split into three layers.

1. **Environment variables** (`.env` / process environment) — values
   needed at boot, such as connection targets and encryption keys.
2. **`crowi.config.json`** — which plugins to load and which drivers to
   enable.
3. **Admin UI settings** — detailed values such as the app title, OAuth,
   mail, and storage. Stored in the MongoDB `Config` collection.

This page covers 1 and 2. For the settings in 3, see [Admin panel](./admin).

## Environment variables

At boot, the API loads `.env` from the working directory it was started in.
In development that directory is the **repository root** (the `pnpm dev` api
script loads it explicitly). In production it is the **runner project's
directory**, or you inject the variables through your compose file /
orchestrator instead of a file. Copy `.env.example` and edit it.

```bash
cp .env.example .env
```

The API validates all of these environment variables together at boot. If
`PORT`, `MONGO_URI` (or an alias), `REDIS_URL` (or an alias), or
`CROWI_ENCRYPTION_KEY` is malformed, boot fails immediately with a single
error message listing every problem found. A malformed `CLIENT_URL`,
`CROWI_MULTI_INSTANCE`, `NODE_ENV`, `JWT_ACCESS_TOKEN_TTL_SECONDS`,
`JWT_REFRESH_TOKEN_TTL_SECONDS`, `COLLAB_MAX_EDITORS_PER_PAGE`, or
`MIGRATION_PREFLIGHT_UNAPPLIED_POLICY` does not block boot — these are
reported together as a single consolidated warning in the boot log instead
(an unset `CLIENT_URL` also gets a warning there, since links in outgoing
mail would otherwise be relative).

`WS_TOKEN_SECRET` is the one exception whose **severity depends on
`NODE_ENV`**. Its requirement is stated on its row in
[Environment variables](../reference/env).

An env var carrying one of the known Crowi prefixes (`CROWI_`, `WS_TOKEN_`,
`JWT_`, `COLLAB_`, `REDIS`, `MONGO`, `MIGRATION_`) that matches no known
variable name exactly is checked against every known name using Levenshtein
(edit) distance; if the closest match is within a distance of 2, it is
flagged as a likely typo ("did you mean `XXX`?") in the same warning report
— this never fails boot, since the heuristic is allowed false positives.
Ordinary OS/CI environment variables without one of those prefixes (`PATH`,
`CI`, `GITHUB_*`, `npm_*`, etc.) are never flagged.

### The list of variables

Names, defaults and meanings are listed in [Environment variables](../reference/env). For how the collaboration variables are used together see [Operating realtime collaboration](./realtime-collab), and for choosing `NEXT_PUBLIC_API_URL` / `NEXT_PUBLIC_COLLAB_URL` per topology see [Deployment topologies](./deployment).

> **Tip**: Both `WS_TOKEN_SECRET` and `CROWI_ENCRYPTION_KEY` can be
> generated with `openssl rand -base64 32`. `CROWI_ENCRYPTION_KEY` can
> also be generated with `pnpm --filter @crowi/api crypto:gen-key`.

### The MCP endpoint

The MCP endpoint for AI clients, `/api/mcp`, is always enabled — there is no feature flag. Three things matter operationally.

- **Only personal access tokens authenticate there.** A web session or an OAuth access token cannot connect. The steps a user follows are in [Using Crowi from AI tools (MCP)](../guide/mcp).
- **The front proxy only has to forward `/api/*` to the api.** MCP clients connect to `/api/mcp` on the same origin as the wiki; there is no extra port or process to expose.
- **Setting `REDIS_URL` shares the rate-limit budget across replicas.** Without it each replica keeps its own in-memory budget, so the effective limit scales with the replica count.

The server is stateless (a fresh session per request), so multi-replica deployments need no sticky sessions.

### Environment variables in Docker

When running the full stack with `docker compose --profile app`, the
`api` service reads `.env` as an `env_file`. However, the
container-network URIs (`MONGO_URI` / `REDIS_URL` / `CLIENT_URL`) are
overridden by the `environment` entries in `docker-compose.yml`.
Secrets such as `CROWI_ENCRYPTION_KEY` and `WS_TOKEN_SECRET` are passed
through as long as they are present in `.env`.

> **Tip**: The web app (`@crowi/web`) is a **separate deployable** with no
> plugin dependencies; it talks to the api over HTTP and can run anywhere
> (Vercel, a container, or co-located with the api). The api, by contrast,
> is a long-lived Node server (persistent database connections, pub/sub
> between replicas, a resident WebSocket server, plugins loaded at boot), so
> it **requires a Node runtime** — a Node host or a Node container (ECS / EKS
> / Fly / Render / Cloud Run / Cloudflare Containers). It does not run on
> edge/isolate serverless platforms such as Cloudflare Workers.

### Renderer plugin assets and CSP (Content-Security-Policy)

Some renderer plugins — KaTeX, for example — serve static assets (CSS,
fonts) from their own public route (`/api/plugins/<plugin-name>/...`).
The web app asks the api which renderer plugins are active and loads their
stylesheets as `<link rel="stylesheet">` tags pointed at the api origin — the
web app never needs to know a plugin's name or CSS ahead of time.

Deployments where web and api share the **same origin** (the recommended
reverse-proxy setup above) need no extra configuration. The existing CORS
policy (allowing `CLIENT_URL` as the origin) already
covers the cross-origin CSS/font responses, so no extra CORS configuration
is needed either.

Deployments that run web and api on **different origins** and enforce a
Content-Security-Policy must allow the api's origin in both `style-src` and
`font-src`. For example, with `CLIENT_URL=https://wiki.example.com` and the
api running at `https://api.example.com`, the web app's CSP header needs
roughly:

```
Content-Security-Policy: style-src 'self' https://api.example.com; font-src 'self' https://api.example.com; ...
```

Forgetting this allowance silently blocks the CSS/fonts in the browser even
though the plugin is active and healthy — neither the api nor the web app
logs an error, since nothing failed server-side. Check the browser console
for a CSP violation report.

## crowi.config.json

`crowi.config.json` is a JSON file placed at the **root of the runner
project**. It declares **which plugins to load and which drivers to
enable**. Per-plugin configuration values
(S3 bucket name, OAuth client ID, mail / storage credentials, etc.) are
not written here — they are stored in the MongoDB `Config` collection and
edited from the admin UI.

```json
{
  "plugins": [
    "@crowi/plugin-storage-aws-s3",
    "@crowi/plugin-search-elasticsearch",
    "@crowi/plugin-renderer-plantuml",
    "@crowi/plugin-renderer-katex"
  ],
  "storage": {
    "driver": "s3"
  },
  "search": {
    "driver": "elasticsearch"
  }
}
```

### Fields and driver names

The keys, their defaults, and the driver names you can set are listed in [crowi.config.json](../reference/config-file). The defaults apply when the file is missing or a key is omitted, and content that does not match the schema fails at boot with an explicit error.

### How plugins are resolved

`@crowi/api` is **plugin-free**: it ships the SDK (`@crowi/plugin-api`) and
core only, and bundles no drivers. The plugins are owned by the runner
project. The names listed in `plugins` are resolved at boot from the runner
project's own `node_modules/`. To add a plugin, declare it as a dependency
in the runner's `package.json` and add
its name to `crowi.config.json:plugins`. The api package itself does not
need to be rebuilt.

Three plugins are always loaded as **implicit default plugins** and need no
configuration: `@crowi/plugin-storage-local`, `@crowi/plugin-search-mongo`,
and `@crowi/plugin-mail-smtp`. As a result, a fresh install works out of
the box with **local storage + MongoDB search + SMTP mail** — MongoDB is
the only required infrastructure.

The runner project is started with its `package.json` `"start": "crowi-api"`
script (the `crowi-api` bin provided by `@crowi/api`), run from the project
directory itself so that plugins resolve against its `node_modules/`.

When a plugin declares other plugins via `requires`, those dependencies are
also **resolved and loaded automatically (transitively)**, so you do not need
to list the dependency in `plugins` as well. For example,
`@crowi/plugin-storage-aws-s3` and `@crowi/plugin-mail-aws-ses` both declare
the shared base `@crowi/plugin-aws` via `requires`, so listing **only the
driver plugins** in `plugins` is enough — `@crowi/plugin-aws` is loaded
automatically. You do not need to list the umbrella `@crowi/plugin-aws`
explicitly (which avoids a double load). For the end-to-end procedure using
the full AWS stack, see [Running on AWS Lightsail](./aws-lightsail).

For detailed steps on adding and enabling plugins, see
[Installing and configuring plugins](./plugins); for the kinds of plugins, see
[Plugin architecture](../develop/plugins-overview).

### Plugins with no driver to select

Renderer plugins (`@crowi/plugin-renderer-katex` / `-plantuml` /
`-mermaid` / `-crowi-legacy`) are enabled simply by adding them to
`plugins`; they need no driver selection like `storage` / `search`. Emoji
shortcodes and link cards (`@[card](url)`) are Crowi core features, not
plugins — they are always on with no `plugins` entry required (link-card's
outbound fetch can be disabled via the `linkCardEnabled` toggle under admin
Security).

> **Tip**: Even if you switch a driver name in `crowi.config.json`, a
> warning is logged at boot if the corresponding plugin is not in
> `plugins`. Always switch drivers together with adding the plugin.
