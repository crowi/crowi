title: Attachments
description: Attaching files and images to pages
---

In Crowi, you can attach files to any page. Screenshots, PDFs, log files —
anything you want to keep alongside a page's body can be uploaded as an
attachment.

## Where attachments live

Attachments are stored **bound to an existing page**. When you open a page,
an "Attachments" section appears in the page body footer and lists every
attachment linked to that page.

> **Note**: Attachments require the page to exist first. Crowi 1.x had a
> behaviour where uploading an attachment could implicitly create an empty
> page (`page_id=0`); this was removed in v2. To attach a file to a new
> page, create and save the page first, then add the attachment.

## Adding a file

Use the Attachments section in the page footer to pick a file and upload
it. Once the upload finishes, the file is added to the list right away,
along with a record of who uploaded it and when.

Internally, an attachment is sent to `POST /api/v2/pages/:pageId/attachments`
as `multipart/form-data`. The uploaded file is stored via the configured
storage driver (local disk / S3, depending on the operator's setup) and a
single `Attachment` document is created.

For choosing a storage backend, see
[Storage configuration](../operations/storage).

## The attachment grid

The Attachments section in the page footer renders attachments as a
**uniform tile grid**. Each tile shows either the image thumbnail (for
PNG / JPEG / GIF / WebP, etc.) or a file-type icon stacked above the
filename (for PDFs, zips, text, and other non-image files).

- Clicking a tile opens a **modal preview** in-page — you do not
  navigate away from the page.
- The modal includes an "Open original" link that opens the
  **unmodified original file** in a new tab (as described below, images
  in the grid and page body use a display-optimized version, but this
  link always points at the original).
- The list shows only attachments referenced by the page's **latest
  revision**. A "view all attachments" link at the bottom routes to a
  dedicated listing (see below).

Each attachment is assigned a URL of the form `/api/v2/attachments/<id>`.
Hitting that URL delivers the actual file; non-image files are downloaded
under their original filename.

### Display-optimized images

When you upload a still JPEG/PNG/WebP image, a display-optimized
derivative (capped at 1728px wide, with metadata stripped) is generated
on a best-effort basis right after the original is saved.
**`/api/v2/attachments/<id>` prefers this optimized derivative whenever
one is available** — embedded images in the page body, thumbnails in the
attachment grid, and the editor preview all reference the same URL, so
they automatically receive the lighter-weight derivative with no code
changes on their side.

- SVGs, GIFs (static or animated), animated WebP/APNG, and images already
  at or below 1728px are not optimized — the original is served as-is
  (never upscaled or duplicated).
- If derivative generation fails, the original is unaffected and the
  upload still succeeds; that attachment simply keeps serving the
  original until a derivative is generated.
- The derivative is a best-effort display cache, not durable data — the
  original's Exif/GPS metadata is preserved unchanged. Metadata is only
  stripped from the derivative.

Right-clicking an image embedded in a page body and choosing "Save
image as…" saves this optimized derivative, not the original. To get an
unmodified original, use the "Open original" link in the attachment
detail modal, or open `/api/v2/attachments/<id>/original` directly.

> **Tip**: Attachment delivery enforces the page's view permission. Even
> if someone knows an attachment's URL, the file is not delivered to a
> user who cannot view the owning page (a 404 is returned to hide its
> existence). `/original` enforces this same page-view check, plus one
> more requirement the canonical URL does not have: it additionally
> requires the `attachments:read` scope, so a token scoped without it can
> still fetch the canonical delivery URL but not `/original`.

### The "All attachments" page

`/_attachments?pageId=<id>` opens the dedicated listing for a page,
split into two sections:

- **Used in the latest revision** — files actually embedded in the
  current page content.
- **Used only in past revisions** — files no longer referenced by the
  latest revision but still present in older history entries (or
  orphaned by edits).

This view is useful when you need to inspect or clean up attachments
that the page footer no longer surfaces.

### Images in the page body

To display an image inside the Markdown body, reference the attachment's
URL with image syntax.

```markdown
![Screenshot](/api/v2/attachments/64f0a1b2c3d4e5f6a7b8c9d0)
```

Besides typing the URL by hand, uploading directly into the editor via
**paste** or **drag-and-drop** (below) automatically inserts the image
syntax for you.

> **Note**: Paste and drag-and-drop always insert a plain, attribute-less
> `![filename](url)` by default. Add a `{width= height= align= float=}`
> attribute block by hand afterward if you want to set the image's size,
> alignment, or text-wrap float (see [Writing Markdown](./markdown)'s
> "Image display attributes" section). Hovering over — or placing the
> cursor inside — an image's Markdown span in the editor also shows a
> tooltip with `width` / `align` / `float` controls.

## Uploading directly into the editor

On the page edit screen (`/_edit?page_id=<page ID>`), you can upload a
file by **pasting** it into the editor or **dragging and dropping** it.
The uploaded attachment is bound to the page you're editing, and its
Markdown syntax is inserted automatically at the cursor.

> **Note**: This only works inside the edit screen's editor. Uploading
> from the Attachments section in the page footer still works as
> described above.

### Pasting an image

Pasting a screenshot or an image copied from another app uploads it
automatically.

- The filename is auto-generated as `pasted-<timestamp>.<ext>` (e.g.
  `pasted-1717891234.png`).
- While uploading, a placeholder `![Uploading pasted-1717891234.png
  (37%)…](#)` is inserted at the cursor, with the percentage updating
  live. Other members editing the same page collaboratively see this
  progress too.
- Once the upload finishes, the placeholder is replaced with
  `![pasted-1717891234.png](/api/v2/attachments/...)`.
- Pasting the same image twice creates two separate attachments (there
  is no client-side de-duplication). Delete the extra one from the
  attachment list if you don't need it.

Pasted images are accepted up to **10 MB**, for these types:

| Type | MIME type |
| ---- | --------- |
| PNG | `image/png` |
| JPEG | `image/jpeg` |
| GIF | `image/gif` |
| WebP | `image/webp` |
| SVG | `image/svg+xml` |

> **Tip**: For what happens when you paste non-image text or a bare
> URL, see [Writing Markdown](./markdown) — pasting a URL is
> automatically converted into link syntax.

### Dragging and dropping files

Dragging a file over the editor highlights the drop target; dropping it
starts the upload at the cursor position.

- Images are inserted as `![filename](url)`, other files as
  `[filename](url)`.
- The progress-placeholder behaviour is the same as pasting.
- Dropping multiple files at once processes them **serially**, in the
  order the OS reports them, with one placeholder per file.
- The per-file limit is **50 MB**, and a single drop can carry at most
  **5 files**. Exceeding either limit shows a toast notification.

The default allow-list of file types accepted by drag-and-drop is (an
operator can change this — see [Storage driver](../operations/storage)):

| Category | Accepted |
| -------- | -------- |
| Images | Same as paste (PNG / JPEG / GIF / WebP / SVG) |
| Documents | `.pdf` / `.txt` / `.md` / `.csv` |
| Archives | `.zip` |

Dropping a type not on the allow-list shows a toast naming the rejected
type.

> **Note**: When the edit screen is in **read-only mode** (the
> simultaneous-editor cap was reached, or you lack edit permission —
> see [Realtime collaborative editing](./realtime-editing)),
> drag-and-drop is disabled and a permission toast is shown instead.

### When an upload fails

If an upload fails (e.g. a network disconnect), the placeholder is
replaced with a static error marker: `![Upload failed:
<filename>](#)` (or `[Upload failed: …](#)` for non-images).

The error marker stays in the body as-is — there is no retry button.
Delete the marker by hand, then paste / drop again.

## Removing an attachment

Removal happens from inside the **detail modal** — there is no inline
delete button on each tile. Click an attachment to open its modal, then
remove it from there. Removing an attachment deletes both the
`Attachment` document and the actual file in storage.

Only users matching one of the following can remove an attachment:

| Condition | Description |
| --------- | ----------- |
| Attachment creator | The user who uploaded the file |
| Administrator | A user with the `admin` role |
| Granted user of the page | A user listed in the page's `grantedUsers` |

> **Note**: In Crowi 1.x anyone could delete an attachment; in v2
> permission is restricted as shown above.

## Compatibility with legacy URLs

Crowi 1.x URLs of the form `/files/:id` are 302-redirected to the new
delivery endpoint `/api/v2/attachments/:id`. Attachment URLs embedded into
page bodies before the migration keep working, so there is no need to
rewrite older pages.

## When a page is permanently deleted

When a page is permanently deleted from the trash, the attachments linked
to that page are deleted as well, including their storage objects. See
[Trash](./trash) for details.
