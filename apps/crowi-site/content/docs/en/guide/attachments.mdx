title: Attachments
description: Attaching files and images to pages
---

In Crowi, you can attach files to any page. Screenshots, PDFs, log files —
anything you want to keep alongside a page's body can be uploaded as an
attachment.

## Where attachments live

Attachments are stored **bound to an existing page**. When you open a page,
an "Attachments" section appears in the page body footer and lists every
attachment linked to that page.

> **Note**: Attachments require the page to exist first. Crowi 1.x had a
> behaviour where uploading an attachment could implicitly create an empty
> page (`page_id=0`); this was removed in v2. To attach a file to a new
> page, create and save the page first, then add the attachment.

## Adding a file

Use the Attachments section in the page footer to pick a file and upload
it. Once the upload finishes, the file is added to the list right away,
along with a record of who uploaded it and when.

Internally, an attachment is sent to `POST /api/pages/:pageId/attachments`
as `multipart/form-data`. The uploaded file is stored via the configured
storage driver (local disk / S3, depending on the operator's setup) and a
single `Attachment` document is created.

For choosing a storage backend, see
[Storage configuration](../operations/storage).

### What file types can be uploaded

Whichever of the following three ways you attach a file, the decision of
whether to accept it uses **the same criteria**:

- Uploading from the Attachments section in the page footer
- **Pasting** into the editor
- **Dragging and dropping** into the editor

These used to be checked against separate, per-route allow-lists — for
example, the same HTML file could upload fine from the Attachments button
while being rejected by drag-and-drop. All three routes now consult the
same allow-list, so whether a file is accepted no longer depends on which
one you used.

The main categories accepted:

| Category | Examples |
| -------- | -------- |
| Images | PNG / JPEG / GIF / WebP / SVG / BMP / AVIF / APNG / ICO |
| Documents / text | PDF, plain text, Markdown, CSV, JSON, XML, HTML |
| Office documents | Word (`.doc` / `.docx`), Excel (`.xls` / `.xlsx`), PowerPoint (`.ppt` / `.pptx`) |
| Archives | zip, gzip, tar |
| Audio / video | MP3, WAV, MP4, WebM, QuickTime (`.mov`) |
| Unknown type | Also accepted when the browser sends no `Content-Type` at all (`application/octet-stream`) |

Uploading a type that is not on this allow-list is rejected with the same
error every time: `Files of type <MIME type> cannot be uploaded.` — the
criteria and the wording are identical across every route.

> **Note**: This allow-list only decides "may this be saved at all".
> Whether an attachment is displayed inline in the browser or downloaded
> when opened directly is a separate decision — see "Content types on
> delivery" below. Office documents and archives, the types newly
> accepted here, are downloaded when opened directly.

## The attachment grid

The Attachments section in the page footer renders attachments as a
**uniform tile grid**. Each tile shows either the image thumbnail (for
PNG / JPEG / GIF / WebP, etc.) or a file-type icon stacked above the
filename (for everything else). The icon **varies by file format** — PDF,
zip, plain text, Word, Excel, PowerPoint, and more each get their own icon
— and falls back to a generic icon for any MIME type not in that mapping,
so the grid never breaks on an unrecognised type.

- Clicking a tile opens a **modal preview** in-page — you do not
  navigate away from the page.
- The modal includes an "Open original" link that opens the
  **unmodified original file** in a new tab (as described below, images
  in the grid and page body use a display-optimized version, but this
  link always points at the original).
- The list shows only attachments referenced by the page's **latest
  revision**. A "view all attachments" link at the bottom routes to a
  dedicated listing (see below).

Each attachment is assigned a URL of the form `/api/attachments/<id>`.
Hitting that URL delivers the actual file.

### Content types on delivery

An attachment's MIME type is recorded from what the client declared at
upload time. **When nothing was declared, or `application/octet-stream` was
declared explicitly** — the two are treated identically, as "type unknown" —
the server fills the type in from the filename's extension. MCP, curl,
and hand-written scripts routinely omit the `Content-Type`, which otherwise
stored and served even an image like `pixel.png` as a generic file. An
unknown extension, or no extension at all, stays
`application/octet-stream`. A declared type other than
`application/octet-stream` is **never overridden**, even when it contradicts
the extension — the declaration is the caller's stated intent.

Delivery does not trust the recorded value either way: the outgoing
`Content-Type` is **pinned to a server-side allow-list**.

| Type as delivered | Behaviour |
| ----------------- | --------- |
| PNG / JPEG / GIF / WebP / BMP / AVIF / APNG / ICO | Displayed inline in the browser |
| SVG (`image/svg+xml`) | Displayed inline (with the sandbox described below) |
| PDF (`application/pdf`) | Displayed inline in the browser's PDF viewer |
| `text/plain` / `text/markdown` / `text/csv` | Displayed inline as plain text |
| Everything else | Replaced with `application/octet-stream` and downloaded (`Content-Disposition: attachment`) |

A type that is not on the allow-list is downloaded regardless of what was
declared when it was uploaded. Attaching an HTML file and opening its
URL, for example, never renders as HTML in the browser. The decision is
made **on every delivery**, so the same rule applies to attachments that
are already stored.

Two response headers go with this:

- `X-Content-Type-Options: nosniff` — set on every API response. It stops
  a browser from disregarding the declared `Content-Type` and guessing
  the type from the bytes (MIME sniffing), which would otherwise route
  around the pinned type.
- `Content-Security-Policy: sandbox` — set on attachment deliveries that
  the table above renders inline, PDF excepted. It ensures that even a
  document format that can carry script, such as SVG, is only ever
  rendered without script execution and without an origin.

> **Note**: Embedding an SVG through image syntax in the body or an
> `<img>` tag looks exactly as before (the sandbox does not apply on the
> path where it is processed as an image). What changes is opening an SVG
> directly, or loading it through `<object>` / `<embed>` / `<iframe>`.
> Mermaid and PlantUML diagrams are unaffected: their SVG is embedded
> straight into the body and never goes through attachment delivery.

> **Note**: If you run behind a reverse proxy, do not rewrite or strip
> these headers (`Content-Type` / `Content-Disposition` /
> `X-Content-Type-Options` / `Content-Security-Policy`). Attachment
> delivery relies on them reaching the browser intact.

### Display-optimized images

When you upload a still JPEG/PNG/WebP image, a display-optimized
derivative (capped at 1728px wide, with metadata stripped) is generated
on a best-effort basis right after the original is saved.
**`/api/attachments/<id>` prefers this optimized derivative whenever
one is available** — embedded images in the page body, thumbnails in the
attachment grid, and the editor preview all reference the same URL, so
they automatically receive the lighter-weight derivative with no code
changes on their side.

- SVGs, GIFs (static or animated), animated WebP/APNG, and images already
  at or below 1728px are not optimized — the original is served as-is
  (never upscaled or duplicated).
- If derivative generation fails, the original is unaffected and the
  upload still succeeds; that attachment simply keeps serving the
  original until a derivative is generated.
- The derivative is a best-effort display cache, not durable data — the
  original's Exif/GPS metadata is preserved unchanged. Metadata is only
  stripped from the derivative.

Right-clicking an image embedded in a page body and choosing "Save
image as…" saves this optimized derivative, not the original. To get an
unmodified original, use the "Open original" link in the attachment
detail modal, or open `/api/attachments/<id>/original` directly.

> **Tip**: Attachment delivery enforces the page's view permission. Even
> if someone knows an attachment's URL, the file is not delivered to a
> user who cannot view the owning page (a 404 is returned to hide its
> existence). `/original` enforces this same page-view check, plus one
> more requirement the canonical URL does not have: it additionally
> requires the `attachments:read` scope, so a token scoped without it can
> still fetch the canonical delivery URL but not `/original`.

### The "All attachments" page

`/_attachments?pageId=<id>` opens the dedicated listing for a page,
split into two sections:

- **Used in the latest revision** — files actually embedded in the
  current page content.
- **Used only in past revisions** — files no longer referenced by the
  latest revision but still present in older history entries (or
  orphaned by edits).

This view is useful when you need to inspect or clean up attachments
that the page footer no longer surfaces.

### Images in the page body

To display an image inside the Markdown body, reference the attachment's
URL with image syntax.

```markdown
![Screenshot](/api/attachments/64f0a1b2c3d4e5f6a7b8c9d0)
```

Besides typing the URL by hand, uploading directly into the editor via
**paste** or **drag-and-drop** (below) automatically inserts the image
syntax for you.

> **Note**: Paste and drag-and-drop always insert a plain, attribute-less
> `![filename](url)` by default. Add a `{width= height= align= float=}`
> attribute block by hand afterward if you want to set the image's size,
> alignment, or text-wrap float (see [Writing Markdown](./markdown)'s
> "Image display attributes" section). Hovering over — or placing the
> cursor inside — an image's Markdown span in the editor also shows a
> tooltip with `width` / `align` / `float` controls.

## Uploading directly into the editor

On the page edit screen (`/_edit?page_id=<page ID>`), you can upload a
file by **pasting** it into the editor or **dragging and dropping** it.
The uploaded attachment is bound to the page you're editing, and its
Markdown syntax is inserted automatically at the cursor.

> **Note**: This only works inside the edit screen's editor. Uploading
> from the Attachments section in the page footer still works as
> described above.

### Pasting a file

Pasting a screenshot, an image copied from another app, or a file copied
from your OS file manager uploads it automatically.

- Images are inserted as `![filename](url)`, other files as
  `[filename](url)` — the same image-vs-link rule drag-and-drop follows.
- A pasted image has no filename of its own, so one is auto-generated as
  `pasted-<timestamp>.<ext>` (e.g. `pasted-1717891234.png`). A file
  copied from the file manager keeps its own name.
- While uploading, a placeholder `![Uploading pasted-1717891234.png
  (37%)…](#)` is inserted at the cursor, with the percentage updating
  live. Other members editing the same page collaboratively see this
  progress too.
- Once the upload finishes, the placeholder is replaced with
  `![pasted-1717891234.png](/api/attachments/...)`.
- Pasting the same image twice creates two separate attachments (there
  is no client-side de-duplication). Delete the extra one from the
  attachment list if you don't need it.
- The size cap for paste is **10 MB**.

Which files paste accepts is the **same unified allow-list** described in
"What file types can be uploaded" above — a `.docx` or an HTML file
pasted from the file manager uploads exactly as it would through the
Attachments button or drag-and-drop. Pasting a type not on the allow-list
shows the same `Files of type <MIME type> cannot be uploaded.` toast the
other routes show.

Whether the result is embedded as an image or linked is decided purely
by the file's type, independently of that allow-list: only images become
`![…](…)`.

> **Tip**: Copied *text* — including rich text carrying HTML formatting —
> is not a file, so it is pasted as text, not uploaded. For what happens
> when you paste text or a bare URL, see
> [Writing Markdown](./markdown) — pasting a URL is automatically
> converted into link syntax.

### Dragging and dropping files

Dragging a file over the editor highlights the drop target; dropping it
starts the upload at the cursor position.

- Images are inserted as `![filename](url)`, other files as
  `[filename](url)`.
- The progress-placeholder behaviour is the same as pasting.
- Dropping multiple files at once processes them **serially**, in the
  order the OS reports them, with one placeholder per file.
- The per-file limit is **50 MB**, and a single drop can carry at most
  **5 files**. Exceeding either limit shows a toast notification.

Drag-and-drop accepts the **same unified allow-list** described in "What
file types can be uploaded" above (images / PDF and text formats / Word,
Excel, PowerPoint and other office documents / archives / audio and
video). Drag-and-drop used to have its own narrower allow-list — images
plus PDF/txt/md/csv and zip — which rejected everyday business files like
`.docx`; it now applies the exact same check as the Attachments button. In
the current release this allow-list is fixed — there is no per-instance
setting for it.

Dropping a type not on the allow-list shows a toast: `Files of type <MIME
type> cannot be uploaded.` — the same wording the server returns for the
Attachments button and paste, so the message is identical no matter which
route rejected the file.

> **Note**: `application/octet-stream` (unknown type) is on the allow-list
> already, so it is accepted. When the OS reports no MIME type at
> all (an empty string), the file is treated as that unknown type — the
> same normalisation the server applies — and therefore accepted too.
> What gets **stored** is not necessarily `application/octet-stream`
> though: a file that arrives with no usable type has its type filled in
> from the filename extension by the server (see "Content types on
> delivery" above).

> **Note**: When the edit screen is in **read-only mode** (the
> simultaneous-editor cap was reached, or you lack edit permission —
> see [Realtime collaborative editing](./realtime-editing)),
> drag-and-drop is disabled and a permission toast is shown instead.

### When an upload fails

If an upload fails (a network disconnect, a permission error), the
progress placeholder is **removed from the body** and the reason is shown
in a toast notification. No broken Markdown is left behind, so you can
simply paste / drop again.

## Removing an attachment

Removal happens from inside the **detail modal** — there is no inline
delete button on each tile. Click an attachment to open its modal, then
remove it from there. Removing an attachment deletes both the
`Attachment` document and the actual file in storage.

**Any user who can view the owning page** can remove an attachment. Like
the page body, attachments are treated as collectively editable by the
team — removal is not restricted to the uploader or to administrators.

The page's grant check still applies, so you cannot remove an attachment
on a page you are not allowed to view (a 404 is returned to hide its
existence).

## Compatibility with legacy URLs

Crowi 1.x URLs of the form `/files/:id` are 302-redirected to the new
delivery endpoint `/api/attachments/:id`. Attachment URLs embedded into
page bodies before the migration keep working, so there is no need to
rewrite older pages.

## When a page is permanently deleted

When a page is permanently deleted from the trash, the attachments linked
to that page are deleted as well, including their storage objects. See
[Trash](./trash) for details.
