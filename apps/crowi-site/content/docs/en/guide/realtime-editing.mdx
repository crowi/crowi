---
title: Realtime collaborative editing
description: How to use Crowi's realtime collaborative editing feature
---

Starting with Crowi 2.0, the page edit screen (`/_edit?page_id=<pageId>`)
operates in realtime collaborative mode. Like Google Docs, you can see
other people's cursors and selections, and edits propagate to other
participants within a few hundred milliseconds.

For deployment instructions, see [Operating realtime collaborative
editing](../operations/realtime-collab).

## Live updates while viewing a page

When someone saves a page you are **reading**, its body is swapped to
the latest revision automatically, without a reload
([RFC-0003](https://github.com/crowi/crowi/blob/main/docs/rfcs/0003-realtime-collaborative-editing.md)
read-side soft-refresh). You do not need the editor open — simply
viewing the page keeps you on the latest content.

- The swap happens with **no full reload and no spinner**, and your
  scroll position is preserved (corrected when the height changes).
- At the same time a fixed banner appears at the top-center of the
  screen: **"\<name> updated this page — Showing the latest version"**
  (where `<name>` is the person who saved).
- Clicking **"Read the version you were reading"** in the banner
  returns you locally to the version you had before the swap (no URL
  change, no extra network request). The banner switches to "Showing
  the version you were reading", and **"Show the latest"** brings you
  back to the newest at any time. If an even newer save arrives while
  you are on the old version, the banner changes to "\<name> saved an
  even newer version".
- Both REST saves and collaborative saves (checkpoints) trigger it
  equally.
- It also reaches viewers connected to a different instance in a
  multi-instance deployment (`REDIS_URL` configured).

### When it does not happen (limits)

- **Your own saves** never trigger a swap or a banner. If the same
  user edits and saves from another tab, the reading tab is likewise
  not auto-updated (your own change is assumed to be already known).
- **Viewing a past revision** (a specific version opened via
  `?revision_id=`) and **draft pages** do not receive live updates.
- A burst of rapid saves is coalesced into a single swap.

## Live comment display

When **someone else posts a comment** on a page you are reading, it is
appended to the comment list automatically, without a reload. This is a
sibling of the live body soft-refresh: it rides the same `/presence`
channel, but the target is the comment list rather than the body.

- A newly-arrived comment gets a **background highlight that fades after
  a few seconds** (the same amber as the section highlight when you jump
  to a heading in the body), so you can tell at a glance which comment
  just arrived.
- When someone **deletes** a comment, it disappears from your list too,
  so the list always stays correct.
- **Your own posts** never trigger the auto-append or the highlight —
  your own action already updated the list.
- The comment body never rides the presence channel. Only a "a comment
  changed" notification is delivered; the client then re-fetches the
  comment list from the permission-checked API. A private page's comment
  text never leaks to a viewer's WebSocket.
- It also reaches viewers connected to a different instance in a
  multi-instance deployment (`REDIS_URL` configured).

### When it does not happen (limits)

- **Viewing a past revision** (a specific version opened via
  `?revision_id=`) and **draft pages** do not receive live comment
  updates — the presence socket is not opened, exactly as with the live
  body soft-refresh.
- The header's "N comments" count chip is not updated instantly by this
  live display (it refreshes the next time you open the page).

## Save is an explicit checkpoint

Crowi uses an **explicit-save model**: pressing the "Save" button is
what creates a new revision.

- While you type, your text is shared live with other editors, but
  it is *not yet committed as a revision*. It exists only as a
  transient Yjs state on the server.
- The moment you click **Save** (bottom-right), a checkpoint is taken
  and the current body is persisted as a new `Revision`.
- There is **no autosave**. Save explicitly when you reach a meaningful
  checkpoint.
- The `Ctrl + S` / `Cmd + S` keyboard shortcut is intentionally not
  wired up in v2.0 — it would conflict with the browser's "Save page"
  dialog.

> **Tip:** treat each save as a milestone worth recording in the
> history. The cleaner your save cadence, the easier it is to scan
> the revision list later.

## Contributors

Every saved revision records two kinds of editor information:

- **`savedBy`**: the user who clicked the Save button.
- **`contributors`**: every user who was **present in the same edit
  session** (visible via Yjs awareness) at the time of the save.

"Present" means the page was open in their browser with awareness
broadcasting — they do not have to have typed anything. This is how
Crowi attributes joint editing sessions: anyone who joined the
collaborative session is credited on the resulting revision.

In the **revision history list**, savedBy and contributors are
combined like this:

```
Alice (with Bob, Carol)  · 5 minutes ago
```

Read this as "Alice saved the revision, while Bob and Carol were
in the editing session with her." When there are no other
contributors (solo editing), only `Alice` is shown.

## 20-editor cap per page

Each page allows up to **20 simultaneous editors** by default.

- A 21st editor opening the same page is placed into **read-only
  mode**, and a banner appears explaining that the per-page limit
  has been reached.
- Read-only mode still receives **realtime updates**, so the 21st
  user can watch the discussion in real time.
- When someone within the cap leaves, reloading the page may admit
  the waiting user (there is no explicit queue — slots are first-come).

Administrators can adjust this limit via the
`COLLAB_MAX_EDITORS_PER_PAGE` environment variable (see the operator
guide).

## Disconnecting and reconnecting

What happens when your network drops:

- An **"Offline"** toast appears at the top of the page.
- Local edits in the editor are **preserved** while offline — Yjs
  keeps accumulating deltas locally.
- When the connection comes back, a **"Reconnected"** toast appears,
  your buffered deltas are sent to the server, and you receive any
  delta you missed from peers.
- The Save button is disabled while offline (we cannot send the save
  request). Click it after reconnecting.

If you have been offline for a long time, the server-side Y.Doc may
have diverged significantly. You may see noticeable churn for a few
seconds while your delta is replayed and remote updates catch up.
If the editor still looks wrong, reload the page.

## Force-reload dialog

If an administrator edits the body directly through a CLI tool (for
example after a `crowi-admin renderer:rebuild` consistency recovery
or a data-repair operation), a dialog appears: **"This page was
modified externally. Please reload."**

- Clicking OK reloads the page and pulls in the latest server-side
  state.
- This dialog only appears when the server's `Page.yjsState` was
  reset or invalidated by an external action and your edit session
  cannot continue. It does not appear during normal use.
- Trying to keep editing after dismissing the dialog will most
  likely fail to save. Reload the page.

## Revision history view

The page's **Revisions** tab lists every saved checkpoint in a
table similar to this:

| Editor | When | Note |
| ------ | ---- | ---- |
| Alice (with Bob, Carol) | 5 minutes ago | (empty) |
| Alice | 1 hour ago | (empty) |
| Bob (with Alice) | Yesterday 14:30 | (empty) |

The `(with …)` segment is the contributor list. It gives a glance at
who else participated in each editing session, even if they did not
trigger the save themselves.

Revision diff and rollback work the same way as in earlier Crowi
versions.
