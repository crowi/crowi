`@crowi/cli` is the **end-user command-line tool** for Crowi. It ships via
`npm i -g @crowi/cli` and is invoked as `crowi`. It talks to your wiki over HTTP
only (it never touches the database) and uses OAuth to act **as you** — search,
read, create, and edit pages from the terminal.

<Callout title="Not the same as the operator admin-cli">
  `@crowi/cli` (`crowi`) is for end users acting with their own permissions over
  HTTP. It is a different tool from `@crowi/admin-cli` (`crowi-admin`), which
  connects directly to MongoDB for operator tasks.
</Callout>

## Install

```bash
# global install
npm i -g @crowi/cli
crowi --version

# one-off (no install)
npx @crowi/cli --help
```

Node.js 18+ is required.

## Authentication

`crowi` is a **public OAuth client** and uses PKCE (no client secret). Tokens
are stored as JSON at `~/.config/crowi/contexts.json` (honouring
`$XDG_CONFIG_HOME`), written with file mode `0600`.

The login URL is the **public origin** of the target Crowi (the OAuth issuer —
usually the host that serves the web app). There are three flows:

```bash
# 1. browser authorization-code + PKCE over an ephemeral loopback redirect
#    (the default — opens your system browser)
crowi login https://wiki.example.com

# 2. device authorization grant for headless / SSH sessions (also chosen
#    automatically when no browser is detectable)
crowi login --device https://wiki.example.com

# 3. store a pre-issued personal access token (PAT) directly (no OAuth round-trip)
crowi login --token <pat> https://wiki.example.com
```

Issue a personal access token under **Settings → Password / API tokens /
Linked accounts**, choosing its scopes and expiry ([Account and
security](./account-security)).

Check your session with `crowi whoami` (shows the signed-in user and active
scopes). `crowi logout` revokes and removes the tokens.

## Scopes

The default scope is `pages:read pages:write`, which covers reading, writing,
renaming, deleting, and watching pages plus `whoami`. Commands that work with
comments, attachments or bookmarks need their own scope granted at login; the
command table in [crowi CLI](../reference/cli) lists which needs what.

`--scope` **replaces** the default set, so include `pages:read pages:write` if
you still want the page commands — or request the umbrella `read write`, which
the server expands to every issuable `*:read` / `*:write`:

```bash
crowi login https://wiki.example.com --scope "pages:read pages:write comments:read comments:write"
crowi login https://wiki.example.com --scope "read write"   # everything issuable
```

`--scope` is validated against the server's issuable catalog before any request
leaves your machine, so a typo — or an admin scope, which is never issuable to a
token — fails fast. No CLI command needs an admin scope.

### Running a command without the scope it needs

There is no pre-flight check — the command makes the real API call. If the scope
is missing, the server returns `403 INSUFFICIENT_SCOPE` and the CLI turns it into
an **actionable hint** and exits non-zero (code `3`):

```console
$ crowi comment add /onboarding -m "looks good"
crowi: your token lacks the required scope — re-login granting it: `crowi login --scope "comments:write"`
```

No crash, no silent failure — it tells you which scope is required and how to
re-login.

## Profiles (multi-endpoint / multi-account)

Use named profiles to work across several Crowi servers / accounts (the same
model as `gh` / `kubectl` contexts). Tokens are stored **per endpoint**.

`-p, --profile <alias>` can go **either before or after** the command name,
on every command. Once it's after the command name, it can also go either
before or after a positional argument like `<url>` (it's an independent
option, not tied to `login`'s argument position). When given on both sides
of the command name, the command-side value wins:

```bash
# after the command name, after the argument (the natural reading order)
crowi login https://wiki.almoha.net --profile almoha
crowi login https://strk-wiki.example.com --profile p2b

# after the command name, before the argument — same meaning
crowi login --profile almoha https://wiki.almoha.net

# before the command name (the classic global-option form)
crowi --profile almoha search "release notes"

crowi profiles            # list configured profiles (local; no network)

# given on both sides: the command-side value ("new") wins
crowi --profile old login https://wiki.example.com --profile new
```

The active profile resolves from `--url` / `--token`, then `--profile` /
`$CROWI_PROFILE`, then the stored current profile.

### Switching the current profile

If you don't want to pass `--profile` every time, `crowi profiles use
<alias>` switches the current profile (the default used when `--profile` is
omitted):

```bash
crowi profiles use almoha
crowi search "release notes"   # runs against almoha, no --profile needed
```

An unknown alias leaves the config file untouched, prints `crowi: no such
profile: <alias>` to stderr, and exits with code `4`. `crowi profiles`
prints a hint on stderr showing how to switch (suppressed by `--quiet`; the
`--json` output shape is unaffected either way).

## Commands

The subcommands, their own flags and the scope each needs are listed in
[crowi CLI](../reference/cli). Arguments are validated against the matching
API request schema before anything is sent, so a malformed path fails locally
with a clear error instead of after a round trip.

### `edit` conflicts (409)

`edit` / `update` send the page's `revision_id` for optimistic locking. If the
page changed while you were editing, the write **aborts by default** with exit
code `5` (conflict) — it never silently clobbers. Re-run with `--force` to
overwrite the newer revision.

### Downloading attachments

`attach list <path-or-id>` prints the attachment id at the start of each row. Pass that id to `attach download` to get the bytes.

```bash
crowi attach list /docs/spec
# 6650f0c1a2b3c4d5e6f70123  design.pdf  /api/attachments/6650f0c1a2b3c4d5e6f70123

crowi attach download 6650f0c1a2b3c4d5e6f70123 -o design.pdf
crowi attach download 6650f0c1a2b3c4d5e6f70123 > design.pdf   # stdout when -o is omitted
```

Without `-o` the bytes go to stdout (writing them straight to a terminal is refused, since binary corrupts the display). Progress and confirmation messages go to stderr, so nothing but the file itself ever reaches a redirect or a pipe.

The delivery route an embedded `<img>` reads answers a missing attachment with a placeholder image and a `200`. That keeps browsers from showing a broken image, but for a client extracting a file it means happily saving something that is not the attachment. `attach download` uses a dedicated route that returns `404` (exit code `4`) both when the record is gone and when its stored file is gone, so a saved file is always the real thing.

### Uploading attachments

Before sending anything, `attach add <path-or-id> <file>` **asks the server what it accepts** (`GET /api/attachments/upload-policy`). The server answers with the MIME types it will store, an extension-to-MIME table, and the size ceiling for each upload route. The CLI uses that for two things: to decide which `Content-Type` to declare for the file's extension, and to reject an upload that cannot succeed before it goes out. You no longer push a large file across the wire only to be handed a `413`.

A locally rejected upload exits `6` (invalid) and says why on stderr:

```
upload rejected: video.mkv has type application/octet-stream, which this server does not accept for attachments
```

The policy is cached on the profile for ten minutes, so this is not a round trip on every invocation. **A server old enough not to have the endpoint** answers `404`, and the CLI falls back to its bundled extension table — you lose the pre-flight check, nothing else.

## Output formats & scripting

`search` and `ls` can shape their output with `--format` / `--template`, which
makes them pipe well. The accepted values and the exit codes are listed in
[crowi CLI](../reference/cli).

```bash
# tab-separated path + score, one hit per line
crowi search "release notes" --template '{{path}}\t{{score}}'

# feed search results straight into a fetch (get reads a path from stdin with -)
crowi search onboarding --template '{{path}}' | head -1 | crowi get - > onboarding.md
```

Progress and warnings all go to stderr, so the stdout of `--json` stays clean
for scripts.

## Shell completion

```bash
# bash
eval "$(crowi completion bash)"
# zsh
crowi completion zsh > "${fpath[1]}/_crowi"
# fish
crowi completion fish > ~/.config/fish/completions/crowi.fish
```

## Version skew against the server

Crowi is self-hosted, so `crowi` and the server it talks to can be on different versions. The CLI never refuses a command over that.

When the server's API differs from what this CLI expects, it prints a one-line note and carries on; a feature the server does not have (`search` with no search backend configured, say) reports "not available on this server".
