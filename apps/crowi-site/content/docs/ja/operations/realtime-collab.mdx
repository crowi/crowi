Crowi 2.0 のリアルタイム共同編集機能は、Hocuspocus を `@crowi/api`
プロセス内にライブラリとして同居 attach する構成で出荷されています。
別プロセスや別ポートを起動する必要はなく、既存の api コンテナを動かせば
そのままリアルタイム共同編集が有効になります。

設計の詳細は [RFC-0003](https://github.com/crowi/crowi/blob/main/docs/rfcs/0003-realtime-collaborative-editing.md)
を、利用者向けの使い方は [リアルタイム共同編集](../guide/realtime-editing) を
参照してください。

## 概要

- Hocuspocus は `packages/api/src/collab/attach.ts` 経由で api プロセスの
  `http.Server` に `ws noServer` モードで attach されます。
- WebSocket エンドポイントは `wss://<crowi-host>/collab/:pageId?token=…` で、
  api と同じホスト・ポートを使います。リバースプロキシで別プロセスに
  振り分ける必要はありません。
- マルチインスタンス構成では `@hocuspocus/extension-redis` が
  `REDIS_URL` 設定時に自動 attach され、Yjs アップデートを Redis pub/sub
  で全レプリカへ伝搬します。スティッキーセッションは不要です。
- ページ単位の同時編集者上限 (デフォルト 20) は Redis カウンタで管理され、
  クラスタ全体で正しくカウントされます。

## シングルインスタンスデプロイ

最小構成は api + web + MongoDB の 3 サービスです。

```yaml
# docker-compose.yml (抜粋)
services:
  api:
    image: ghcr.io/crowi/api:2.0
    environment:
      MONGO_URI: mongodb://mongo:27017/crowi
      WS_TOKEN_SECRET: ${WS_TOKEN_SECRET}
      CROWI_ENCRYPTION_KEY: ${CROWI_ENCRYPTION_KEY}
      # REDIS_URL はシングルインスタンスでは任意。7 つの消費者の内訳は
      # 後述の「Redis 接続数の見積もり」を参照
      REDIS_URL: redis://redis:6379
    ports:
      - "3000:3000"
  web:
    image: ghcr.io/crowi/web:2.0
    environment:
      NEXT_PUBLIC_API_URL: https://crowi.example.com
    ports:
      - "3001:3000"
  mongo:
    image: mongo:7
```

このとき:

- `REDIS_URL` はシングルインスタンスでは省略可ですが、7 つの消費者は
  未設定時の退行の仕方が一様ではありません。
  - 共同編集 pub/sub (extension-redis は attach されません)・プレゼンス
    fan-out・通知 invalidation・設定同期は**レプリカ間の連携**専用の
    ため、単一インスタンスでは連携先自体が存在せず、実質的に no-op で
    何も失われません。
  - 編集者上限カウンタは Redis なしでは **fail-open** になり、21 人目
    以降を弾く代わりに `COLLAB_MAX_EDITORS_PER_PAGE` の強制自体を止め
    ます (詳細は[障害時の挙動](#障害時の挙動-failure-modes)) — これは
    意図的な degrade-safe な選択であり no-op ではありません。
  - rate limiting はプロセス内メモリの window にフォールバックする
    ため単一インスタンスでも動作は継続しますが、レプリカ間での共有は
    できません。
  - LRU (最近見たページ) にはフォールバックがなく、`REDIS_URL` 未設定
    ではシングルインスタンスかどうかに関わらずこの機能自体が使えません。
- ブラウザは `NEXT_PUBLIC_API_URL` から `/collab/` への WebSocket URL を
  自動導出するため、`NEXT_PUBLIC_COLLAB_URL` の指定は不要です。
- `WS_TOKEN_SECRET` はシングルインスタンスでは省略可です — 未設定のまま
  でもプロセスごとにランダム鍵が生成され (起動時に警告ログ)、1 レプリカなら
  無害です。api ノードを 2 台以上に増やすときにのみ `CROWI_MULTI_INSTANCE`
  とあわせて設定してください。

## マルチインスタンスデプロイ

api を複数レプリカで運用する場合の追加要件:

1. **`REDIS_URL` を全レプリカで同じ Redis に向ける** — extension-redis が
   自動 attach され、レプリカ間で Yjs アップデートが pub/sub されます。
2. **`CROWI_MULTI_INSTANCE` を宣言し、`WS_TOKEN_SECRET` を全レプリカで同一値に
   揃える** — wsToken は任意のレプリカで発行されて任意のレプリカで検証される
   ため、値がずれると接続が確立できません (詳細は
   [関連環境変数](#関連環境変数) 参照)。各レプリカに `CROWI_MULTI_INSTANCE=1`
   (またはレプリカ数) を設定すると、`WS_TOKEN_SECRET` が未設定 (または
   プレースホルダ) のままだと api は**起動時にエラーで停止**します
   (プロセスごとのランダム鍵では他レプリカが wsToken を検証できないため)。
   シングルインスタンス構成 (`CROWI_MULTI_INSTANCE` 未設定) では
   `WS_TOKEN_SECRET` 未設定でも起動できます。`REDIS_URL` の有無だけでは
   マルチインスタンスとは判定しません (Redis はシングルレプリカでも使われる
   ため)。
3. **スティッキーセッション不要** — クライアントは任意の api レプリカに
   接続できます。Yjs 更新は Redis pub/sub 経由で他レプリカへ即座に
   伝搬します。
4. **`Page.yjsState` が真実の源** — レプリカ全体の再起動時も MongoDB に
   永続化された yjsState から復元されます。Redis はライブのルーティング
   専用です。

> **重要 (データ消失リスク・推奨はシングルインスタンス)**: マルチインスタンス
> 構成には、まれにですが**編集内容が失われる**既知のリスクがあります。
> `extension-redis` はライブの pub/sub のみを担い、切断中レプリカの Y.Doc を
> 再構築しません。あるレプリカが古い `Page.yjsState` から Y.Doc を materialise
> し、その状態でチェックポイント (compaction) を書き戻すと、別レプリカが書いた
> 新しい状態を上書きしうるためです。compaction には**クロスインスタンスの
> ロックがありません** (cross-instance ロック + last-writer 調停は現時点で
> スコープ外)。`@crowi/collab` はこれを**サーバドキュメント保存ロック**で
> 緩和します。ページの revision ポインタは、ライブのサーバ側ドキュメントが
> materialise された revision を基底とする単一のアトミックな compare-and-set
> で前進させるため、別経路の編集 (または別レプリカ) がポインタを動かした後の
> 保存は `CONFLICT` で拒否され、クライアントは再読み込みします (`revision` と
> `currentRevision` が乖離することはありません)。自動チェックポイントには
> **desync ガード**を追加しています。非空ページに対して空ドキュメントを
> 書き込もうとするチェックポイント (= 読み込み失敗で materialise された
> ドキュメントの兆候) はスキップし、スキップ時は既存の状態と保留中デルタの
> 両方を保持するため編集は失われません。エディタからの意図的な削除は (ページの
> 全消去を含め) 明示的なユーザー操作として通常どおり保存されます (削除は短命の
> 行ではなく `Page.yjsState` に永続化されます)。これらにより single/multi
> 両方で最悪ケースを緩和しますが、**完全には防げません**。このため Crowi は
> 当面**シングルインスタンス (例: Lightsail 1 台) を推奨**します。マルチ
> インスタンスは同時編集の負荷分散が必要な場合のみ、このリスクを理解した上で
> 採用してください。

```yaml
# 2 instance 例
services:
  api:
    image: ghcr.io/crowi/api:2.0
    deploy:
      replicas: 2
    environment:
      MONGO_URI: mongodb://mongo:27017/crowi
      REDIS_URL: redis://redis:6379           # マルチ構成では必須
      WS_TOKEN_SECRET: ${WS_TOKEN_SECRET}     # 全レプリカで揃える
      CROWI_ENCRYPTION_KEY: ${CROWI_ENCRYPTION_KEY}
```

## リバースプロキシ設定

WebSocket の `Upgrade` ヘッダを api までフォワードする必要があります。

### nginx

```nginx
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}

upstream crowi_api {
    server api1:3000;
    server api2:3000;
    # マルチインスタンスでもスティッキー指定不要
}

server {
    listen 443 ssl http2;
    server_name crowi.example.com;

    # /api/v2/* と /collab を同じ upstream へ
    location /api/v2/ {
        proxy_pass http://crowi_api;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # 末尾スラッシュ無しの `/collab` も含む prefix match。HocuspocusProvider は
    # bare `ws[s]://<host>/collab` で接続し、page id は handshake 後の protocol
    # で送るため、`location /collab/` (末尾スラッシュ付き) だと bare upgrade が
    # マッチしません。`location /collab` (末尾なし) は `/collab` と `/collab/...`
    # の両方をカバーします。
    location /collab {
        proxy_pass http://crowi_api;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_set_header Host $host;
        proxy_read_timeout 3600s;   # 接続は長時間 keep-alive
        proxy_send_timeout 3600s;
    }

    location / {
        proxy_pass http://crowi_web:3000;
    }
}
```

### Traefik

```yaml
# docker-compose.yml の api service に
labels:
  - "traefik.enable=true"
  - "traefik.http.routers.crowi-api.rule=Host(`crowi.example.com`) && (PathPrefix(`/api/v2`) || PathPrefix(`/collab`))"
  - "traefik.http.services.crowi-api.loadbalancer.server.port=3000"
  # スティッキーセッション無効 (デフォルト)
```

ポイント:

- `/api/v2/pages/:id/yjs-token` (HTTP) と `/collab` (WebSocket。HocuspocusProvider
  が bare `/collab` で接続し、page id は protocol 経由で送る) を同じ api アップ
  ストリームに向ける必要があります。
- WebSocket 接続のアイドルタイムアウトは長め (1 時間程度) に設定して
  ください。長時間の閲覧/編集セッションが prematurely 切断されると
  ユーザー体験が悪化します。
- スティッキーセッションは**不要**です。

> **Note (Crowi 2.0 / RFC-0005)**: ページプレゼンス機能の WebSocket は
> `/presence/:pageId` に attach されており、`/collab/*` と**まったく同じ
> 構成**です。リバースプロキシでは `/presence` ロケーションを `/collab`
> と同じ要領で api アップストリームへ向け、`Upgrade` ヘッダを転送して
> ください (nginx なら上記 `location /collab` と同じブロックをパスだけ
> 変えて複製、Traefik なら `rule` の `PathPrefix` に `/presence` を追加)。
> プレゼンスのビューア状態とマルチインスタンス間の伝搬は `REDIS_URL` の
> Redis を共用します (専用の追加インフラはありません)。プレゼンスの
> WebSocket が届かない場合でも、ライブプレゼンス行が静かに隠れるだけで
> ページ閲覧自体には影響しません。

## 関連環境変数

| 変数名 | 必須 | 用途 |
| ------ | ---- | ---- |
| `WS_TOKEN_SECRET` | マルチでは必須 (全レプリカで揃える) | wsToken (短命 JWT) の HMAC 署名鍵。マルチインスタンス構成では全レプリカで**同じ値**を指定する必要があります。`CROWI_MULTI_INSTANCE` が設定されているのに `WS_TOKEN_SECRET` が未設定 (または既知のプレースホルダ) の場合、api は**起動を中止**します (プロセスごとのランダム鍵では他レプリカが検証できないため)。シングルインスタンス (`CROWI_MULTI_INSTANCE` 未設定) では未設定でも起動でき、プロセス起動ごとにランダム生成され警告ログが出ます。同梱の `.env.example` は意図的に空にしています (世界中で既知の鍵をテンプレートに入れないため)。設定する場合は**最低 32 文字**必要です — 32 文字未満の値は `NODE_ENV=production` (未設定時のデフォルトも production 扱い) では起動時エラーで停止し、それ以外の `NODE_ENV` では起動ログの警告レポートに含まれます (既知のプレースホルダ値は対象外)。`openssl rand -base64 32` で生成してください。 |
| `CROWI_MULTI_INSTANCE` | いいえ (既定はシングル) | マルチインスタンス構成を宣言します (`1` / `true`、またはレプリカ数 `>= 2`)。`WS_TOKEN_SECRET` 起動ガードはこの値を基準に判定します (`REDIS_URL` の有無ではありません)。そのため Redis を rate limiting や編集者上限カウンタなどの用途のみに使う 1 レプリカ構成は共有鍵なしで起動できます。api ノードを 2 台以上に増やすときに全レプリカへ設定してください。 |
| `COLLAB_MAX_EDITORS_PER_PAGE` | いいえ (デフォルト `20`) | ページごとの同時編集者上限。21 人目以降は read-only でリアルタイム表示は受けられますが編集できません。 |
| `NEXT_PUBLIC_COLLAB_URL` | いいえ | ブラウザが WebSocket 接続する URL。未指定時は `window.location.host` + `NEXT_PUBLIC_API_URL` から `/collab/` を derive します。リバースプロキシで `/collab/*` を api 同居ホストに向けているなら設定不要。 |
| `REDIS_URL` | マルチでは必須 | 共同編集の pub/sub・編集者上限カウンタ・プレゼンス・通知 invalidation・設定同期・rate limiting・LRU (最近見たページ) のための連携用途。未設定時の挙動は次節参照。 |
| `CROWI_ENCRYPTION_KEY` | 推奨 | 機密 Config (OAuth secret 等) を AES-256-GCM で暗号化。共同編集には直接影響しませんが、`pnpm --filter @crowi/api crypto:gen-key` で生成して全レプリカで揃えてください。 |

## Redis 接続数の見積もり

api インスタンスあたりの接続数は、インスタンスのライフサイクル段階に
よって変わります(固定本数ではありません):

- **boot 完了直後** (共同編集セッションがまだ 1 つも開始していない状態):
  **6 本** — 共有クライアント 1 本 (編集者上限カウンタ・LRU・rate
  limiting・プレゼンスのハッシュ書き込み・通知 publish がすべて相乗り)
  + プレゼンス subscriber 2 本 + 通知 subscriber 1 本 + Config
  publisher/subscriber 2 本。
- **そのインスタンスで最初の共同編集セッションが開始した後**: **8 本**
  — 上記 6 本 + `@hocuspocus/extension-redis` が張る専用 `ioredis`
  pub + sub 接続 2 本 (`lazyConnect: true` のため最初のドキュメント
  読み込みまでは接続されません)。

例: 10 api レプリカ + 1 web レプリカの構成

- boot 直後: 10 × 6 = 60 接続。
- 全レプリカで共同編集セッションが 1 回でも開始された後: 10 × 8 = 80 接続。
- web 側からの直接 Redis 接続: なし (api 経由)。

デフォルトの `maxclients=10000` 内で十分まかなえますが、Redis Cluster や
ElastiCache の低リソースインスタンス (`cache.t3.micro` / `cache.t4g.micro`
等) では余裕を持って割り当ててください。

## 2 インスタンス smoke テスト手順

同梱の compose 構成から実 2 レプリカ環境を組みます。事前に 2 点だけ
準備が必要です: api の固定ホストポート公開の解除(レプリカ間で衝突する
— ブラウザはもともと `caddy` 同一オリジン proxy 経由)と、multi-instance
要件(全レプリカ共有の `WS_TOKEN_SECRET` + `CROWI_MULTI_INSTANCE` 宣言 —
宣言すると boot が secret の未設定を起動時エラーで弾いてくれます):

```bash
# 0. .env(env_file 経由で全 api レプリカが読む)に共有 secret を設定:
#    WS_TOKEN_SECRET=<`openssl rand -base64 32` の出力>

# 1. スケール用の最小 override — ホストポート公開を外し multi-instance を
#    宣言する(`!override` は Docker Compose v2.24.4+)
cat > docker-compose.smoke.yml <<'OVERRIDE'
services:
  api:
    ports: !override []
    environment:
      CROWI_MULTI_INSTANCE: "2"
OVERRIDE

# 2. api を 2 レプリカにスケールして起動
docker compose -f docker-compose.yml -f docker-compose.smoke.yml \
  --profile app up -d --build --scale api=2

# 3. 2 つの api コンテナが立っていることを確認
docker compose ps api
# crowi-api-1   Up   3000/tcp
# crowi-api-2   Up   3000/tcp

# 4. 両レプリカで extension-redis の attach を確認(identifier が 1 つずつ)
docker compose logs api | grep extension-redis
```

検証手順:

1. 2 つのブラウザウィンドウ (Chrome 通常 + シークレット、または異なる
   ブラウザ) で別ユーザーとしてログイン。
2. 同じページの `/_edit?page_id=<pageId>` を 2 ウィンドウで開く。
3. 一方で文字を入力 → もう一方にリアルタイムで反映されることを確認。
4. `caddy` 前段 proxy は Docker の DNS 経由で `api` サービスへ到達し、
   接続はレプリカ間に分散されます。api ログに接続単位のレプリカ識別子は
   出ない ため、「両レプリカが実際にトラフィックを担っていた」ことの
   確認は手順 7(片方を停止しても編集が継続する)を正とします。
5. **プレゼンス**: 2 ウィンドウとも同じページを開いたまま、お互いの
   ウィンドウのライブ閲覧者表示にもう一方のユーザーが表示されることを
   確認する — プレゼンス subscriber がレプリカ間で viewer 状態を Redis
   経由で伝搬していることの確認になる。次の手順でレプリカを停止すると
   残りは 1 レプリカだけになりレプリカ間の伝搬が確認できなくなるため、
   **この確認は次の手順より先に**行うこと。
6. **通知**: 一方のウィンドウからもう一方のユーザー宛の通知を発生させ
   (例: コメントでメンションする)、2 つのブラウザが別レプリカに
   振り分けられている状態でもリアルタイムで届くことを確認する — 通知
   subscriber のクロスインスタンス invalidation が Redis 経由で機能して
   いることの確認になる。同じ理由でこの確認も**次の手順より先に**行うこと。
7. 一方のレプリカを `docker stop crowi-api-1` で停止(`docker compose
   stop` はサービス単位でしか指定できない)→ 残ったレプリカに自動再接続
   し、編集が継続できることを確認。

## 障害時の挙動 (Failure modes)

- **起動成功後の Redis 障害**: クライアントの再接続ループが動き続け
  ます。新規 Yjs 更新はローカルの Hocuspocus engine 内では伝搬しますが、
  他レプリカへの pub/sub は途切れます。編集者上限 counter は
  **fail-open** (上限チェックを通す) に倒れます。Redis 復旧後は自動で
  pub/sub が再開します。
- **boot 時点で Redis に到達できない場合**: api は初回接続を有界化して
  います(約 10 回・数秒)。上限到達で `Redis connection failed.
  Continuing without Redis...` をログに出して Redis なしの縮退状態で
  起動します — このとき collab の Redis extension は**そもそも attach
  されない**ため、Redis が復旧してもクロスインスタンス pub/sub は自動
  では再開しません。復旧後に api を再起動してください。
- **`WS_TOKEN_SECRET` 不一致 / 未設定**: あるレプリカが発行した wsToken を別の
  レプリカが検証できず、`onAuthenticate` で reject されます。クライアントは
  WebSocket connect 後すぐに切断され、エディタが "接続できませんでした"
  状態のままになります。対処: 全レプリカで同じ secret を再設定して
  ローリング再起動。なお `CROWI_MULTI_INSTANCE` を宣言しつつ `WS_TOKEN_SECRET`
  を未設定 (または既知のプレースホルダ) にした場合、api は**起動時にエラーで
  停止**してこの問題を未然に防ぎます。シングルインスタンス構成
  (`CROWI_MULTI_INSTANCE` 未設定) は secret なしで問題なく起動します。これらの
  診断 (wsToken 検証失敗 / 編集者上限到達) は本番ログに**サンプリングされた警告**
  として出力されるため、"接続できませんでした" の真因 (期限切れ / secret 不一致 /
  クロック skew / 上限到達) を切り分けられます。
- **`WS_TOKEN_SECRET` が短すぎる (32 文字未満)**: 値は設定されているものの
  32 文字に満たない場合 (既知のプレースホルダは対象外)、`NODE_ENV=production`
  (未設定時のデフォルトも production 扱い) では api が起動時にエラーで停止します。
  エラーメッセージには変数名・現在の長さ・要求 (32 文字以上)・
  `openssl rand -base64 32` での生成方法が含まれます。`development` / `test`
  など production 以外の `NODE_ENV` では起動を止めず、他の env 検証と同じ
  起動時の警告レポートに 1 回まとめて出力されます。entropy や辞書のような
  推測的なチェックは行わず、文字数のみの単純なチェックです。
- **マルチインスタンスでの編集消失 (既知のリスク)**: 上記「マルチインスタンス
  デプロイ」の重要注記を参照。stale なレプリカが古い `Page.yjsState` から
  materialise した Y.Doc で compaction を書き戻すと、新しい状態を上書きしうる
  既知のリスクです。サーバドキュメント保存ロックと desync ガードで緩和されますが
  完全には防げず、シングルインスタンス運用を推奨します。
- **WebSocket Upgrade 失敗**: リバースプロキシで `Upgrade` ヘッダが
  落とされていると `/collab/` 接続が 400/426 で失敗します。`nginx` 設定で
  `proxy_set_header Upgrade $http_upgrade` を確認してください。
- **ライブ編集セッション中の外部編集**: 共同編集セッションが開いている
  ページに対して、REST API・MCP の `crowi_update_page`・プロセス内の
  `Page.updatePage` などの**外部経路**から本文が更新されると、Crowi は
  `currentRevision` を新しい revision に張り替え `Page.yjsState` を null に
  します。このとき**同一 api プロセス内**にライブな Y.Doc があれば、Crowi は
  保存コミット後にその Y.Doc を無効化します — 接続中の全クライアントへ
  `crowi:force-reload` を broadcast し、ドキュメントの基底 revision を
  tombstone して進行中の古い保存を `CONFLICT` で拒否し、短い猶予の後に
  ライブ接続を閉じます。これにより、先に reload したクライアントが古い
  ライブ Y.Doc に再アタッチして `CONFLICT` ループに陥ることを防ぎます。
  クライアント側は警告ダイアログを出してページを reload し、未保存の
  ローカル編集は復旧バッファから復元できます。次回接続時は新しい
  `currentRevision` の本文から再構築されます。
  - **既知の制約 (マルチインスタンス / プロセス外)**: 無効化のハンドルは
    **その api プロセス内**のライブ Y.Doc にしか届きません。**別レプリカ**で
    開いているライブ Y.Doc や、**プロセス外の書き込み** (DB を直接叩く
    admin CLI の `Page.updatePage` 等) には届かないため、マルチインスタンス
    構成では外部編集後に接続中クライアントが**古い内容のまま編集を続ける**
    可能性があり、**手動で再接続**するまで収束しません。クロスインスタンスの
    無効化チャネル (Redis pub/sub による全レプリカへの伝搬) は将来対応であり
    現時点ではスコープ外です (RFC-0003 §5b)。これも**シングルインスタンス
    運用を推奨**する理由のひとつです。
- **ライブ編集セッション中の rename / delete**([RFC-0017](https://github.com/crowi/crowi/blob/main/docs/rfcs/0017-collab-invalidate-on-rename-delete.md) Phase 1): 共同編集中のページが rename・
  soft delete・revert された場合、Crowi は Page モデル上の monotonic な
  epoch (`collabLifecycleVersion`) を該当ミューテーションと**同じ書き込み**
  で必ず進めます。この epoch は wsToken の発行時に署名され、接続の
  `onAuthenticate`・保存の atomic compare-and-set・checkpoint の書き込みの
  3 箇所で検証されるため、**rename / delete 前に発行されたライブ編集
  セッションからの保存は、マルチインスタンス構成でも(どのレプリカが
  rename / delete を行ったかに関わらず)確実に reject されます**。
  path や revision が変わらない rename のケースでも、epoch の不一致だけで
  古い保存を CONFLICT として弾けるのがこの仕組みの要点です — つまり
  **rename / delete に対する write-safety は Phase 1 の時点で既に
  cross-replica 安全**です。
  - **Phase 2 までの制約**: 一方で reload prompt (`crowi:force-reload`
    broadcast + 強制切断) は、この G1 の外部編集無効化と同様に
    **rename / delete を実行した api プロセス内のライブ Y.Doc にしか
    届きません**。別レプリカで開いているエディタは、reject された保存が
    `CONFLICT` エラーとして表示されるまで reload prompt を見ない可能性が
    あります(=書き込みは安全だが、通知の即時性はレプリカローカルに
    留まります)。クロスレプリカな prompt 配信 (Redis pub/sub での
    全レプリカへの伝搬) は Phase 2 の対応であり、本ドキュメント時点では
    未実装です。
- **`Page.yjsState` 破損**: `onLoadDocument` で yjsState の
  `Y.applyUpdate` が失敗した場合、Crowi は revision の Markdown 本文から
  Y.Doc を再構築し、接続中の全クライアントへ force-reload 通知を送ります。
  クライアント側は警告ダイアログを出してページを reload します。
- **`renderedAst` 不整合 (RFC-0002 連動)**: 共同編集の保存は
  `Revision.prepareRevision` を呼び出して renderedAst を自動再生成
  します。何らかの理由で `Page.body` と最新 `Revision.body` がずれた
  場合は、対象ページを通常どおり保存し直せば両方が再生成されます
  (一括再ビルド用の `crowi-admin rebuild renderer` は RFC-0008 で
  予定されていますが未実装です)。
- **api プロセスダウン**: 接続中の全クライアントが reconnect ループに
  入ります。ヘルスチェックで他レプリカへフェイルオーバーする構成なら
  クライアントは自動的に他レプリカへ繋ぎ直し、Y.Doc は MongoDB の
  yjsState から復元されます。

## Redis のライセンスとエンジンサポート方針

> このセクションはリアルタイム共同編集に固有のものではありません —
> このコードベースが Redis と通信する**全 8 経路**(共同編集 pub/sub・
> 編集者上限カウンタ・プレゼンス・通知 invalidation・設定同期・rate
> limiting・LRU (最近見たページ)・boot 接続そのもの)に適用される、
> Redis 全体のライセンス・エンジンサポート・セキュリティ方針です。
> Redis の要件・接続数見積もり・障害時の挙動を運用者がすでに読んで
> いるこのドキュメントに置いているだけで、共同編集専用の内容では
> ありません。

### ライセンスの事実とプロジェクト方針

- **確立事実**: Redis Open Source 8.0 以降、Redis プロジェクトは
  RSALv2・SSPLv1・AGPLv3 の3つのライセンスから選べる選択制になって
  います。このうち OSI 承認の open source なのは AGPLv3 のみです。
- **確立事実**: Crowi は Redis サーバー本体を一切バンドルしません。
  `@crowi/api`・`@crowi/web` はいずれも TCP 経由で Redis と通信する
  だけで、npm パッケージにも api/web の Docker イメージ
  (`packages/api/Dockerfile`・`packages/web/Dockerfile`) にも Redis
  バイナリは含まれません。
- **プロジェクト方針**: Crowi がテスト対象とするリファレンス構成は
  未改変のアップストリームイメージであり、その構成を3択のうち唯一
  OSI open source である AGPLv3 のもとで評価しています。(AGPLv3
  §13 のネットワーク越しソース開示義務は、ライセンシー自身が対象
  プログラムを改変していることが発火の前提条件です。Crowi の
  リファレンス構成は Redis を改変しないため、この構図には該当
  しません。)
- **プロジェクト方針**: `docker-compose.yml` や quickstart docs の
  `image:` はアップストリームイメージを参照するだけです。Crowi が
  Redis サーバー自体を改変・サブライセンス・再配布することはあり
  ません — compose ファイルでアップストリームイメージを参照する
  ことは、実際にイメージレイヤー・アーカイブ・バイナリをコピーする
  「バンドル/配布」とは別物です。
- **プロジェクト方針**: テスト済みの正確な patch バージョンと digest
  を記録し、`redis:7` のような moving tag は再現性が必要な運用者向け
  手順には使いません — 詳細は後述の「イメージ pin 方針」参照。本稿
  執筆時点で Docker Hub の `redis:7` タグはすでに RSALv2/SSPLv1
  選択制の Redis 7.4.x 系に解決されており、BSD-3-Clause ライセンス
  だった Redis 7.2 系ではありません — moving tag が通常のバージョン
  ドリフトとは別に、運用者が選んだ覚えのないライセンス境界を静かに
  越えさせうる具体例です。
- **プロジェクト方針**: Valkey は、Redis 8 自身が満たしたのと同じ
  基準をクリアするまでは BSD-3-Clause の best-effort な代替として
  扱います (詳細は後述の「Valkey」参照)。
- **運用者向け notice**: Redis 本体、および Redis 互換のマネージド
  サービス (ElastiCache・MemoryDB・Upstash 等) はいずれも独自の
  ライセンス/利用規約を持つ別製品です。それらの選定と遵守は Crowi
  ではなく運用組織の責任です。
- **非法的助言のフレーミング**: このセクションは Crowi の技術
  アーキテクチャとメンテナ方針の記録であり、法的助言ではありません。
  執筆時点の Crowi の理解を反映したものであり、専門家による法的
  助言の代わりにはなりません。Redis の再配布・改変・バンドル、
  またはマネージドサービスとしての提供を検討する場合は専門家に
  相談してください — Crowi 自身の利用パターン (未改変のアップ
  ストリームサーバーとネットワーク越しに通信するだけ) はこの問いに
  答える必要がありませんが、皆さんのケースは答える必要があるかも
  しれません。

> **スコープに関する注記であり、法的結論ではありません**: Crowi
> 自身のデプロイパターン — 未改変の Redis サーバーを Crowi の裏で
> ネットワーク越しに動かすだけ — は、RSALv2 の「third-party へ
> サービスとして提供する」制限が想定していると理解されている商用
> データベース・アズ・ア・サービスの提供とは異なり、素朴な自己
> ホスト利用に見えます。ただしこの解釈は確定した法的結論ではない
> ため、ここでは事実としてではなく Crowi の作業上の前提として
> 記載しています。

### Valkey

Valkey は Redis の BSD-3-Clause フォークですが、現時点では**正式
サポートはしておらず** best-effort 扱いです。Crowi は共同編集
pub/sub・編集者上限カウンタ・プレゼンス・通知 invalidation・設定
同期・rate limiting・LRU・boot 接続の8経路をカバーする実 Redis 8
互換性 smoke テスト一式を、CI 上で Valkey に対しては実行していません。
この8経路の smoke テスト一式が Valkey に対しても CI で継続的に通る
ようになった時点で — Redis 8 自身が満たしたのと同じ基準で — 正式
サポートへ昇格します。

### イメージ pin 方針

- ドキュメント上の互換範囲は **`>=8.0 <9`** です。これはテスト・
  サポート対象のバージョン範囲を示す運用者向けの明示的な方針で
  あり、ランタイムで強制されるものではありません。Crowi はコード上
  で Redis 7 系の接続を拒否しません。
- `docker-compose.yml` と CI は、レビュー済みの1つの patch タグを
  digest 付きで pin しています:
  `redis:8.8.0@sha256:234c902a2db49461a129e2d4aeff85b28cf20187ed274a67f6e50995fa713c7b`。
  `redis:7`・`redis:8`・`redis:latest` のような moving tag は使い
  ません。
- 実際に CI/compose が継続的に exercise するのは、この pin された
  1つのパッチタグのみです。`>=8.0 <9` はサポート対象として明示して
  いる範囲であり、その範囲内の全パッチ/マイナーバージョンを個別に
  検証したという主張ではありません。

### 複数レプリカでの移行とロールバック

- **標準手順は協調的な drain/restart です**。全レプリカを揃えて
  停止し、全レプリカの `REDIS_URL` を新しいエンドポイントへ切り替え
  てから、揃えて再起動します。Redis の pub/sub は分散排他制御を
  提供しないため、**レプリカが異なる Redis サーバーを向いたまま
  同時稼働する構成 (「split-brain」) は明示的に禁止**します — この
  構成は派手に失敗するのではなく、レプリカ間の fan-out (共同編集・
  プレゼンス・通知・設定同期) が2つの断絶したグループへ静かに分裂
  するだけだからです。
- **ベンダーサポートのオンライン昇格** (マネージドなレプリカ昇格や
  blue-green 切替など) は、**お使いの Redis ディストリビューション
  が実際に 7→8 のトポロジ変更をその方法でサポートすると確認できた
  場合にのみ**利用してください — Crowi 自身のツールはこれを検証
  しません。
- **RDB のクロスエンジン可搬性は保証しません**。Redis が書き出した
  RDB スナップショットを Valkey が読み込める (またはその逆) という
  前提を置かないでください。
- **ロールバック時は再接続前に stale なコーディネーション state を
  クリアします**。編集者上限カウンタのキー
  (`crowi:collab:editors:<pageId>`、24 時間 TTL) やプレゼンスの
  ハッシュ (`crowi:presence:viewers:<pageId>` /
  `crowi:presence:editing:<pageId>`) は、切替前のインスタンスに
  残存することがあります。これをクリアせず全レプリカを再接続すると、
  stale なソケット ID が新しい接続と混在し、編集者上限カウンタが
  実際より高い数値を報告して editor が意図せず read-only になったり、
  プレゼンスに短命な幽霊 viewer が表示されたりし得ます。標準手順:
  1. 全レプリカが旧エンドポイントから drain 済み (既存 WebSocket
     接続が閉じ、新規接続が旧エンドポイントを向いていない) である
     ことを確認する。
  2. ロールバック先を**新規に立てた、または `crowi:` prefix の
     キーをクリアした**空の Redis インスタンスにする。
  3. 切替後、編集者上限カウンタの `peek()` とプレゼンスの viewer
     リストが実際の接続数と一致することを確認してから、運用
     トラフィックを戻す。

  8経路のいずれも Redis にページ本文を保持しません — `Page.yjsState`
  を含むページ本文の真実の源は MongoDB のみです。したがって、これら
  Redis インスタンスのコールドスタートはページ本文のデータ消失を
  意味しません — [障害時の挙動](#障害時の挙動-failure-modes) 参照。
  ただし、各消費経路が Redis 上に持つ状態が同じように「消えても
  問題ない」わけではありません: 共同編集 pub/sub・プレゼンス・通知
  invalidation・設定同期はレプリカ間連携専用でコールドスタートで
  失うものはありません。編集者上限カウンタと rate limiting は
  意図的に fail-open / インメモリ window へのフォールバックとして
  リセットされます。LRU (最近見たページ) だけはフォールバックが
  なく、コールドスタートでそのリストを完全に失います — 消費経路
  ごとの内訳は[シングルインスタンスデプロイ](#シングルインスタンスデプロイ)
  参照。

### 見直しトリガー (re-review triggers)

以下のいずれかが発生した場合はこの方針を見直してください (詳細な
内部設計レビューを6カテゴリに要約したものです):

1. Crowi が Redis イメージ自体を fork・改変・ミラー・バンドルする
   ようになった場合。
2. Crowi が RESP をエンドユーザーへ直接公開する、または Redis 自体
   の機能をサービスとして販売・提供するようになった場合。
3. Redis が別プロセス/別サービスのままではなく、単一プロセス統合や
   共有メモリなど、プロセス境界を越える結合に変わった場合。
4. Redis 自体のライセンス・公式イメージの内容・バージョンポリシー
   が変わった場合。
5. クライアントライブラリ (`node-redis`・`ioredis`・
   `@hocuspocus/extension-redis` 等) のライセンスが変わった場合。
6. Valkey を正式サポートへ格上げする、または現在使っていない Redis
   モジュールを新たに使うようになった場合。

### セキュリティ運用ガイド

> このガイドは執筆時点の実コードとアップストリームライブラリの
> ソースを精査して導いたものです。**CI で検証済みの契約ではあり
> ません** (詳細は後述の「CI が検証していること/していないこと」
> 参照) — `redis`・`ioredis`・`@hocuspocus/extension-redis` を更新
> した際は、発行されるコマンドがバージョン間で変わりうるため、
> 再確認してください。

**Transport / 認証情報**: `rediss://` と `REDIS_REJECT_UNAUTHORIZED`
のデフォルト (証明書検証 有効) を維持してください。検証無効化は、
明示的に制御された開発環境や private CA のシナリオに限定してくだ
さい。credential は環境変数か secret manager に保持し、Config の
平文フィールドやログには書かないでください。

**ネットワーク露出**: Redis は Crowi と内部インフラからのみ到達
可能にしてください。認証なしで公開ネットワークへ露出させないで
ください。

**ACL コマンド/キー/チャンネルの手引き**: 制限付き ACL ユーザーを
作る場合、以下のすべてを許可しないと、「未対応機能」としてのきれい
な失敗ではなく、共同編集の保存などが permission エラーで失敗し
始めます:

| 消費経路 | コマンド | キー / チャンネル |
| --- | --- | --- |
| 共同編集 pub/sub | `SUBSCRIBE`, `UNSUBSCRIBE`, `PUBLISH` | `crowi:collab:<documentName>` — ドキュメントごとの単一チャンネル。Y.Doc の同期と awareness の更新はいずれもこの1チャンネル上に多重化される (`:awareness:` / `:y-update:` のような個別サブキーはない) |
| 編集者上限カウンタ | `SADD`, `SCARD`, `SREM`, `EXPIRE` | `crowi:collab:editors:<pageId>` |
| プレゼンス | `HSET`, `HGET`, `HGETALL`, `HDEL`, `EXPIRE`, `PUBLISH`, `SUBSCRIBE` | `crowi:presence:viewers:<pageId>`, `crowi:presence:editing:<pageId>`, `crowi:presence:updates`, `crowi:presence:page-updated`, `crowi:presence:comment-changed` |
| 通知 invalidation | `PUBLISH`, `SUBSCRIBE`, `UNSUBSCRIBE` | `crowi:notifications:user:<userId>` |
| 設定同期 (Config) | `PUBLISH`, `SUBSCRIBE` | 固定チャンネル `config` |
| rate limiting | `INCR`, `PEXPIRE` | `crowi:ratelimit:<name>:<userId>:<window>` |
| LRU (最近見たページ) | `ZREMRANGEBYRANK`, `ZADD`, `ZRANGE`, `MULTI`, `EXEC` (書き込み 2 コマンドは `MULTI`/`EXEC` トランザクション内で発行 — この 2 つを欠く ACL では LRU の書き込みが失敗する) | 運用者が選ぶ namespace キー (固定の `crowi:` prefix なし) |
| boot 接続 | 接続確立コマンドのみ | なし |

見落としやすい、もう2種類のコマンド発行元があります (いずれも
Crowi 自身のコードが直接発行するものではありません):

- **クライアントライブラリが接続時に発行するコマンド**: node-redis
  (共有クライアント `crowi.redis`) は接続のたびに `CLIENT SETINFO`
  (`LIB-NAME`/`LIB-VER`) を送ります。ioredis (共同編集用の pub/sub
  専用クライアント2本) は ready check として `INFO` を実行します。
  ACL でこれらを拒否しても接続が即座に壊れるとは限りません —
  ioredis は `INFO` が `NOPERM` で失敗した場合、warning を出して
  ready check をスキップするだけですし、node-redis は permission
  denied の `CLIENT SETINFO` エラー応答を無視します (`ErrorReply`
  以外の無関係な失敗のときだけ connect の Promise を reject します)
  — とはいえ、この「壊れずに生き残る」挙動に頼らず、明示的に許可
  しておくべきです。
- **collab extension が内部で実行する upstream の Redlock**:
  `@hocuspocus/extension-redis` は**共同編集の保存のたびに**
  `@sesamecare-oss/redlock` 経由でクロスインスタンスの store lock
  を acquire/release します。これは `EVAL`/`EVALSHA` で
  Lua スクリプトを実行する形で行われます。Redis の ACL は Lua
  スクリプト**内部**から呼ばれるコマンドにもユーザー権限を要求する
  ため、ACL には `EVAL`/`EVALSHA` に加えて、スクリプト内部の
  `SELECT` (`pcall` 保護)・`EXISTS`・`SET`・`GET`・`DEL` (`pcall`
  保護) を対象キー `crowi:collab:<documentName>:lock` に対して
  許可する必要があります。**この行列を欠いた ACL は、Redis が
  有効な本番環境で共同編集の保存のたびに permission エラーを発生
  させます** — 保存は Crowi 自身の Mongo compare-and-set チェック
  ポイントに到達せず、編集はメモリ上に留め置かれたまま (次の
  debounce サイクルで再試行) 永続化されず、ACL を直すまで恒常的な
  エラーログ noise が出続けます。**この Redlock 自体は永続化を保証
  しません** — 複数インスタンス間で store の試行を直列化するだけ
  です。Redis の store hook (この Redlock を含む) が成功した**後**、
  Crowi 自身の Mongo compare-and-set チェックポイントが完了する**前**
  に Crowi プロセスが落ちた場合、保存できていない編集内容はクライア
  ントが再接続して Yjs が最後に永続化された Mongo の状態から再同期
  するまで失われる可能性があります。

**ACL のスコープはユーザーであってリスナーではない**: Redis の
ACL は**ユーザー**にスコープされるのであって、listen している
ポートにはスコープされません — 「TLS ポートだけを制限する」という
設計は成立しません。制限付き運用をしたい場合は、すべての listener
で `default` ユーザーを無効化またはパスワード保護し、Crowi の各
クライアント (共有 node-redis クライアントと collab の ioredis
クライアント) には常にスコープ済みの認証情報を明示的に使わせる
必要があります。`@all` のような広いカテゴリより、key/channel
パターンで絞った権限を優先してください。

**障害時の意味論**: 編集者上限カウンタは認可/セキュリティ境界では
なくソフトな可用性制御であり、その fail-open 挙動 (上限を強制する
代わりに弾かず通す) は意図的な設計判断です — [障害時の挙動](#障害時の挙動-failure-modes)
参照。Redis に到達できないことは JWT / WS-token 認証を一切バイパス
しません — どちらのチェックも Redis に依存していません。rate
limiting も fail-open です: Redis へのラウンドトリップが例外を
投げると、リクエストはブロックされず許可されます。そのため rate
limiter が必要とする ACL の権限が漏れていると、Redis 障害時と
まったく同じ「サイレントに検知されない無効化」が起きます — ACL を
絞る際は注意してください。

**key/channel の分離**: 8経路はそれぞれ独立した prefix を使います:
`crowi:collab` (共同編集 pub/sub、ドキュメント単位のサブキー)、
`crowi:collab:editors:<pageId>` (編集者上限)、`crowi:presence:*`
(プレゼンスのハッシュ/チャンネル)、`crowi:notifications:user:<userId>`
(通知)、固定チャンネル `config` (設定同期 — `crowi:` prefix では
ない)、`crowi:ratelimit:*` (rate limiting)。LRU だけは固定 prefix
のない、運用者が選ぶ namespace キーを使います。**worktree や
クラスタの分離に Redis URL のデータベース番号セグメントを頼らない
でください** — ここで説明したどの仕組みもデータベース番号には
依存しておらず、上記の prefix の代わりにはなりません。

**代替エンジンの開示**: 前述の「Valkey」参照 — テスト済みサポート・
best-effort なプロトコル互換・非サポート構成は3つの異なる階層です。
Valkey の BSD-3-Clause ライセンスと独立したガバナンスは、それを
選好する運用者にとって重要ですが、バイナリ/RDB の永続化互換性は
保証されません — 前述の「複数レプリカでの移行とロールバック」参照。

**サプライチェーン**: (前述の「イメージ pin 方針」のとおり) 明示的
なイメージファミリ/バージョンを pin し、可能な限りテスト済みの
digest を自分たちのリリースツールに記録し、汎用的な distro alias
を互換性の主張の代わりに使わないでください。

**CI が検証していること/していないこと**: CI は8経路すべてに対して
実 Redis 8 の smoke テストを実行しますが、**制限付き ACL ユーザー
に対しては実行していません** — 上記の行列はソースコードの精査から
書き起こしたものであり、自動化された permission-denial テストで
検証されたものではありません。運用者向けの参考情報として扱い、
契約とはみなさず、`redis`・`ioredis`・`@hocuspocus/extension-redis`
をアップグレードした際は再確認してください。

## キャパシティチューニング

- `COLLAB_MAX_EDITORS_PER_PAGE` で同時編集者上限を変更できます。20 は
  経験則的な目安で、awareness の cursor 描画コストが大きくなる前の
  上限です。これを大きく上げる場合は、editor 側の同時 awareness 配信に
  対する描画負荷も検証してください。
- Y.Doc の差分は `debounce: 2000` ms で `onChange` に流れます。これは
  Hocuspocus のデフォルトを継承していて、変更が小さいうちは無駄な
  `PageYjsUpdate` 書き込みを抑えます。
- `PageYjsUpdate` は TTL 1 時間で自動 expire し、ベースラインの
  `Page.yjsState` への compaction も定期的に走ります。1 ページに対して
  延々と編集が続いても DB は線形には肥大化しません。

## Save の SLO

- 保存処理は通常 100-500ms で完了します。
- サーバ側には 5 秒のタイムアウトがあり、5 秒を超えると 408 相当の
  エラーをクライアントへ返します。
- ただし**タイムアウトしても実際には保存が成功している可能性**が
  あります (DB は書き込み済みで応答が遅延しただけのケース)。
  クライアント側は自動リトライしません。ページを reload して最新
  revision を確認するのが正しい対処です。
- 5 秒タイムアウトはあくまで extreme slow への安全網であり、通常の
  ネットワーク条件では十分余裕があります。タイムアウトが恒常的に
  発生する場合は MongoDB のレイテンシ / renderer 処理時間 / 接続
  プールサイズを疑ってください。
