title: ストレージドライバ
description: ローカル / S3 のファイルストレージ設定
---

Crowi にアップロードされた添付ファイルは、**ストレージドライバ** を通じて
保存されます。Crowi 2.0 では、どのドライバを使うかをランナープロジェクトの
`crowi.config.json` (`storage.driver`) で選択し、ドライバの実体は対応する
`@crowi/plugin-storage-*` プラグインが提供します。

> **Note**: Crowi v1 にあった `FILE_UPLOAD` 環境変数は廃止されました。
> ストレージの選択は `crowi.config.json` の `storage.driver` と、対応する
> `@crowi/plugin-storage-*` パッケージの組み合わせで行います。

## 利用できるドライバ

| ドライバ名 | 提供プラグイン | 保存先 |
| ---------- | -------------- | ------ |
| `local` | `@crowi/plugin-storage-local` (デフォルトで常に有効) | サーバのローカルファイルシステム |
| `s3` | `@crowi/plugin-storage-aws-s3` | Amazon S3 (互換ストレージ含む) |

`@crowi/plugin-storage-local` は **暗黙のデフォルトプラグイン** として常に
読み込まれます。`crowi.config.json` に何も書かなければ、`local` ドライバが
使われます。

## ローカルストレージ (local)

ローカルストレージは、アップロードファイルをサーバのファイルシステムに
保存します。最小構成では設定は不要で、`crowi.config.json` を省略するか
次のように書くだけで有効になります。

```json
{
  "storage": {
    "driver": "local"
  }
}
```

保存先ディレクトリのデフォルトは `data/uploads` です (`crowi.config.json`
を置いたディレクトリからの相対パス)。

> **Tip**: コンテナで運用する場合は、保存先ディレクトリを永続ボリュームに
> マウントしてください。コンテナを作り直すとローカルファイルは失われます。
> S3 を使えばこの心配はなくなります。

## S3 ストレージ (s3)

Amazon S3 (または S3 互換ストレージ) にファイルを保存するには、
`@crowi/plugin-storage-aws-s3` プラグインを使います。

### 1. プラグインを有効化する

`crowi.config.json` の `plugins` に S3 ストレージプラグインを追加し、
`storage.driver` を `s3` にします。

```json
{
  "plugins": [
    "@crowi/plugin-storage-aws-s3"
  ],
  "storage": {
    "driver": "s3"
  }
}
```

`@crowi/plugin-storage-aws-s3` は AWS の共通クレデンシャル基盤である
`@crowi/plugin-aws` に依存しているため、依存プラグインは自動で
読み込まれます。プラグインの解決方法の詳細は
[プラグインの管理](../plugins/managing) を参照してください。

### 2. バケットとクレデンシャルを設定する

S3 のバケット名と AWS のクレデンシャルは、管理画面から設定します。

- **バケット名** — `@crowi/plugin-storage-aws-s3` 自身の設定。管理画面の
  プラグイン設定 (`/admin/plugins`) から「AWS S3」の設定を開いて入力します。
- **リージョン / アクセスキー / シークレットキー** — `@crowi/plugin-aws`
  の設定。同じくプラグイン設定から入力します。

アクセスキー ID とシークレットアクセスキーは機密扱いとして登録されて
おり、`CROWI_ENCRYPTION_KEY` が設定されていれば自動で暗号化されて
保存されます。詳細は [機密設定の暗号化](./encryption) を参照してください。

> **Tip**: EC2 / ECS のインスタンスロールや IRSA を使う場合は、アクセス
> キーを空のままにしておけば、AWS SDK のデフォルトのクレデンシャル解決
> (環境変数やインスタンスメタデータ) が使われます。

### 3. 設定の即時反映

プラグインの設定を管理画面から保存すると、S3 ドライバは `reconfigure`
により **サーバ再起動なしで** 新しいバケット / クレデンシャルを反映
します。

## ストレージの現在の状態を確認する

管理画面のストレージ画面 (`/admin/storage`) を開くと、登録されている
ドライバの一覧と、現在アクティブなドライバが表示されます。内部的には
`GET /api/admin/storage` が呼ばれ、各ドライバについて以下が返ります。

- `driverName` — ドライバ名 (`local` / `s3` など)
- `pluginName` — そのドライバを登録したプラグイン名
- `isActive` — `crowi.config.json` で選択中のドライバかどうか

## ドライバの切り替えとファイル移行

ドライバを切り替える (例: `local` → `s3`) と、`crowi.config.json` を
書き換えた時点で **新規アップロードは新しいドライバに保存** されます。
しかし、**既存のファイルは自動では移動しません**。古いドライバに残った
ファイルは、`crowi-admin` CLI で新しいドライバへコピーします。

### crowi-admin rebuild storage copy

`crowi-admin` はサーバ内 (ssh / kubectl exec) での実行を想定した運用者用
CLI です。`rebuild storage copy` サブコマンドで、あるドライバから別のドライバへ
全オブジェクトをコピーできます。

```bash
# local から s3 へ全ファイルをコピー
crowi-admin rebuild storage copy --from local --to s3

# まず対象キーだけを確認する (コピーは行わない)
crowi-admin rebuild storage copy --from local --to s3 --dry-run
```

ポイント:

- コピー元・コピー先の **両方のドライバが、いずれかのプラグインで
  読み込まれている** 必要があります。`crowi.config.json` の `storage.driver`
  が指す「アクティブなドライバ」とは無関係なので、`s3` をアクティブに
  する前に `local` から `s3` へデータを先にコピーしておけます。
- `--dry-run` を付けると、コピー対象のキーを列挙するだけで実際の書き込みは
  しません。件数の事前確認に使えます。
- 添付ファイルの行は MongoDB のカーソルで逐次処理されるため、ファイル数が
  非常に多くてもメモリ使用量は一定です。
- 1 件単位のエラーはイテレーションを止めず、`failed` カウントに加算
  されます。再実行は安全です (local / S3 ドライバはキー単位で上書きします)。

終了コードは次のとおりです。

| 終了コード | 意味 |
| ---------- | ---- |
| `0` | 全件コピー成功 (または dry-run 完了) |
| `1` | 致命的エラー (初期化失敗、または処理開始前の例外) |
| `2` | 部分的失敗 (コピーは走ったが 1 件以上失敗 — 再実行を推奨) |

### 推奨される移行手順

`local` から `s3` へ移行する場合の安全な手順:

1. `@crowi/plugin-storage-aws-s3` を `crowi.config.json:plugins` に追加し、
   管理画面で S3 バケット / クレデンシャルを設定する (`storage.driver` は
   まだ `local` のまま)。
2. `crowi-admin rebuild storage copy --from local --to s3 --dry-run` で対象件数を
   確認する。
3. `crowi-admin rebuild storage copy --from local --to s3` で実際にコピーする。
   `failed` が出た場合は再実行する。
4. `crowi.config.json` の `storage.driver` を `s3` に変更し、API を
   再起動する。
5. 新しいアップロードとダウンロードが S3 経由で動くことを確認する。

> **Tip**: 手順 1 で先に S3 へデータをステージングしておけば、ドライバを
> 切り替えた瞬間からダウンタイムなしで S3 が使えます。

### crowi-admin rebuild attachment-display-derivatives

[添付ファイル](../guide/attachments) の画像は、表示用に最適化された
派生ファイルをアップロード時にベストエフォートで生成します。
`rebuild attachment-display-derivatives` サブコマンドは、この派生ファイルを
既存の添付ファイルに対して事後生成・修復・回収するための運用コマンドです。

```bash
# 未生成/失敗のみを対象に、通常どおり生成する
crowi-admin rebuild attachment-display-derivatives

# まず対象件数だけを確認する (書き込みなし)
crowi-admin rebuild attachment-display-derivatives --dry-run

# 現行レシピの記述済みレコードも含め、全件を再生成する (ストレージ移行後は必須)
crowi-admin rebuild attachment-display-derivatives --force

# 「記述はあるが実体が無い」ものだけを狙って修復する
crowi-admin rebuild attachment-display-derivatives --repair-missing

# 無参照になった派生オブジェクトを報告する (local ドライバのみ、削除はしない)
crowi-admin rebuild attachment-display-derivatives --gc

# 報告された無参照オブジェクトを実際に削除する
crowi-admin rebuild attachment-display-derivatives --gc --confirm
```

主なフラグ:

| フラグ | 説明 |
| ------ | ---- |
| `--dry-run` | Mongo・ストレージのどちらにも書き込まず、対象件数と内訳のみ報告する |
| `--concurrency <n>` | 並列ワーカー数 (既定 `2`)。容量見積もりは後述 |
| `--force` | 現行 recipe で既に記述済みのレコードも再評価・上書きする |
| `--repair-missing` | 現行 recipe の `resized` レコードだけを対象に、実体の有無を `get()` で確認し、無いものだけ再生成する (デコード・再エンコードは行わない軽量モード) |
| `--only-missing` | `derivatives.display` が未記録の添付ファイルのみを対象にする |
| `--only-stale` | 記録済みの `recipeVersion` が現行と異なる添付ファイルのみを対象にする |
| `--page-id <id>` | 指定したページの添付ファイルのみを対象にする |
| `--since <iso>` | この ISO 8601 タイムスタンプ以降に作成された添付ファイルのみを対象にする |
| `--until <iso>` | この ISO 8601 タイムスタンプ以前に作成された添付ファイルのみを対象にする |
| `--gc` | 無参照になった派生オブジェクトの候補を報告する (local ドライバのみ、v1) |
| `--gc-grace-hours <n>` | `--gc` の候補から除外する猶予期間 (既定 24 時間)。生成中の `put`→publish の間隙を無参照と誤認しないための安全マージン |
| `--confirm` | `--gc` の候補を実際に削除する (指定しない限り report-only) |

ポイント:

- **通常実行 (`--force`/`--repair-missing` なし) は idempotent** です。
  現行 recipe の `resized`/`passthrough`/`unsupported` はスキップされ、
  `failed`・未生成・古い recipe のレコードだけが再処理されます。
  **メタデータ上は `resized` だが実体がストレージから失われている場合、
  通常実行では検出されずスキップされ続けます** —— この修復には
  `--force` または `--repair-missing` が必要です。
- Attachment の行は MongoDB のカーソルで**単一の producer だけが pull**
  し、取り出したアイテムの処理だけが `--concurrency` で有界並列化されます
  (`storage copy` と同じくメモリ使用量は一定に保たれます)。
- 各ワーカーは original をローカル一時ディレクトリへステージしてから
  生成処理に渡し、処理後に自分がステージした一時ファイルを削除します。
  同時にステージされるデータ量の目安は **`--concurrency` × 100MB**
  (footer 添付追加の実際の上限に基づく) です。`--concurrency` を既定より
  上げる場合は、このディスク/メモリ使用量の見積もりを掛け直してください。
  ステージ前に空き容量を確認し、不足時はそのアイテムを安全に skip・
  failed として記録します。
- **SIGINT (Ctrl-C)** を受け取ると、新規アイテムの受付を止め、進行中の
  一時ファイルを片付けてから直近の進捗サマリを出力し、**非ゼロで終了**
  します。
- 項目単位の失敗があっても実行は継続し、Attachment ID と分類済みの
  理由を出力します。

終了コードは次のとおりです。

| 終了コード | 意味 |
| ---------- | ---- |
| `0` | 全件成功 (または dry-run 完了) |
| `1` | 致命的エラー (初期化失敗、または処理開始前の例外) |
| `2` | 部分的失敗 (1 件以上のアイテムが失敗 — `failed` の内容を確認して再実行を検討) |
| SIGINT による中断時 | 上記に関わらず非ゼロで終了する |

> **Note**: **ストレージドライバを移行した直後は `--force` の実行が
> 必須です。** `storage copy` は original のみをコピーし、派生ファイルは
> コピーしません(派生ファイルは durable data ではなく disposable な
> キャッシュのため)。移行後にそのまま `rebuild
> attachment-display-derivatives` を実行しても、全ての `resized`
> レコードは(新ドライバ上に実体が無くても)「完了済み」として通常実行
> ではスキップされ、**何も再生成されません**。必ず `--force`(全件
> 再評価)、または実体が失われた記述子だけを狙いたい場合は
> `--repair-missing` を実行してください。`--force` 実行までの間、
> canonical URL は original へ安全にフォールバックし続けます(データ
> 損失ではありません)。

> **Note**: **S3 での派生オブジェクトの孤児残存リスク**。ローカル
> ドライバの atomic write 化と、削除処理の原子的スナップショット取得 +
> 決定的キーの sweep により、通常運用ではほぼすべての孤児発生源が閉じて
> います。ただし、運用規約(rebuild/`--gc` は同時に 1 プロセスのみ)に
> 反して複数のプロセスが同じ添付を並行処理した場合など、ごく稀に
> 無参照オブジェクトが残ることがあります。`--gc` は v1 では local
> ドライバのみに対応しており、S3 では「未対応」を報告して正常終了
> します。長期的な蓄積が気になる場合は、S3 の `derivatives/` プレフィックス
> 配下に対して十分保守的な(例えば 1 年程度の)有効期限のライフサイクル
> ルールを **最後の砦としてのみ** 設定することを推奨します —— ライフ
> サイクルルールは「参照されているか」を判定できず経過時間でしか判断
> できないため、短い有効期限を設定すると生きた派生ファイルまで削除して
> しまい、original フォールバックへ静かに劣化します。`--gc` の代替には
> なりません。

## エディタからのアップロード制限

ページ編集画面では、画像の **貼り付け (paste)** とファイルの
**ドラッグ&ドロップ** でエディタへ直接アップロードできます
(利用者向けの説明は [添付ファイル](../guide/attachments) 参照)。
これらのアップロードには、サーバ負荷とストレージ消費を抑えるための
制限がかかっています。

### レート制限

エディタからのアップロードは **1 ユーザーあたり 1 分間に 20 回** まで
です。上限に達すると `POST /api/attachments/upload` は HTTP 429 を
`Retry-After` ヘッダ付きで返し、エディタ側には「アップロード上限に
達しました。N 秒後に再試行してください」というトーストが表示されます。

### サイズ上限

| 経路 | 1 ファイルあたりの上限 |
| ---- | ---------------------- |
| 画像の貼り付け (paste) | 10 MB |
| ドラッグ&ドロップ | 50 MB |

ドラッグ&ドロップは 1 回の操作で **最大 5 ファイル** まで扱えます。
これを超えてドロップした場合はアップロードされず、トーストで通知
されます。

### ファイル種別の許可リスト

エディタからアップロードできるファイル種別は許可リストで制限されて
います。既定の許可リストは次のとおりです。

| 分類 | 受け付けるもの |
| ---- | -------------- |
| 画像 | `image/png` / `image/jpeg` / `image/gif` / `image/webp` / `image/svg+xml` |
| 文書 | `.pdf` / `.txt` / `.md` / `.csv` |
| アーカイブ | `.zip` |

許可リストにない種別は拒否され、エディタ側には拒否された種別名を
添えたトーストが表示されます。許可リストはインスタンス全体に対する
グローバル設定です(ユーザーグループ単位の設定はありません)。

> **Note**: これらの制限はエディタからの直接アップロード経路に対する
> ものです。ページフッターの添付ファイルセクションからのアップロード
> やストレージドライバ自体の設定とは独立しています。
